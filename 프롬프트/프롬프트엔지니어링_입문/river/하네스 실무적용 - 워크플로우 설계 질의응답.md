# 하네스 실무적용 — 워크플로우 설계 질의응답

> 형식: river가 「입문가이드 질의응답 정리」를 마친 뒤, **"반복되는 개발 플로우를 하나의 단위로 굳히고 싶다"**는 번외 고민을 10년차 AI 전문가 페르소나와 **한 문항씩 역으로** 검증한 기록.
> 앞 문서가 "하네스가 *무엇인가*"였다면, 이 문서는 "그걸 *내 손의 개발 워크플로우로 어떻게 설계하나*". 이번엔 전문가가 묻고 river가 답하는 **소크라테스식** 진행.
> 작성일: 2026-06-15

---

## 총평

river는 "개발은 반복적이다(파악→구조→코드→실행확인→디버깅→테스트→완료) → 이 전체 플로우를 하나의 단위로 정의해 다중 사용자 일관성을 확보하고 싶다"는 좋은 목표에서 출발했다. 7문항을 거치며 본인이 직접 **라우터 + 전용 워크플로우 + 게이트** 구조를 재구성해냈고, 특히 Q5에서 전문가의 "단일 거대 플로우" 오해를 **역으로 교정**한 것(=라우터 구조)이 백미였다.

**핵심 교정 두 가지:**
1. "막는 규칙은 프롬프트로 적으면 된다" → **불변식은 프롬프트(부탁)가 아니라 센서(벽)로.** 모델은 순응적이라 글로 적은 규칙은 한 번의 우김에 무너진다 (Q1·Q2).
2. "최대한 재사용" → **재사용 vs fork는 판단의 영역.** 결정적으로 못 박고, 가이드+센서+사람 게이트로 분담 (Q7).

**관통 원리:** 모든 설계 장치가 결국 앞 문서의 **가이드(피드포워드) + 센서(피드백) + 사람 게이트** 삼분할로 떨어진다.

## Q1. "벗어나면 막는다"는 누구한테 맡길까?

**질문:** 워크플로우의 "정해진 방법에서 벗어나면 막는" 규칙 중 *절대 빠지면 안 되는 것*(테스트 누락·브랜치 규칙)을 (a) 스킬 프롬프트에 글로 적기 vs (b) CI·훅·lint로 차단 — 어디에 맡길까?

**river 답:** (a). 어겼을 때 소통하려면 시작 단계 검증이 필요하고, (b)는 끝나고 확인이라 수정량이 커진다.

**채점 — 절반 정답, 절반은 함정:**
- ✅ **맞은 직관:** "일찍 개입이 늦게 잡기보다 싸다" = 피드포워드(가이드)·Keep Quality Left. 그래서 (a) 가이드는 반드시 필요.
- 🚩 **함정 ①:** "(b) 센서 = 끝에만"은 틀린 전제. 센서는 pre-commit 훅·저장 시 lint·컴포넌트별 테스트로 **앞에서도 돈다**(= Keep Quality Left의 뜻).
- 🚩 **함정 ②(핵심):** *절대 불변식*을 (a)에만 맡기면 **모델이 순응적이라 봐준다.** "급하니 테스트 건너뛰자" 한마디에 글 규칙이 무너짐. river 자신의 Q2 문서: *"가이드만 → 한 번 까먹으면 그냥 뚫림."*

**정답:** (a)냐 (b)냐가 아니라 **둘 다, 역할 분담.** (a)=평소 유도+조기 소통, (b)=그래도 어기면 물리적 차단. **(a)는 부탁, (b)는 벽.**

→ ✅ 교정 완료.

## Q2. (a)만 있을 때 실제로 무슨 일이 나나?

**질문:** "테스트 반드시 작성"을 프롬프트로만 적어둔 상태에서 팀원이 "시간 없으니 테스트 생략하자" 하면, 에이전트는 버틸까 넘어갈까? 그게 "다중 사용자 일관성" 목표에 어떤 결과를?

**river 답:** 넘어간다. 사용자마다 다른 결과물이 나온다.

**채점 — 만점.** 그리고 이게 결정적인 이유: river가 (a)에 걸었던 목표가 바로 **다중 사용자 일관성**인데, (a)만 쓰면 모델이 사람마다 봐주니 **그 목표가 가장 먼저 무너진다.**

> **일관성은 "스킬을 잘 적었기를 바라는 것"이 아니라 "산출물이 자동 검사당하는 것"에서 나온다.** 불변식은 센서에, 가이드는 그 위에 얹어 조기 소통용으로.

→ ✅ 이해 완료.

## Q3. 사람은 *어디서* 멈춰야 하나 — "멈추지 마" vs "컴포넌트마다 확인"

**질문:** (1)"확인 포인트 전까진 안 멈춤"과 (2)"컴포넌트 단위로 세세히 확인"은 모순 아닌가? 자율 실행 단위와 멈춤 단위를 각각 뭘로 잡아야 충돌이 사라지나?

**river 답:** 컴포넌트 안에선(설계 확인→테스트→개발→스토리북→확인 가능할 때까지) 안 멈추고, 컴포넌트 경계에서 멈춰 확인. + 페이지/큰 기능은 컴포넌트 여러 개를 묶는 상위 단위.

**채점 — 통과 + 보너스:**
- ✅ **핵심 정답:** 경계 안=자율(안 멈춤), 경계선=게이트(확인). **하나의 경계가 두 역할.** 모순은 "같은 컴포넌트 경계의 안쪽이냐 경계선이냐"의 차이였을 뿐.
- ✅ **보너스:** 묻지 않은 **2단 계층**을 정확히 세움 (= OpenAI 케이스: 페이지/기능=작업/브랜치/worktree, 그 안에 컴포넌트).
- ✅ 설계-게이트(앞)·스토리북-게이트(뒤)로 컴포넌트를 감싼 것 = Q5 심화 ④ **"사람은 중간(타이핑)이 아니라 양 끝"** 그대로.

```
페이지/기능  = 하나의 작업 = 브랜치/PR = worktree
   └─ 컴포넌트 = 자율실행 + 게이트 단위
```

→ ✅ 이해 완료.

## Q4. 모든 게이트를 *사람*이 봐야 할까?

**질문:** 컴포넌트마다 사람 게이트가 앞뒤로 2개면 8개 컴포넌트 = 16번 멈춤. 어떤 게이트가 기계 자동이고 어떤 게 사람 눈이 필요한가?

**river 답(예시):** 회원가입을 7개 작업으로 쪼갬. 1·2(API)는 중단 없이, 3·4·5(컴포넌트)는 스토리북에서 한 번씩 멈춰 확인, 7(연동)은 마지막 확인.

**채점 — 행동은 정답, 원리를 추출:**
- river가 무의식적으로 쓴 규칙 = **"사람만 판단할 수 있는 게 있느냐."** API는 안 보임→기계 게이트로 충분→자동 통과. 컴포넌트는 보임→"의도대로 보이나"는 사람만→사람 게이트.
- 🚩 **표현 함정(Q1 복습):** "중단 없이" = **사람을 안 부른다**는 뜻이지 **검사를 안 한다**가 아님. API도 타입·테스트(기계 게이트)는 통과해야 함. 깨진 API가 *조용히* 넘어가면 6·7번에서 터짐.
- **한 단계 더:** 사람 게이트도 기계가 *먼저* 거른다.

```
컴포넌트 개발 → [기계] 테스트·렌더 OK? → 통과 시 → [사람] "보기 좋나?"
                     └ 실패 시 사람 안 부르고 에이전트가 고침
```
이유: **사람 시간이 가장 비싸다.** 기계가 "최소한 돌아간다"를 보장한 뒤에야 사람을 부른다.

→ ✅ 이해 완료.

## Q5. 이 플로우가 "회원가입" 말고 "버그 수정"에도 통할까?

**질문(유도):** "로그인 버튼 에러 고쳐줘"에 7단계 빌드 플로우가 그대로 맞나? 안 맞으면 "하나의 동일한 플로우로 처리"라는 목표에 뭘 말해주나?

**river 답(전문가 전제를 교정):** "무조건 하나의 플로우"가 아니다. **입력 → 공통 첫 플로우(분류)** 로 "어떤 작업인가?"(기능추가/개선/버그/문서/워크플로우 수정)를 먼저 가른 뒤, 정의된 워크플로우로 라우팅. 없으면 기존 것 조합, 새 워크플로우 추가는 브랜치/PR/승인 필수.

**채점 — river가 전문가를 교정. 라우터 구조 정답:**

```
입력 → [공통: 분류] "어떤 작업인가?"
        ├ 기능 추가  → 기능추가 워크플로우
        ├ 기능 개선  → 개선 워크플로우
        ├ 버그 해결  → 디버그 루프(/diagnose, 재현-먼저)
        ├ 문서 작업  → to-prd 등 조합
        └ 미정의     → 기존 조합 / 새 워크플로우는 PR+승인(브레이크)
```
- ✅ 이게 곧 **"얇은 오케스트레이터 + 작은 스킬들"**(목차 패턴). 버그가 디버그 루프로 갈라지니 "빌드 ≠ 디버그"도 라우터가 해결.
- ✅ "새 워크플로우 추가 = PR+승인" = Q5 심화 ④ **"하네스 진화는 사람"** — 하네스를 바꾸는 행위 자체에 사람 게이트.

→ ✅ 이해 완료.

## Q6. 라우터가 틀리거나 헷갈리면?

**질문:** (1)모호한 입력("로그인 페이지 손봐줘")으로 오분류, (2)섞인 작업("폼 만들고 + 버그도 고쳐") — 분류가 추론적 게이트임을 인정하면, 혼자 추측해 진행이 맞나?

**river 답:** 역질문해야 한다. "이 워크플로우로 갈까?" 확인, 또는 "내용이 부정확하다, 보기 중 선택하거나 더 설명해달라."

**채점 — 정답:**
> **추론적 게이트 + 확신 낮음 → 추측 말고 묻는다.**
- 섞인 작업은 라우터가 **"두 작업으로 보이는데 분리할까?"** 되물어 *쪼갠다.* 한 입력을 억지로 한 버킷에 넣지 않음.

→ ✅ 이해 완료.

## Q7. "무조건 최대한 재사용"이 항상 옳을까?

**질문:** 기존 `Button`과 70% 같지만 동작이 다른 버튼이 필요해 props를 계속 추가 → props 20개·if 범벅 괴물. 재사용해야 할 때와 fork해야 할 때의 기준은? (힌트: 결합도)

**river 답:** 어렵다. UI(디자인)로 나눠야 하나? 다른 사람들은 어떻게 하나? — *판단 영역이라며 전문가 설명 요청.*

**전문가 설명 (정답 없는 taste 영역):**
- **UI 차이는 fork 기준이 아니다.** `variant`/`size`/`color` 같은 *보이는 변형*은 props로 흡수. 정상.
- **진짜 기준:** *"같은 이유로 함께 변할 것"이면 재사용, "지금 우연히 비슷할 뿐 다른 이유로 변할 것"이면 fork.*
- **불리언 플래그 냄새:** *동작을 분기시키는* boolean이 늘면(`isModal`, `asLink`…) 🚩 fork/composition 신호. boolean 하나당 복잡도 ≈ 2배.
- **fork보다 composition 먼저:** 베이스는 멍청·범용으로 두고 특수 동작은 *감싸는* 새 컴포넌트로.
- **업계 휴리스틱:** ①Rule of Three(3번째 등장에서야 추상화) ②"잘못된 추상화보다 중복이 싸다"(Sandi Metz) ③디자인 시스템 프리미티브=적극 재사용 / 기능 컴포넌트=조합 위주.
- **결합도 회수:** props 20개 괴물 = 모든 호출처가 서로 엮임 → A 때문에 고치면 B·C가 깨짐 = `improve-codebase-architecture`의 *반대* 방향. 그래서 과한 재사용이 아키텍처를 악화.

**워크플로우에 박는 법 (삼분할):**
| 메커니즘 | 적용 |
|---|---|
| 가이드(CLAUDE.md) | "프리미티브는 재사용, 단 *동작 분기 boolean*을 공유 컴포넌트에 추가 금지 — 조합으로. 애매하면 물어라." |
| 센서(자동) | props 개수/복잡도 lint 임계값, 기존 컴포넌트 테스트로 회귀 차단 |
| 사람 게이트 | 재사용 vs fork "판단"은 사람 승인 (river가 이미 넣은 "재사용 시 먼저 승인") |

→ ✅ "결정적으로 못 박지 말고 가이드+센서+사람 게이트로 분담" 이해.

# 📋 최종 산출물 — 워크플로우 설계 골격

7문항에서 합의된, 실제로 만들 수 있는 골격:

```
[입력]
  │
  ▼
[① 라우터 — 공통 첫 플로우] (추론적)
  - "어떤 작업인가?" 분류: 기능추가 / 개선 / 버그 / 문서 / 워크플로우수정
  - 확신 낮거나 섞임 → 역질문(추측 금지), 섞이면 분리 제안
  │
  ▼
[② 전용 워크플로우로 라우팅] (조립식, 거대 단일 트리 ❌)
  - 버그 → 디버그 루프(/diagnose, 재현-먼저)
  - 기능추가 → 빌드 루프(아래)
  - 미정의 → 기존 조합 / 새 워크플로우는 PR+승인(브레이크)
  │
  ▼
[③ 빌드 루프 — 작업 단위 = 페이지/기능 = 브랜치/PR/worktree]
  - 계획·작업 쪼개기 → 큰 문서(스펙·순서) 작성 → [사람 게이트: 설계 OK?]
  - md 파일 먼저 생성, 사용자에게 순서 알림
  │
  ▼
[④ 컴포넌트 루프 — 자율실행 + 게이트 단위] (경계 안=안 멈춤)
  - 설계 확인 → 테스트 작성 → 컴포넌트 개발 → 스토리북 생성/실행
  - [기계 게이트] 테스트·렌더 통과? → 통과해야 다음
  - [사람 게이트] "의도대로 보이나?" (보이는 것만 사람, 안 보이면 자동 통과)
  - 재사용 만나면: 가이드 유도 + 복잡도 센서 + [사람 승인]
  │
  ▼
[⑤ 통합·연동 → 최종 확인 → 완료]

※ 모든 불변식(테스트 존재·브랜치 규칙·복잡도)은 프롬프트 아닌 CI/훅(센서)로 강제.
※ 워크플로우 자체의 진화(새 워크플로우 추가)는 PR+사람 승인 = 래칫.
```

**3대 원칙 (전 대화 관통):**
1. **불변식은 센서(벽), 취향·판단은 가이드(부탁)+사람 게이트.** 모델은 순응적 — 절대 규칙을 글에 맡기지 말 것.
2. **경계 안은 자율, 경계는 게이트.** 사람은 양 끝(의도·설계 / 리뷰)에만. 사람 게이트도 기계가 먼저 거른 뒤 호출.
3. **거대 트리 금지 — 라우터 + 조립.** 경우의수는 미리 다 짜지 말고 **래칫으로 자라게.**
