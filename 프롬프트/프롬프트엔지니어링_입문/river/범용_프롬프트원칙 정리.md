# 범용 프롬프트 원칙 정리

> 스터디 주제: "일반 원칙부터 익히자"의 후속. 「프롬프트 엔지니어링 입문 가이드」(`_공통/입문가이드.md`)를 기반 자료로, 모델이 바뀌어도 **변하지 않는 원칙**을 중심으로 정리.
> 범위: 입문가이드 §3(변하지 않는 7원칙) + §4(발전 기법)에서 "원칙으로 굳은 부분" + 가이드에 없지만 범용적으로 통하는 보강 원칙.
> 작성일: 2026-06-15
> 작성자: river

## 0. 왜 "기법"이 아니라 "원칙"인가

가이드의 결론을 한 줄로: **"기법을 외우지 말고 원칙을 이해하라."** 모델이 GPT-4 → Claude 4 → 다음 세대로 바뀌면 *기법의 최적값*은 바뀌지만, 원칙은 유지된다. 예를 들어 "few-shot 예시를 몇 개 줘야 하나"는 모델마다 다르지만, "예시로 패턴을 보여주면 모델이 따른다"는 원칙은 불변이다.

또 하나의 큰 그림(질의응답에서 정리한 것):
```
프롬프트 엔지니어링 ⊂ 컨텍스트 엔지니어링 ⊂ 하네스 엔지니어링
```
범용 프롬프트 원칙은 이 중 가장 **안쪽(프롬프트)** 의 기술이지만, 바깥(컨텍스트·하네스)에서도 그대로 통하는 *토대*다. 그래서 "일반 원칙부터" 익히는 게 맞다.

## 1. 변하지 않는 7원칙 (가이드 §3)

### 원칙 1 — 명확성 (Clarity)
AI는 머릿속을 못 읽는다. 모호한 질문 → 모호한 답.
- ❌ "이 코드 고쳐줘"
- ✅ "이 함수는 빈 리스트에서 IndexError를 낸다. 빈 리스트 처리 로직을 추가하고, 변경 이유를 주석으로 달아줘. [코드]"
- **핵심:** 원하는 것 + 제약 조건 + 출력 형식을 명시할수록 결과가 좋아진다.

### 원칙 2 — 맥락 제공 (Context)
AI는 내 상황을 모른다. 배경을 먼저 줄수록 관련성↑.
- ✅ "나는 스타트업 CEO, 상대는 잠재 투자자. 지난주 미팅 후속으로 IR 자료 첨부 메일. 톤: 전문적이되 친근, 200자 이내."
- **핵심:** 좋은 프롬프트의 90%는 "충분한 맥락을 줬는가"에서 갈린다.

### 원칙 3 — 예시 (Few-shot)
설명보다 예시가 강하다 (GPT-3, 2020에서 증명).
```
"안녕하세요" → "Hello"
"감사합니다" → "Thank you"
"사랑해요" → ???
```
- **핵심:** 패턴을 보여주면 그 패턴을 그대로 적용한다. (최신 모델은 zero-shot도 강해져 예시 필요성은 줄었지만 0이 된 건 아니다 — §4-1.)

### 원칙 4 — 역할 부여 (Role)
"당신은 ___입니다"가 어휘·관점·수준을 바꾼다.
- "10년차 시니어 백엔드 개발자" vs "대학교수, CS 개론 수준" → 같은 질문도 답이 달라진다.

### 원칙 5 — 단계별 사고 유도 (Step-by-step / CoT)
복잡할수록 "단계적으로 생각하라"가 효과적 (Wei et al. 2022).
- "각 단계의 이유를 설명하며 풀어줘."
- **주의(현재 방향):** 최신 추론 모델은 이걸 *내부적으로* 수행한다(§4-2). 그래서 명시적 CoT 지시의 필요성은 줄어드는 중 — 하지만 "추론 과정을 보여달라"고 요청하는 것 자체는 검증·디버깅에 여전히 유용.

### 원칙 6 — 구조화 (Structure)
출력 형식을 지정하면 일관성↑.
```
## 요약(3줄)  ## 주요 포인트(번호)  ## 결론
```
- Anthropic은 특히 **XML 태그**를 강력 추천:
```xml
<instructions>이 텍스트를 요약</instructions>
<text>[분석할 텍스트]</text>
```
- 구조화는 입력에도 통한다(§4-5): `<task>`, `<context>`, `<code>`, `<focus>`로 입력을 나누면 모델이 역할을 헷갈리지 않는다.

### 원칙 7 — 반복 개선 (Iteration)
첫 프롬프트가 완벽할 수 없다.
```
작성 → 결과 확인 → 문제 파악 → 수정 → 반복
```
- **핵심:** 실패한 출력의 원인 분석이 가장 빠른 학습. (이게 하네스의 "래칫 원칙"의 프롬프트 버전이다 — 실수 → 규칙으로 고정.)

## 2. 가이드에 없지만 범용으로 통하는 보강 원칙

7원칙은 토대이고, 실무에서 품질을 가르는 추가 원칙들. (출처: Anthropic/OpenAI 공식 가이드의 공통 권고를 정리)

### 보강 1 — 부정형보다 긍정형 (Do, not Don't)
"~하지 마"보다 "~해라"가 잘 먹힌다.
- ❌ "마크다운 쓰지 마"
- ✅ "순수 텍스트로, 줄바꿈만 써서 답해줘."
- 이유: 모델은 "하지 말라"는 대상을 오히려 떠올리기 쉽다. *원하는 행동을 직접 지시*하는 게 안전.

### 보강 2 — 모델에게 "모름"의 출구를 줘라
환각(hallucination)을 줄이는 가장 싼 방법.
- ✅ "자료에 근거가 없으면 '모르겠다'고 답하고 추측하지 마."
- 출구가 없으면 모델은 빈칸을 *그럴듯한 거짓*으로 채운다.

### 보강 3 — 독자(audience)와 목적을 명시
- "주니어에게" vs "CTO에게" vs "비개발자 고객에게" → 같은 내용도 톤·깊이가 달라진다.
- 원칙 2(맥락)의 특수 케이스지만 자주 빠뜨리는 축이라 따로 챙길 것.

### 보강 4 — 길이·형식을 정량으로
- "짧게"(❌) → "3문장 이내"(✅), "리스트로"(❌) → "최대 5개 불릿"(✅).
- 정성 표현은 모델마다 해석이 다르다. 숫자로 못 박아라.

### 보강 5 — 한 프롬프트엔 한 가지 일 (분해)
- 거대한 한 방 프롬프트보다 **프롬프트 체이닝**(§4-3)이 오류율 35~50%↓.
- "자료 수집 → 분석 → 작성"을 한 프롬프트에 욱여넣지 말고 단계로 쪼개라. → 이게 에이전트 워크플로우의 토대.

### 보강 6 — 근거를 먼저, 결론을 나중에 (reasoning-then-answer)
- "먼저 근거를 나열하고, 그다음 결론을 내려라."
- 결론을 먼저 뱉게 하면 모델이 그 결론에 끼워맞추는 경향. 추론을 앞세우면 정확도↑ (원칙 5의 응용).

## 3. "발전하는 기법" 중 원칙으로 굳은 것 (가이드 §4)

| 기법 | 변하는 부분(기법) | 변하지 않는 부분(원칙) |
|---|---|---|
| Few-shot → Zero-shot | 필요한 예시 개수 | "패턴을 보여주면 따른다" |
| CoT → Extended Thinking | 명시적 지시 필요 여부 | "추론을 거치면 정확해진다" |
| 프롬프트 체이닝 | 몇 단계로 쪼갤지 | "복잡한 일은 분해하면 오류↓" |
| RAG | 검색·임베딩 구현 방식 | "필요 정보를 컨텍스트에 넣어라" (= 컨텍스트 관리) |
| XML 구조화 | 태그명·모델별 반응 | "입력을 구조화하면 역할 혼동↓" |

→ **읽는 법:** 새 기법을 만나면 이 표처럼 "어디가 기법이고 어디가 원칙인가"를 갈라보라. 원칙만 챙기면 모델이 바뀌어도 재학습 비용이 거의 없다.

## 4. 원칙 → 컨텍스트/하네스로 이어지는 다리

범용 프롬프트 원칙은 바깥 계층에서 이렇게 확장된다(질의응답에서 정리한 연결):

| 프롬프트 원칙 | 컨텍스트 엔지니어링에서 | 하네스 엔지니어링에서 |
|---|---|---|
| 맥락 제공 | 컨텍스트 창에 무엇을 넣을지 설계(선택·압축·오프로딩) | RAG·메모리(CLAUDE.md)를 하네스 부품으로 |
| 구조화 | 시스템 프롬프트·역할·규칙의 배치 | 문서 세분화 + AGENTS.md=목차 |
| 역할 부여 | 멀티 에이전트의 각 역할 정의 | 서브에이전트 오케스트레이션 |
| 반복 개선 | 결과를 보고 컨텍스트 조정 | **래칫 원칙**(실수 → 영구 규칙) + 센서(테스트·리뷰) |

> 즉 "프롬프트를 잘 쓰는 법"을 제대로 익히면, 그게 곧 "컨텍스트를 잘 채우는 법" → "하네스를 잘 설계하는 법"의 토대가 된다. 가이드가 "일반 원칙부터"라고 한 이유.

## 5. 실습 체크리스트 (프롬프트 짤 때 점검)

- [ ] **명확성** — 원하는 것·제약·출력 형식을 다 적었나?
- [ ] **맥락** — 모델이 모르는 배경을 줬나? (독자·목적 포함)
- [ ] **예시** — 형식이 까다로우면 예시 1~2개 줬나?
- [ ] **역할** — 어떤 관점/수준으로 답해야 하는지 정했나?
- [ ] **추론** — 복잡하면 "근거 먼저, 단계적으로"를 요청했나?
- [ ] **구조** — 입력/출력을 XML·헤더로 구조화했나?
- [ ] **긍정형** — "하지 마" 대신 "해라"로 썼나?
- [ ] **출구** — "모르면 모른다고 해"를 넣었나?
- [ ] **정량** — 길이·개수를 숫자로 못 박았나?
- [ ] **분해** — 한 프롬프트에 일을 너무 많이 넣지 않았나?
- [ ] **반복** — 결과가 나쁘면 원인을 분석하고 프롬프트를 고쳤나?

---

## 6. 한 줄 결론

> **프롬프트의 세세한 기법보다, "원하는 것을 명확히 + 충분한 맥락과 함께 + 적절히 구조화해서 표현하는 능력"이 모델 세대를 넘어 통하는 진짜 역량이다.**
> 그리고 그 역량은 바깥 계층(컨텍스트·하네스)으로 그대로 확장된다.
