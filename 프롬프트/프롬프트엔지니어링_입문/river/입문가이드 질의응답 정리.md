# 입문가이드 질의응답 정리

> 형식: river가 「프롬프트 엔지니어링 입문 가이드」를 읽고 작성한 질문 + 가이드 작성자(10년차 AI 전문가) 페르소나의 답변을 **한 문항씩 대화로** 검증한 기록.
> 요약본이 아니라 질문·응답을 모두 담은 전문(full) 기록. 맨 끝에 요약 + "부족한 개념·자료 평가"를 붙임.
> 작성일: 2026-06-15

## 총평

river의 질문 세트는 입문자가 흔히 빠지는 "기법 암기" 함정을 피하고, 글의 가장 중요한 축(하네스 엔지니어링)을 집요하게 파고든 좋은 질문들이었다. 특히 외부 1차 자료를 직접 연결하려는 태도, "내가 이해한 게 맞냐"고 자기 모델을 검증하는 질문(Q5), 다른 스터디 개념(맷 포콕 스킬)과 연결하는 시도(Q2-e)가 돋보였다.

핵심 오해는 하나였다 — **"하네스 = 프롬프트 개념"**. 이 오해가 Q5와 후속 질문에 영향을 줬고, 대화를 통해 다음 두 단계로 완전히 교정됐다:
1. 하네스 = 프롬프트가 **아니라**, 모델을 뺀 시스템 **전체** (프롬프트는 그 일부).
2. 하네스 엔지니어링 = 배포된 **서비스의 런타임 동작**이 아니라, **AI 에이전트가 개발하는 작업 환경(개발 방식)**.

## Q1. "컨텍스트 관리"란 무엇인가?

**가이드 위치:** §1 하네스 구성요소 표 — "컨텍스트 관리 | 어떤 정보를 모델에게 줄지 결정"

**답변:** 컨텍스트 관리는 **"모델의 한정된 작업 메모리(컨텍스트 창)에, 지금 이 작업에 딱 필요한 정보만 골라 넣고 불필요한 건 빼는 일"**. 컨텍스트 창에는 사용자 입력·시스템 프롬프트·RAG 검색 문서·도구 실행 결과·이전 대화·에이전트 상태가 섞여 들어간다. 관리의 세 동작:

1. **선택(selection)** — 무엇을 넣을지 (RAG로 관련 문서만, 관련 없는 파일은 안 읽음)
2. **압축(compaction)** — 길어진 과거를 요약해 토큰 회수
3. **오프로딩(offloading)** — 큰 출력은 외부에 두고 포인터만 남김

§5 "컨텍스트 엔지니어링"이 이를 부르는 학문적 이름이고, "컨텍스트 관리"는 하네스가 그 일을 수행하는 기능 — 사실상 같은 것의 다른 호칭.

**핵심 직관:** 많이 넣을수록 좋은 게 아니다. 관련 없는 정보는 오히려 품질을 떨어뜨린다(context rot). 그래서 "관리" = 더하기뿐 아니라 **빼기**가 핵심.

→ ✅ 이해 완료.

## Q2. Martin Fowler(Böckeler) 「Harness engineering」 핵심 요약

**출처:** Birgitta Böckeler, *Harness engineering for coding agent users*, martinfowler.com (2026-04).

핵심 정의: `Agent = Model + Harness`. 하네스 = 모델을 제외한 모든 것 = "에이전트 행동을 안내·검증하는 바깥 통제 계층".

가장 중요한 기여 — 하네스를 **두 메커니즘**으로 분해:

**① 가이드(Guides) = 피드포워드 — "사고 전에 미리 막는다"**
- 추론적: `AGENTS.md`, 코딩 컨벤션, how-to 스킬 (모델이 읽고 해석)
- 계산적: 스크립트, codemod, Language Server, 부트스트랩 도구 (결정적 강제)

**② 센서(Sensors) = 피드백 — "결과를 보고 고친다"**
- 계산적: 테스트, 린터, 타입체커 (빠르고 결정적, 매 커밋)
- 추론적: 코드리뷰 에이전트, 시맨틱 분석 (느리고 비결정적, 비쌈)

> 핵심 통찰: **"피드백만 있으면 같은 실패를 반복하고, 피드포워드만 있으면 검증 안 된 규칙만 쌓인다."** → 둘 다 필요.

**그 외:** 세 규제 영역(유지보수성 > 아키텍처 적합성 > 행동/정확성, 성숙도 순) · Keep Quality Left(싼 검사는 왼쪽, 비싼 검사는 파이프라인) · Harnessability(강타입·명확한 경계일수록 하네스 걸기 쉬움; 정작 레거시가 가장 어려움) · 인간 역할("입력을 없애는 게 아니라 가장 중요한 곳으로 보내는 것").

**실용 take:** 모든 도구를 "가이드냐 센서냐 / 계산적이냐 추론적이냐" 격자에 분류해본다.

→ ✅ 이해 완료.

## Q2-b. QA 병목을 "가독성 향상"으로 푼다 (worktree·CDP)

river의 세 추측 모두 본질을 짚었고, 결론은 "거의 다 맞다".

**(1) worktree별 앱 부팅 = Codex가 직접 부팅?** → **맞다.** 사람은 "한 명령으로 부팅되도록 환경을 정비"했고, 실행 주체는 에이전트. 이게 "가독성"의 의미. 기존엔 동작 확인을 사람이 해서 병목이었는데, 이제 에이전트가 스스로 띄우고 클릭하고 로그 보고 "고쳐졌다"를 **자기검증(센서)** → 병목 해소.

**(2) 실행·제어 단위 = 커밋? PR?** → **"작업(브랜치) 단위", 사실상 PR에 가깝다.** 격리 단위는 git worktree. 커밋 단위 ❌. 하나의 작업 = 하나의 브랜치 = 하나의 worktree = 하나의 앱 인스턴스 + 하나의 관측성 스택, 끝나면 통째 폐기. 여러 Codex 병렬 작업이 서로 간섭 안 하는 이유.

**(3) CDP를 런타임에 연결 = 개발자도구의 기능?** → **개발자도구 GUI의 기능이 아니라, 그 도구가 쓰는 하부 프로토콜(API).** CDP는 WebSocket 기반 API라서 프로그램이 브라우저를 열고·이동·DOM 읽기·스크린샷을 하게 해준다(Puppeteer/Playwright가 쓰는 그것). Codex가 "헤드리스 브라우저를 조종하는 자동화 클라이언트"를 갖게 된 셈.

**합쳐지면:** worktree 격리 + CDP + 관측성 → 에이전트가 "수정 → 앱 띄움 → 클릭/관찰 → 로그 확인 → 자기판정"의 QA 루프를 사람 없이 완주.

→ ✅ 이해 완료.

## Q2-c. 세분화된 문서 목록 — 각 문서는 무엇을 담나

**디렉터리**
| 경로 | 내용 |

| `references/` | LLM 최적화 레퍼런스(`design-system`, `nixpacks`, `uv`) |

→ ✅ 이해 완료.

## Q2-e. 엔트로피·가비지 컬렉션 ≈ 맷 포콕 `improve-codebase-architecture`?

**직관이 옳다. 같은 패밀리다.**

**OpenAI GC:** Codex가 기존 패턴(나쁜 것 포함)을 복제 → 드리프트(AI 슬로프). 해법: `QUALITY_SCORE.md`의 golden principles 기준으로 백그라운드 작업이 주기적으로 스캔 → 일탈 발견 → 등급 갱신 → 타깃 리팩터링 PR 자동 생성. "취향을 한 번 명문화하면 모든 줄에 계속 강제."

**맷 포콕 스킬:** `CONTEXT.md`(도메인 언어) + `docs/adr/`(결정 기록) 기준으로 deepening(심화) 기회를 찾아 결합도↓·테스트/AI탐색 용이 구조로 끌어올림.

**공통점:** 둘 다 "인간 기준을 한 번 명문화하고, 그 기준을 향해 주기적으로 코드를 정렬해 드리프트/슬로프를 되돌린다" = 하네스의 **래칫·자기수정 루프**의 구체 사례.

**차이점:**
| | OpenAI GC | improve-codebase-architecture |
|---|---|---|
| 기동 | 자동·주기적 | 사람 호출 |
| 기준 | golden principles + QUALITY_SCORE.md | CONTEXT.md + ADR |
| 프레이밍 | 청소(cleanup) | 심화(deepening) |

비유: "자동 청소부 vs 호출하는 리모델링 전문가". 일반 패턴 이름: **"기준 명문화 → 주기적 정렬 루프."**

### Q2-e 보충 — 너네 저장소에 적용하면

| OpenAI | 너네 저장소 |
|---|---|
| golden principles | **`CLAUDE.md`** (폴더 구조·참여자표·스킬 라우팅·자동화 규칙 = 이미 있음) |
| `QUALITY_SCORE.md` | **`_공통/정리물 품질기준`** (출처 링크 必, 원리/기법 구분 必, 비교분석은 관점차 必 등 — 만들면 좋음) |
| 백그라운드 GC | **`study-log`에 정합성 점검 추가** 또는 `study-gc` 스킬 (빈 `_공통/`, 폴더와 안 맞는 스터디로그, 지난 마감일의 `다음주제.md`, 깨진 링크 스캔) |
| 센서 | git commit 규칙·자동화 규칙 (이미 있음) |

**통찰:** 너네는 "명문화"는 이미 했고, 빠진 건 **"기준과 실제 상태를 주기적으로 대조하는 루프"**.

→ ✅ 이해 완료.

## Q3. Addy Osmani 명제 "좋은 모델+나쁜 하네스 < 평범한 모델+좋은 하네스" — 어느 문서에?

**출처 확정:** Addy Osmani 블로그 ***Agent Harness Engineering***. 원문: *"A decent model with a great harness beats a great model with a bad harness."*

- **공식:** `coding agent = AI model(s) + harness`. 레버리지 대부분은 하네스에서.
- **"Skill issue" 리프레임:** 실패 시 모델 탓이 아니라 셋업 문제로 본다. *"모델이 할 수 있는 것과 실제로 보이는 성능의 격차는 대부분 하네스 격차다."*
- **결정적 증거:** 같은 모델(Claude Opus 4.6)을 커스텀 하네스에 넣었더니 Terminal Bench 점수가 크게 상승 → 모델 고정, 하네스만 교체로 성능↑. (Q5의 직접 근거)
- **래칫 원칙:** *"좋은 AGENTS.md의 모든 줄은 무엇이 잘못됐었는지로 추적 가능해야 한다."*

가이드 §6 방향3("하네스 설계가 핵심 경쟁력")의 근거 문장.

## Q5. "프롬프트 한 줄보다 둘러싼 시스템이 더 중요하다" — 핵심 교정

river는 모순된 두 문장을 동시에 들고 있었다:
- (A) 정의: "하네스 = 실수를 줄이는 **프롬프트 개념**"
- (B) 추측: "git workflow·DevTools Protocol·MCP 연동을 의미하나?"

**(B)가 정답, (A)가 오해.**

**오해 교정:** 하네스는 프롬프트를 *포함*하지만 프롬프트는 하네스의 *한 부품*일 뿐.
```
하네스 = 컨텍스트 관리 + 도구 + 훅 + 권한 + 피드백 루프 + 오류 처리
```
프롬프트는 "컨텍스트 관리"의 일부에 불과하고, 나머지는 코드·시스템 = (B)가 추측한 git workflow·CDP·MCP·린터·테스트. **(B) 추측은 하네스의 정의 그 자체.**

**"둘러싼 시스템이 더 중요"의 의미:**
- ~2025: 가치가 프롬프트 문자열에 있음.
- 2026: 같은 모델·프롬프트라도 *무엇을 읽고(컨텍스트)·할 수 있고(도구)·금지되고(권한)·검증하느냐(센서)*에 따라 성과가 갈림 → 가치가 시스템 전체로 이동.
- 증거: Osmani(Q3) — 프롬프트 고정, 하네스만 교체로 벤치 상승. (A)가 옳다면 일어날 수 없는 결과.

**멘탈모델:** 하네스는 "더 좋은 프롬프트"가 아니라 **"프롬프트가 작동하는 무대 전체"**. 무대가 좋으면 평범한 대사로도 좋은 연기가 나온다.

### Q5 후속 — 확인 퀴즈와 두 번째 교정

**퀴즈:** 다음 중 하네스는? ① 역할 부여 프롬프트 ② lint 훅 ③ worktree 부팅 스크립트 ④ MCP DB 도구 ⑤ 모델 가중치
→ river 답: ④. **정답: ①②③④ 전부 하네스, ⑤만 아님.**
- ⑤ 가중치 = 모델 그 자체(하네스가 감싸는 *대상*)라서 제외 — 정확히 봄.
- 단 ①(프롬프트)도 하네스. **Q5의 진짜 교훈은 "하네스 ≠ 프롬프트"가 아니라 "하네스 ≠ 프롬프트만"**. 프롬프트는 하네스에 *포함*되고 거기에 도구·훅·권한·격리·검증이 *더해진* 게 하네스 전체.
- 재정리: **하네스 = 모델(⑤)을 뺀 나머지 전부.**

### Q5 심화 — "스킬도 하네스인가 / 하네스 엔지니어링은 무엇의 범주인가 / 버그 나면 어떻게 도나 / 사람은 어디서 끼어드나"

**(1) `/tdd`·`/diagnose`·`improve-codebase-architecture` 같은 스킬도 하네스인가?** → **그렇다.** `/tdd`=가이드+센서, `/diagnose`=센서+절차 가이드, 아키텍처 스킬=가이드 갱신+정렬 루프. **스킬 = 하네스에 꽂는 부품.**

**(2) 하네스 엔지니어링은 무엇의 범주인가?** → river의 질문엔 두 '하네스'가 섞여 있었다:
| | (a) 하네스 엔지니어링이 말하는 것 | (b) river가 상상한 것 |
|---|---|---|
| 무엇 | **에이전트가 코드를 만드는 작업 환경/발판** | 배포된 제품의 런타임 동작 |
| 시점 | 개발·유지보수 시점 | 서비스 운영 시점 |

**핵심 교정: 하네스 엔지니어링은 (a)다.** 원문 제목이 *"for coding agent users" / "leveraging Codex"*. **"런타임 아키텍처가 아니라 개발 방식(practice/discipline)"** — DevOps가 도구가 아니라 일하는 방식이듯. "하네스가 적용된 서비스"가 따로 있는 게 아니라 "하네스를 잘 갖춘 개발팀/저장소"가 있는 것. (너네 저장소로 치면 하네스 = 정리 문서가 아니라 그걸 만드는 `CLAUDE.md`+스킬+git 자동화.)

**(3) 버그가 나면 실제 동작 (river의 두 시나리오 모두 맞음, 스케일만 다름):**
```
1. [사람]   "X 버그 있다" 보고 (또는 모니터링 자동 감지)
2. [에이전트] worktree 띄움 → CDP로 재현        ← 하네스 없으면 불가
3. [에이전트] 로그/트레이스로 원인 추적          ← 관측성 하네스
4. [에이전트] 수정 → 테스트(센서)로 자기검증
5. [에이전트] PR 생성
6. [사람]   PR 리뷰·승인·머지                  ← 사람의 게이트
```
"기능 개발 + 자체 QA"도 같은 루프를 키운 것(PR 전에 에이전트가 직접 띄워보고 테스트). **하네스 없으면 에이전트는 "추측"만, 있으면 "실행·관찰·검증"까지.**

**(4) 사람은 어디서 끼어드나 ("온전히 맡기지 마라"의 실제 의미):** 루프 중간(코드 타이핑)이 아니라 **양 끝과 설계** 4군데.
| 지점 | 무엇을 | 왜 사람이어야 |
|---|---|---|
| ① 의도/스펙(앞) | 무엇을 만들지·무엇이 "맞는지" 정의 | 정확성 기준은 사람이 정함 |
| ② 하네스 설계 | 테스트·CLAUDE.md·golden principle·부팅 환경 | 발판 까는 게 사람의 진짜 일 |
| ③ 리뷰/승인 게이트(끝) | PR 머지 승인, 특히 보안·제품 판단 | **행동(정확성) 하네스가 가장 미성숙** → AI 테스트만 믿으면 안 됨 |
| ④ 래칫(실패 후) | 실수 막을 규칙 한 줄 추가 | 하네스 진화는 사람 |

> Böckeler: **"좋은 하네스는 인간 입력을 없애는 게 아니라, 가장 중요한 곳으로 보내는 것."**
> 너의 노동이 "코드 타이핑"에서 → **"스펙 정의 + 발판 설계 + 게이트 리뷰 + 래칫"**으로 이동.

→ ✅ 이해 완료.

6. **Claude Code 하네스(Q4)** = 시스템프롬프트/CLAUDE.md·도구·권한·훅·서브에이전트·스킬·MCP·컨텍스트관리·슬래시커맨드·피드백루프의 총합.
7. **핵심 교정(Q5)** = ① 하네스 ≠ 프롬프트**만** (프롬프트는 하네스의 일부, 하네스 = 모델 뺀 전부). ② 하네스 엔지니어링 = 런타임 서비스가 아니라 **에이전트의 개발 환경(개발 방식)**. ③ 버그 처리/기능 개발은 같은 자율 루프의 다른 스케일. ④ 사람은 중간(타이핑)이 아니라 **의도·설계·게이트·래칫**에 끼어든다.

**이해 상태 종합:** river는 기법이 아니라 **원리(래칫·자기수정 루프) 층위에서 사고**(특히 Q2-e). 유일한 핵심 오해("하네스=프롬프트", "하네스=런타임 서비스")는 대화로 완전 교정. **위험한 오개념 없음.**
