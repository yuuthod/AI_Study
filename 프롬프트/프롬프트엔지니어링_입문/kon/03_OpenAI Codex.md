# 03_OpenAI Codex — Harness engineering: leveraging Codex in an agent-first world

> **대상 문서**: 「Harness engineering: leveraging Codex in an agent-first world」
> **저자/소속**: OpenAI Codex 팀
> **원문**: https://openai.com/index/harness-engineering/

---

## 1. 정의 & 핵심 주장

OpenAI는 **사람이 코드를 한 줄도 직접 쓰지 않고** 소프트웨어 제품의 내부 베타를 구축·출시하는 실험을 했다. 애플리케이션 로직·테스트·CI 구성·문서·관측성·내부 툴링까지 **모든 코드를 Codex가 작성**했고, 사람은 거의 전적으로 **프롬프트를 통해서만** 시스템과 상호작용했다.

핵심 주장은 **소프트웨어 엔지니어링 팀의 주 업무가 이동한다**는 것이다. 코드 작성에서 벗어나, **환경을 설계하고(designing environments) · 의도를 명시하며(specifying intent) · Codex가 안정적으로 일하도록 피드백 루프를 구축하는 것**으로 바뀐다. 사람의 시간과 주의가 가장 부족한 자원이므로, 그것을 어떻게 극대화하느냐가 관건이다.

## 2. 규모 & 타임라인 — 빈 git 저장소에서 시작

- 빈 저장소에 **첫 커밋: 2025년 8월 말**. 초기 뼈대(스캐폴드 — 저장소 구조·CI·포매팅 규칙·패키지 매니저·앱 프레임워크)와 최초 `AGENTS.md`까지 **GPT-5 기반 Codex CLI가 직접 생성**했다. 사람이 미리 써둔 코드는 없었다.
- **5개월 후 약 100만 줄.** Codex를 이끈 엔지니어는 처음 **3명**(현재 7명으로 성장)이었고, 약 **1,500개의 PR**을 열고 병합했다(엔지니어 1인당 하루 평균 3.5개). 처리량은 팀이 커지며 오히려 늘었다.
- 수작업 대비 **약 1/10 시간**으로 추정. 출력만을 위한 출력이 아니라, **내부 파워 유저 포함 수백 명이 매일 사용**하는 실제 제품이었다.

## 3. 엔지니어의 역할 재정의

사람이 직접 코딩하지 않으므로, **시스템·비계·레버리지**(leverage = 지렛대. 한 번의 사람 노력이 여러 에이전트 실행에 걸쳐 몇 배로 증폭되는 일. 예: 버그를 손으로 고치면 1건이지만, 그 버그류를 막는 린터 규칙을 만들면 이후 모든 실행에 자동 적용)에 집중하는 다른 종류의 엔지니어링이 필요했다. 초기 진행이 느렸던 것은 Codex의 역량 부족이 아니라 **환경이 갖춰지지 않았기** 때문이었다. 그래서 큰 목표를 더 작은 빌딩 블록(설계·코드·검토·테스트)으로 쪼개 에이전트가 이를 조립하게 하는 **깊이 우선(depth-first)** 방식을 썼다. 실패할 때 "더 분발"이 아니라 *"어떤 기능이 누락됐고, 그것을 에이전트가 읽기 쉽고 실행 가능하게 만들려면 어떻게 해야 하나?"*를 물었다.

PR을 완료할 때 Codex는 **자기 변경을 스스로 검토 → 로컬·클라우드의 에이전트 검토 추가 요청 → 사람·에이전트 피드백에 응답 → 모든 에이전트 검토자가 만족할 때까지 반복**한다(이를 글은 **랄프 위검 루프(Ralph Wiggum Loop)라 부른다). 사람이 PR을 검토할 수는 있으나 필수는 아니며, 거의 모든 검토를 에이전트 간 처리로 전환**해 왔다.

## 4. 애플리케이션의 가독성 향상 (Legibility)

코드 처리량이 늘자 **사람의 QA 역량이 병목**이 됐다. 그래서 UI·로그·메트릭을 **Codex가 직접 읽고 이해**할 수 있게 만들었다.

- **git worktree별로 앱을 부팅**해 변경마다 격리된 인스턴스를 띄운다.
- **Chrome DevTools Protocol**을 에이전트 런타임에 연결하고 DOM 스냅샷·스크린샷·탐색 스킬을 만들어, Codex가 버그를 재현하고 수정을 검증하며 UI 동작을 직접 추론하게 했다.
- **로컬 관측성 스택**(워크트리마다 임시 유지)으로 로그·메트릭·트레이스를 노출한다. Codex는 LogQL로 로그를, PromQL로 메트릭을 쿼리한다. 덕분에 *"서비스 시작을 800ms 이내로"* 또는 *"이 네 가지 핵심 사용자 여정에서 어떤 스팬도 2초를 넘지 않게"* 같은 프롬프트를 다루기 쉬워진다.
- 한 번의 Codex 실행이 **6시간 이상(종종 사람이 자는 동안)** 한 작업을 수행하기도 한다.

## 5. 저장소 지식을 "기록 시스템(System of Record)"으로

컨텍스트 관리가 가장 큰 과제였다. 교훈은 단순했다 — *"Codex에 1,000페이지짜리 설명서가 아니라 **맵(map)**을 줘야 한다."* "하나의 큰 AGENTS.md" 방식은 예측 가능하게 실패했다:

1. **컨텍스트는 희소 자원** — 거대한 지침 파일이 작업을 복잡하게 만들어 핵심 제약을 놓치게 한다.
2. **지침이 너무 많으면 지침이 아니다** — 모든 게 "중요"하면 중요한 건 없다. 에이전트가 탐색 대신 로컬 패턴 매칭을 한다.
3. **순식간에 낡는다** — 거대 매뉴얼은 낡은 규칙들의 무덤이 된다.
4. **검증하기 어렵다** — 단일 블롭은 기계적 점검(커버리지·신선도·소유권·교차링크)에 부적합해 드리프트가 불가피하다.

그래서 `AGENTS.md`(약 100줄)는 **백과사전이 아니라 목차**로 두고, 구조화된 `docs/` 디렉터리(`design-docs/`·`exec-plans/`·`product-specs/`·`references/` 등)로 **점진적 공개(progressive disclosure)** 한다. 특히 계획(plan)을 일급 아티팩트로 취급해, 복잡한 작업은 진행 상황·의사결정 로그와 함께 실행 계획(exec-plans)으로 저장한다. 이 모두를 전용 린터와 CI가 기계적으로 검증하고, 반복 실행되는 "doc-gardening" 에이전트가 낡은 문서를 찾아 수정 PR을 연다.

## 6. "에이전트가 못 보는 것은 존재하지 않는다"

저장소가 전적으로 에이전트에 의해 생성됐기에, 무엇보다 **Codex의 가독성에 최적화**됐다. 핵심 통찰 — *"에이전트 관점에서, 실행 중 컨텍스트에서 접근할 수 없는 것은 사실상 존재하지 않는다."* Google Docs·Slack·사람 머릿속 지식은 시스템에서 접근 불가다. **저장소 안의 버전 관리되는 아티팩트(코드·마크다운·스키마·실행 계획)만** 접근 가능하다. 그래서 Slack에서 합의된 아키텍처 패턴조차 검색 가능하게 **마크다운으로 인코딩**해야 한다("3개월 후 입사한 신입이 모르는 것과 같다").

이 관점이 절충점을 분명히 했다. 저장소 안에서 완전히 추론 가능한 의존성·추상화를 선호했고, **"지루하다"고 불리는 기술**(결합성·API 안정성·학습 데이터 내 풍부한 표현 덕에 에이전트가 모델링하기 쉬움)을 택했다. 때로는 외부 라이브러리의 불투명한 동작에 맞추기보다 **일부 기능을 직접 재구현**하는 편이 더 쌌다(예: 범용 `p-limit` 대신 자체 `map-with-concurrency` 헬퍼 — OpenTelemetry와 긴밀히 통합, 커버리지 100%).

## 7. 아키텍처와 취향을 기계적으로 강제

문서만으로는 일관성을 유지할 수 없다. **구현을 세세히 관리하지 않되 불변식(invariant)을 강제**해, 기초를 튼튼히 하면서 빠른 출시를 가능케 했다. 에이전트는 **엄격한 경계와 예측 가능한 구조**에서 가장 잘 동작하기 때문이다.

- 각 비즈니스 도메인은 고정된 계층으로 나뉘고, 코드는 **`Types → Config → Repo → Service → Runtime → UI`** 한 방향으로만 흐른다. 뒤로 향하는 import도, 계층 건너뛰기도 금지.
- 교차 관심사(인증·커넥터·텔레메트리·기능 플래그)는 **`Providers`라는 단일 명시 인터페이스**로만 유입된다. 그 외는 전부 불허이며 기계적으로 강제된다.
- 강제 수단은 **Codex가 생성한 커스텀 린터 + 구조적 테스트**, 그리고 소수의 **"취향 불변성(taste invariants)"**(구조적 로깅·명명 규칙·파일 크기 제한 등). 린트가 커스텀이라, **오류 메시지에 수정 지침을 담아 에이전트 컨텍스트에 주입**한다.
- 보통 수백 명 규모가 돼서야 도입하는 이런 아키텍처를, 코딩 에이전트에선 **초기 전제 조건**으로 둔다 — *"제약이 있어야 성능 저하나 드리프트 없이 속도를 낼 수 있다."*
- 결과 코드가 사람의 문체 취향과 늘 맞지는 않아도, **정확하고·유지보수 가능하고·향후 에이전트가 읽기 쉬우면** 기준 충족이다. 사람의 취향은 리뷰 코멘트·리팩터 PR·사용자 버그를 통해 **문서 갱신이나 툴링 인코딩으로 시스템에 되먹임**된다("문서가 부족하면 규칙을 코드로 승격").

## 8. 처리량이 바꾼 병합 철학

Codex 처리량이 늘자 전통적 규범이 역효과를 냈다. 저장소는 **최소한의 차단 게이트**로 운영되고, **PR은 수명이 짧으며**, 테스트 불안정성은 무기한 차단 대신 후속 실행으로 해결한다. 에이전트 처리량이 사람 주의를 크게 초과하는 시스템에서는 **수정 비용은 싸고 대기 비용은 크기** 때문이다. (처리량이 적은 환경엔 맞지 않는, 상황 의존적 절충이다.)

## 9. 자율성의 증가 — 그리고 일반화 경고

테스트·검증·리뷰·피드백 처리·복구 같은 개발 루프가 시스템에 인코딩되면서, 이제 에이전트는 **한 번의 프롬프트로** 다음을 처음부터 끝까지 주도할 수 있다: 현재 상태 검증 → 버그 재현 → 실패 영상 녹화 → 수정 구현 → 앱 실행해 검증 → 해결 영상 녹화 → PR 열기 → 피드백 응답 → 빌드 실패 감지·수정 → **판단이 필요할 때만 사람에게 에스컬레이션** → 병합.

다만 글은 분명히 경고한다 — *"이 동작은 이 저장소의 특정 구조·툴링에 크게 의존하며, 유사한 투자 없이 일반화할 수 있다고 가정해선 안 된다."*

## 10. 엔트로피와 가비지 컬렉션

완전한 자율성은 새 문제를 낳는다. Codex는 저장소의 기존 패턴(불균일하거나 최적이 아닌 것조차) 복제하므로 **드리프트가 필연적**이다. 처음엔 사람이 매주 금요일(주 20%)을 "AI 슬로프(slop)" 청소에 썼지만 확장되지 않았다.

대신 **"황금 원칙(golden principles)"**을 저장소에 직접 인코딩하고 정기 정리 프로세스를 구축했다(예: 직접 만든 헬퍼보다 공유 유틸리티 패키지 선호, 경계 검증·타입 SDK 없이 "YOLO 식"으로 데이터 추정 금지). **백그라운드 Codex 작업이 편차를 상시 스캔해 품질 등급을 갱신하고 대상 리팩터 PR을 연다 — 대부분 1분 내 검토되고 자동 병합**된다. 이는 **가비지 컬렉션**처럼 작동한다. 기술 부채는 고금리 대출과 같아, 한꺼번에 갚기보다 매일 조금씩 갚는 편이 낫다.

## 11. 여전히 배우는 것 (불변 vs 가변)

- **아직 모르는 것**: 완전한 에이전트 생성 시스템에서 아키텍처 일관성이 **수년에 걸쳐 어떻게 진화**하는지, **사람의 판단이 가장 큰 영향을 내는 지점**과 그 판단을 인코딩해 복리로 활용하는 법, 그리고 모델이 향상되며 시스템이 어떻게 발전할지.
- **분명해진 것 (핵심 결론)**: *"소프트웨어 구축에는 여전히 규율이 필요하지만, 규율은 코드보다 **비계**에서 더 많이 드러난다."* (비계(scaffolding) = 에이전트가 일하도록 둘러친 받침 구조 — 도구·추상화·문서·린터·피드백 루프 등. 건설 현장의 비계처럼, 결과물(코드)이 아니라 그것을 만들어내는 환경 쪽을 가리킨다.) 일관성을 유지하는 툴링·추상화·피드백 루프가 점점 중요해진다. 지금 가장 어려운 과제는 **에이전트가 복잡하고 안정적인 소프트웨어를 대규모로 만들 수 있는 환경·피드백 루프·제어 시스템을 설계하는 것**이다.

## 종합: 하네스 엔지니어링의 법칙

이 글에서 끌어낼 수 있는, 모델·도구가 바뀌어도 유지되는 원칙은 다음과 같다.

- **제약을 먼저 건다** — 계층형 아키텍처·황금 원칙·커스텀 린터처럼, 에이전트가 일하기 전에 경계를 박아두면 성능 저하나 드리프트 없이 속도를 낼 수 있다.
- **에이전트가 자기 결과를 보게 한다** — 가독성(legibility)·로컬 관측성·에이전트 간 리뷰로, 에이전트가 자기 변경의 효과를 직접 검증하게 한다.
- **에이전트가 막히면 그것을 신호로 본다** — 무엇이 누락됐는지(도구·가드레일·문서) 파악해 채운다. 막힘은 에이전트의 실패가 아니라 환경의 결함을 가리킨다.
- **사람은 가장 중요한 판단으로 물러난다** — 코드 작성에서 손을 떼고, 우선순위·수용 기준·진짜 설계 판단에 시간을 쓴다.

### 한 줄 요약
> 모델이 좋아져도 하네스 엔지니어링의 핵심은 그대로다 —
> **에이전트가 일할 환경에 제약을 박고, 결과를 스스로 보게 하며, 막힘을 신호 삼아 환경을 고치고, 사람은 가장 중요한 판단만 맡는 것.**
> 한마디로 *"규율은 코드보다 비계에서 드러난다."*
