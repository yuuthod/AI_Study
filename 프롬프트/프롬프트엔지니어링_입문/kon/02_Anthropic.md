## 1. Building effective agents (2024-12)

원문: https://www.anthropic.com/engineering/building-effective-agents

### 핵심 주장
- 성공한 구현은 **복잡한 프레임워크가 아니라 단순하고 조합 가능한(composable) 패턴**으로 만들어졌다.
- **워크플로우 vs 에이전트** 구분:
  - **워크플로우(Workflow)**: LLM·도구가 **미리 정해진 코드 경로**로 조율됨.
  - **에이전트(Agent)**: LLM이 **스스로 과정·도구 사용을 동적으로 통제**함.
- 핵심 권고: **"가장 단순한 프롬프트로 시작 → 평가로 최적화 → 단순한 해법이 부족할 때만 에이전트 도입."** 에이전트는 지연·비용을 성능과 맞바꾸므로 신중히.

### 구성 요소 / 패턴

> 아래 6가지는 "AI에게 일을 시키는 방식"을 단순한 것부터 복잡한 것 순으로 나열한 것이다.
> 맨 처음 **Augmented LLM**은 모든 패턴의 재료(토대)이고, 나머지 5개는 그 재료를 어떻게 엮느냐의 차이다.

**① Augmented LLM (강화된 LLM) — 모든 것의 토대**
그냥 대화만 하는 기본 AI에, **세 가지 능력**을 달아준 것이다.
- **검색(Retrieval)**: 모르는 건 외부 문서·DB에서 찾아본다.
- **도구(Tools)**: 계산기·코드 실행·웹 검색 같은 외부 기능을 직접 쓴다.
- **메모리(Memory)**: 앞에서 한 일을 기억해 다음에 활용한다.

**② Prompt chaining (프롬프트 사슬) — 한 줄로 이어 처리**
큰 작업을 **여러 단계로 쪼개, 앞 단계의 결과를 다음 단계 입력으로** 넘긴다.
- 예: "보고서 작성"을 → (1) 자료 요약 → (2) 목차 잡기 → (3) 본문 작성, 순서대로.
- 장점: 한 번에 다 시키는 것보다 각 단계가 단순해져 **오류가 줄고 검토하기 쉽다**.

**③ Routing (라우팅) — 분류해서 알맞은 곳으로 보내기**
들어온 요청이 **어떤 종류인지 먼저 판단**한 뒤, 그에 맞는 전문 처리로 보낸다.
- 장점: 모든 걸 하나의 만능 프롬프트로 처리하지 않으니 **각 분야에서 더 정확**해진다.

**④ Parallelization (병렬 처리) — 동시에 나눠서 처리**
하나의 AI가 순서대로 하는 대신, **여러 갈래를 동시에** 돌린다. 두 방식이 있다.
- **분할(Sectioning)**: 작업을 독립된 조각으로 나눠 **동시에** 처리 후 합친다. (예: 긴 문서를 3등분해 각각 요약 → 합치기)
- **투표(Voting)**: **같은 문제를 여러 번** 풀게 한 뒤 다수결/종합으로 답을 고른다. (예: 코드 보안 점검을 3번 돌려 한 번이라도 걸리면 위험으로 판단)

**⑤ Orchestrator-workers (지휘자-작업자) — 중앙이 그때그때 나눠 맡김**
중앙의 **지휘자(Orchestrator) AI가 작업을 동적으로 쪼개** 여러 **작업자(Worker) AI에게 위임**하고, 결과를 모은다.
- ④ 병렬 처리와 비슷해 보이지만 결정적 차이: ④는 **나누는 방식이 미리 정해져** 있고, ⑤는 **상황을 보고 지휘자가 즉석에서** 몇 개로·어떻게 나눌지 정한다.
- 예: "이 기능 추가해줘" → 지휘자가 "그럼 파일 A·B·C를 고쳐야겠군" 하고 판단해 각 파일 수정을 작업자에게 분배.

**⑥ Evaluator-optimizer (평가자-개선자) — 만들고-채점하고-고치는 루프**
한 AI가 **결과물을 만들고(생성)**, 다른 AI가 그것을 **평가·피드백**하면, 그 피드백을 받아 다시 고치는 과정을 **반복**한다.
- 예: 번역문을 만들면 → 평가자가 "이 문장이 어색하다" 지적 → 다시 번역 → 만족할 때까지 반복.
- 핵심: **만드는 역할과 채점하는 역할을 분리**한 것. (4번 문서의 Generator–Evaluator 분리, Böckeler의 "센서"와 같은 뿌리)

### 이 글이 명시하는 원칙
1. **단순성(Simplicity)** 유지
2. **투명성(Transparency)** — 계획 단계를 드러내기
3. **에이전트-컴퓨터 인터페이스(ACI)** — 도구 문서화·테스트에 HCI만큼 투자 (poka-yoke: 실수하기 어렵게 설계)
- 메타 원칙: *"가장 정교한 시스템이 아니라, 필요에 맞는 올바른 시스템을 만드는 것."* 복잡성은 결과가 개선될 때만 추가.

<details>
<summary><b>ACI(에이전트-컴퓨터 인터페이스)란?</b></summary>
<br>

<b>HCI를 알면 ACI가 보인다.</b>

<ul>
<li><b>HCI(Human-Computer Interface, 인간-컴퓨터 인터페이스)</b>: 사람이 컴퓨터를 쓰는 접점. 버튼·메뉴·화면처럼 <b>사람이 헷갈리지 않고 잘 쓰도록</b> 디자인하는 분야다.</li>
<li><b>ACI(Agent-Computer Interface, 에이전트-컴퓨터 인터페이스)</b>: 사람 대신 <b>AI 에이전트가 도구(Tool)를 쓰는 접점</b>. 즉 "AI가 도구를 헷갈리지 않고 잘 쓰도록" 도구의 설명서·입력형식·이름을 디자인하는 것이다.</li>
</ul>

<b>핵심 주장: "AI가 도구를 잘못 쓰면 AI 탓이 아니라 도구 설계 탓일 수 있다. 사람용 UX처럼 도구도 친절하게, 실수 못 하게 만들어라."</b><br>
우리는 사람이 쓸 앱은 버튼 위치 하나까지 고민하면서, 정작 AI에게 주는 도구는 대충 설명만 적어두는 경우가 많다. 그런데 AI도 <b>도구 설명이 모호하면 똑같이 실수한다.</b> 그래서 도구 설계에 <b>HCI만큼(혹은 그 이상) 투자</b>해야 한다.

<br>

<b>구체적으로 무엇을 하라는 건가:</b>

<ul>
<li><b>명확한 설명서</b>: 도구마다 사용 예시·예외 상황·입력 형식·경계(쓸 수 있는 것/없는 것)를 친절히 적는다.</li>
<li><b>AI에게 익숙한 형식 사용</b>: 인터넷 텍스트에서 자연스럽게 본 형식에 가깝게 만든다. (예: 수천 줄의 줄 번호를 일일이 세야 하는 것 같은 <b>불필요한 부담</b>을 없앤다.)</li>
<li><b>생각할 여유 주기</b>: 답을 쓰기 전 "막다른 길로 들어가지 않게" <b>생각할 토큰</b>을 충분히 준다.</li>
</ul>

<br>

<b>poka-yoke(포카요케) = "실수 방지 설계"</b><br>
일본 제조업 용어로, <b>애초에 실수할 수 없게 만드는</b> 장치를 뜻한다.

<ul>
<li>일상 예: USB-C는 <b>뒤집어 꽂아도 들어간다</b>, 콘센트 모양이 정해져 있어 <b>거꾸로 못 꽂는다</b>.</li>
<li>ACI 적용: 도구의 입력 인자(argument)를 <b>잘못 쓰기 어렵게</b> 바꾼다. (예: 상대 경로처럼 헷갈리는 입력을 받지 말고, <b>절대 경로만</b> 받도록 강제 → AI가 경로를 헷갈려 실수할 여지 자체를 없앰)</li>
</ul>

</details>

## 2. Effective context engineering for AI agents (2025-09)

원문: https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents

### 정의 — 프롬프트 엔지니어링 vs 컨텍스트 엔지니어링

- **프롬프트 엔지니어링**: 최적의 결과를 위해 **LLM 지시문을 작성·구성**하는 것. 프롬프팅을 하나의 개별 작업으로 본다.
- **컨텍스트 엔지니어링**: 추론(inference) 동안 **최적의 토큰 집합을 큐레이팅하고 유지하는 전략 전체**. 루프를 도는 에이전트는 계속 데이터를 생성하므로, 컨텍스트 창에 무엇을 넣을지 **주기적으로 정제**해야 한다.
- 차이는 시점·범위에 있음 — 프롬프트 E.는 일회성, 컨텍스트 E.는 순환적. → 프롬프트 E.는 컨텍스트 E.의 부분집합.

### 핵심 원칙

- **가장 적은 수의 고신호(high-signal) 토큰으로 원하는 결과를 극대화**한다. (high-signal = 작업에 실제로 도움 되는 정보 밀도가 높은 토큰)
- **시스템 프롬프트는 "적정 고도(right altitude)"를 찾아야 한다.** 두 실패 모드 사이에 알맞은 지점:
  - 한 극단 — 깨지기 쉬운 로직을 하드코딩.
  - 다른 극단 — 공유되지 않은 맥락을 가정한 채 막연한 지침만 제공.
  - 최적 — 행동을 효과적으로 이끌 만큼 구체적이되, 모델에 강한 판단 기준을 줄 만큼 유연한 상태.

### 주요 기법

- **Context Rot(컨텍스트 부식)**: 컨텍스트 창이 커질수록 모델의 정보 회상 정확도가 떨어지는 현상. 정도 차이는 있으나 모든 모델에서 나타난다.
- **Just-in-Time Retrieval(적시 검색)**: 관련 데이터를 미리 전부 적재하지 않고, **파일 경로·URL·쿼리 같은 가벼운 식별자**만 유지하다가 런타임에 도구로 동적 로드한다. (사람이 외부 인덱싱 시스템에 의존하는 방식과 유사하다고 설명함.)
- **Compaction(압축)**: 컨텍스트 한계에 가까워지면 대화 기록을 요약해 중요한 내용은 보존하고 중복 출력은 버린 뒤, 그 요약으로 재시작한다.
- **Structured Note-Taking / Agentic Memory(구조화된 노트 작성)**: 외부에 영속되는 노트를 주기적으로 작성하고 나중에 다시 가져온다. 모든 맥락을 창 안에 유지하지 않고도 복잡한 작업의 진행 상황을 추적한다.
- **Sub-Agent 아키텍처**: 특화된 서브에이전트가 깨끗한 컨텍스트 창에서 집중 작업을 처리하고, **요약된 결과만** 조율하는 메인 에이전트에 반환한다(관심사 분리).
- **장기(long-horizon) 작업**: 수 시간에 걸친 작업은 위 세 가지(압축·노트 작성·멀티에이전트)를 주된 수단으로 삼는다. 작업 특성에 따라 선택 — 압축은 대화 흐름 유지에, 노트 작성은 반복적 개발에, 멀티에이전트는 병렬 탐색이 필요한 복잡한 연구에 적합.

### 이 글이 명시하는 원칙

1. **컨텍스트는 유한한 자원** — 모델이 발전해도 컨텍스트는 "귀중하고 유한한 자원"으로 남으며, 신중한 큐레이션은 신뢰할 수 있는 에이전트 구축의 핵심으로 유지된다. 창이 커지는 것만으로 해결되지 않음(부식은 남음).
2. **점진적 자율성(progressive autonomy)** — 모델 능력이 향상될수록 사람의 큐레이션은 점차 줄고 똑똑한 모델이 더 알아서 행동하는 쪽으로 가지만, 그렇더라도 사려 깊은 컨텍스트 엔지니어링은 여전히 필요하다.

## 3. Effective harnesses for long-running agents (2025-11)

원문: https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents

### 정의 & 문제

긴 작업은 한 번의 세션으로 끝나지 않고 여러 세션으로 나뉘는데, **각 세션은 이전 세션의 기억이 전혀 없이 시작**한다. 컨텍스트 압축(compaction)이 도움은 되지만, 여러 창에 걸친 복잡한 작업에서 프로덕션 수준의 품질을 내기에는 그것만으로 부족하다.

Claude Opus 4.5로 풀스택 웹앱 개발을 시켰을 때 두 가지 실패 양상이 관찰됐다.
- 한 세션에 **너무 많은 범위를 욕심내** 기능을 절반만 구현하고 문서화도 하지 않은 채 끝낸다.
- 일부만 진행해 놓고 **작업이 다 끝났다고 성급히 선언**한다.

### 2-파트 해법

이 문제를 두 개의 에이전트로 나눠 푼다.
1. **Initializer Agent**: 맨 처음 한 번 실행되어 개발 환경의 기반을 닦는다.
2. **Coding Agent**: 이후 세션마다 **깨끗한 상태를 유지하면서** 기능을 조금씩 점진적으로 진행한다.

### 환경 관리 / 신뢰성 기법

세션이 끊겨도 일관성을 잃지 않도록, 진행 상태를 컨텍스트 창 바깥에 명시적으로 남겨 둔다.
- **기능 목록(Feature list)**: 200개 이상의 테스트 가능한 기능을 JSON으로 관리하며 각 항목을 통과/실패로 표시한다. JSON 형식을 쓴 이유는 모델이 목록을 함부로 손대지 못하게 하기 위함이다. (*"테스트를 지우거나 고치는 것은 허용되지 않는다"* — 그래야 누락·버그를 막을 수 있기 때문.)
- **Git 버전 관리 + 진행 기록 파일**: 설명이 충실한 커밋 메시지와 진행 기록 덕분에, 새로 시작하는 세션이 **이전 작업 상태를 추측 없이 명확히 파악**할 수 있다.
- **초기화 스크립트**: 어느 세션에서나 개발 서버를 동일한 방식으로 띄울 수 있게 한다.
- **세션 시작 프로토콜**(매 세션이 따르는 표준 순서): 작업 디렉터리 확인 → git 기록·진행 문서 읽기 → 기능 목록에서 우선순위가 가장 높은 미완 항목 확인 → 초기화 스크립트 실행 후 기본 동작을 검증한 다음에야 새 작업 착수.
- **검증(Verification)**: 단위 테스트만으로는 부족하므로, Puppeteer MCP 같은 **브라우저 자동화로 실제 사용자 행동을 흉내 낸 E2E 검증**을 한다. 또한 새 기능을 만들기 전에 **기존 기능부터 먼저 검증**해, 이전 세션에서 생긴 버그를 즉시 잡아낸다.

### 이 글이 명시하는 원칙

이 글은 **세션마다 달라지는 부분**(Initializer용 프롬프트와 Coding용 프롬프트는 서로 다름)과 **모든 세션에서 변하지 않는 인프라**(동일한 시스템 프롬프트·도구 세트·하네스)를 구분한다. 이는 **작업을 잘게 나누는 분해(decomposition)와 상태를 관리하는 패턴이, 모델이 좋아지더라도 변치 않는 토대**임을 시사한다.

다만 **단일 범용 에이전트가 나은지, 특화된 멀티에이전트가 나은지**는 아직 열린 질문으로 남아 있다.

## 4. Harness design for long-running application development (2026-03)

원문: https://www.anthropic.com/engineering/harness-design-long-running-apps

### 핵심 주장

에이전트는 스스로를 평가하게 두면 자기 작업에 지나치게 후한 점수를 주고, 작업이 길어질수록 컨텍스트가 차오르며 일관성이 무너진다. 이 글은 **만드는 역할(Generator)과 채점하는 역할(Evaluator)을 분리**하면 결과물 품질이 크게 좋아진다는 것을 보여준다. 이 발상은 생성기와 판별기를 맞붙이는 GAN에서 착안한 것이다.

### 주요 패턴

- **3-에이전트 아키텍처**: 작업을 세 역할로 나눈다. **Planner**는 단순한 프롬프트를 야심 찬 상세 스펙으로 펼치고, **Generator**는 그 스펙을 반복적으로 구현하며, **Evaluator**는 Playwright로 기능이 스펙대로 동작하는지 검증한다. 세 에이전트는 파일을 주고받으며 소통하므로, 세부를 과하게 명시하지 않고도 스펙에서 구현으로 이어진다.
- **Sprint Contracts(스프린트 계약)**: 무언가를 만들기 시작하기 전에 Generator와 Evaluator가 **"무엇이 완료인지"를 테스트 가능한 기준으로 먼저 합의**한다. 덕분에 기술 세부를 일일이 못 박지 않고도 둘의 방향이 어긋나지 않는다.
- **채점 기준의 언어화**: 모호한 미감을 design·originality·craft·functionality 네 축으로 나눠 측정 가능한 기준으로 바꾼다. 이때 **기준에 쓰는 표현 자체가 출력의 성격을 바꾼다.** few-shot 예시로 채점 기준을 보정하면, 반복하는 사이 점수가 들쭉날쭉해지는 것을 막을 수 있다.
- **컨텍스트 관리**: 컨텍스트가 한계에 다다를 때, 요약으로 이어가는 압축보다 **컨텍스트를 비우고 구조화된 인수인계로 새로 시작하는 방식**이 더 깔끔했다. 다만 이 효과는 모델에 따라 다르다 — 컨텍스트가 차오를 때 작업을 서둘러 마무리하려는 "context anxiety" 경향이 4.5에서는 강했지만 4.6에서는 거의 사라졌다.

### 불변 vs 가변

이 글의 가치는 **무엇이 변하지 않고 무엇이 변하는지를 직접 구분**해준다는 데 있다.
- **변하지 않는 것**:
	- 평가를 분리하면 품질이 오른다.
	- 복잡한 작업은 잘게 나눈다.
	- 구조화된 산출물로 컨텍스트를 인수인계한다.
	- 주관적 판단을 구체적 채점 기준으로 바꾼다.
- **변하는 것**: 모델이 좋아질수록 **떠받쳐주는 비계(scaffolding)는 줄어든다.** 실제로 4.6은 4.5보다 적은 구조만으로 충분했고, 스프린트 단위로 잘게 쪼개던 것도 선택 사항이 됐다. 또한 평가자(Evaluator)의 효용은 작업 난이도가 **모델 능력의 경계에 걸쳐 있을 때** 가장 크고, 모델이 쉽게 해내는 작업에서는 오히려 군더더기가 된다.
- **결론**: *"흥미로운 하네스 조합은 줄지 않고 이동한다(don't shrink, they move)."* 더 좋은 모델은 하네스를 없애는 게 아니라, **더 야심 찬 목표**를 가능하게 만들어 그에 맞는 새로운 특화 에이전트를 다시 불러들인다.

## 종합: 4편을 관통하는 시간 흐름

### 변하지 않는 것 (불변 원칙)

4편을 시간순으로 겹쳐 읽으면, 표현과 이름은 바뀌어도 **밑바탕 원리는 계속 이어진다**는 점이 보인다.

- **단순성을 먼저 둔다.** 1편이 "필요할 때만 복잡성을 더하라"고 한 원칙은 이후 글에서도 흔들리지 않고 유지된다.
- **만드는 일과 평가하는 일을 분리한다.** 1편의 evaluator-optimizer, 2편 계열의 하네스 센서, 4편의 Generator·Evaluator 분리는 **이름만 다를 뿐 같은 원리**다.
- **큰 작업을 잘게 나눈다.** 1편의 prompt chaining에서 3편의 기능 목록·점진적 진행을 거쳐 4편의 sprint contracts까지, 분해(decomposition)라는 뼈대는 그대로다.
- **컨텍스트는 유한하다.** 2편이 짚었듯 창이 아무리 커져도 부식(context rot)은 남기 때문에, 무엇을 넣을지 골라 담는 큐레이션은 늘 필요하다.
- **진행 상태를 명시적으로 인수인계한다.** 2·3편의 노트 작성·진행 파일·git이 4편의 구조화된 핸드오프로 이어진다.
- **도구·인터페이스 설계(ACI)와 검증(verification)** 은 어느 글에서나 중요하게 다뤄진다.

### 변하는 것 (가변 요소)

반대로, 모델이 세대를 거듭하며 **달라지는 것들도 분명하다.**

- **비계(scaffolding)의 양이 줄어든다.** 모델이 좋아질수록 떠받쳐줄 구조가 덜 필요해, 4.5에서 4.6으로 넘어오며 스프린트 분해가 선택 사항이 됐다. "context anxiety"처럼 특정 세대에만 강하게 나타나는 **모델 의존적 현상**도 세대마다 바뀐다.
- **사람이 개입할 자리가 옮겨간다.** 점진적 자율성에 따라 사람이 일일이 큐레이션할 필요는 줄지만, "어디에 개입해야 하는가"라는 판단 자체는 사라지지 않는다.
- **하네스의 무게중심이 이동한다.** 이미 해결된 문제(예: 유지보수성)에서 아직 어려운 문제(예: 기능 정확성)로, 나아가 더 야심 찬 목표 쪽으로 초점이 옮겨간다.

### 한 줄 요약
> 모델이 좋아져도 **하네스의 원리(분리·분해·유한한 컨텍스트·검증)는 그대로**이고,
> 바뀌는 것은 **그 원리를 구현하는 비계의 양과 위치**다. — *"하네스는 줄지 않고 이동한다."*


<details>
<summary><b>"비계(scaffolding)의 양과 위치"란?</b></summary>
<br>

<b>비계(scaffolding)란?</b><br>
비계는 건물 지을 때 인부가 딛고 작업하라고 둘러치는 임시 가설물이다. 건물이 완성되면 걷어낸다. 하네스 맥락에서 비계 = <b>모델 혼자서는 잘 못 하는 부분을 떠받쳐주려고 둘러친 보조 장치</b>를 말한다. (<i>"every component encodes an assumption about what the model can't do alone"</i> — 모든 구성요소는 모델이 혼자 못 하는 것에 대한 가정을 담고 있다.)<br>
예: 작업을 잘게 쪼개주는 스프린트 분해, Planner·Evaluator 같은 별도 에이전트, 세션 시작 체크리스트 등이 다 비계다.

<br><br>

<b>변하는 것은 비계의 "양"과 "위치"다.</b>

<ul>
<li><b>① 양(amount) = 비계를 얼마나 많이 둘러치는가</b><br>
같은 작업이라도 모델이 좋아지면 보조 장치를 더 적게 써도 된다. (4.6은 4.5보다 적은 구조로 충분했고, 스프린트 분해가 선택 사항이 됨.)</li>
<li><b>② 위치(location) = 비계를 어느 지점에 두는가</b><br>
모델이 발전하면 쉬워진 곳의 비계는 떼고, 아직 어려운 새 경계로 비계를 옮겨 세운다. (평가자는 작업이 모델 능력의 "경계"에 걸쳐 있을 때 가장 유용함.)</li>
</ul>

즉, <b>원리(분리·분해·검증)는 그대로</b>인데, 그걸 구현하는 <b>비계만 양이 줄고 자리를 옮긴다</b>는 뜻 → <i>"하네스는 줄지 않고 이동한다."</i>
