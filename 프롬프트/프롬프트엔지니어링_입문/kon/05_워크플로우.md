# 05_워크플로우 — 하네스 엔지니어링 기반 워크플로우

> [04_종합비교](04_종합비교.md)에서 도출한 **다섯 불변 원칙**을 실제 워크플로우로 옮긴 문서.
> 먼저 규모와 무관한 **일반형 뼈대**를 세우고, 이를 **소규모 실서비스**에 맞춰 경량화한 뒤, **실제 스킬 매핑**까지 잇는다.

---

## 1. 기본 뼈대 (일반형)

핵심 루프는 **가이드(행동 전) → 실행 → 센서(행동 후) → 사람 게이트**이고, 그 바깥을 **컨텍스트 적재 / 핸드오프**가 감싼다.

```
┌─ [0] 컨텍스트 적재 ──────────────────────────────┐
│   저장소의 맵·규칙·진행상황을 먼저 읽는다           │  ← 원칙④ 지식 외부화
│   (AGENTS.md/CLAUDE.md = 목차, 필요시 링크 따라감)   │     원칙③ 컨텍스트는 유한
│                                                  │
│   ┌─ [1] 계획·분해 (가이드/피드포워드) ──────────┐ │  ← 원칙② 작업 분해
│   │   큰 목표 → 작은 단위로 쪼갬                  │ │     원칙① 가이드
│   │   "무엇이 완료인가" 수용 기준 먼저 합의        │ │
│   └────────────────┬───────────────────────────┘ │
│                    ▼                              │
│   ┌─ [2] 실행 ─────────────────────────────────┐  │
│   │   한 단위씩 구현 (깊이 우선)                  │ │
│   └────────────────┬───────────────────────────┘ │
│                    ▼                              │
│   ┌─ [3] 검증 (센서/피드백) ───────────────────┐  │  ← 원칙① 센서
│   │   계산적: 린터·타입·테스트 (매번, 싸고 빠름)   │ │     "품질을 왼쪽으로"
│   │   추론적: 코드리뷰·E2E·평가 (게이트, 비쌈)     │ │     센서는 LLM이 읽기 좋게
│   │   ※ 오류 메시지에 "이렇게 고쳐라" 지침 포함    │ │     (수정 지침 주입)
│   └────────────────┬───────────────────────────┘ │
│            통과? ──아니오──▶ [2]로 자가 교정 루프    │  ← Ralph Wiggum 루프
│                    │ 예                            │
│                    ▼                              │
│   ┌─ [4] 사람 게이트 ──────────────────────────┐  │  ← 원칙⑤ 사람은 핵심 판단
│   │   판단 필요한 지점만 에스컬레이션             │ │
│   │   (트레이드오프·새 설계·사업 결정)            │ │
│   └────────────────┬───────────────────────────┘ │
│                    ▼                              │
└─ [5] 핸드오프·기록 ──────────────────────────────┘  ← 원칙④ 지식 외부화
    진행상황·결정을 파일+git으로 남김 (다음 세션이 이어받게)

  ┌─ [주기] 비계 점검 ──────────────────────────────┐
  │  모델 버전 올릴 때: 줄일 비계(양) / 옮길 비계(위치)  │  ← 04 결론
  └──────────────────────────────────────────────┘
```

| 단계 | 하는 일 | 근거 원칙 |
|---|---|---|
| **0 적재** | 맵·규칙·진행 읽기 | ③④ |
| **1 분해** | 작게 쪼개고 완료 기준 합의 | ①(가이드) ② |
| **2 실행** | 한 단위씩 구현 | ② |
| **3 검증** | 계산적(매번)+추론적(게이트) 센서, 수정 지침 포함 | ①(센서) |
| **4 게이트** | 막히거나 판단 필요할 때만 사람 | ⑤ |
| **5 핸드오프** | 결과·결정 외부화 | ④ |
| **주기 점검** | 비계 양·위치 재조정 | 04 결론 |

## 2. 설계 전제 (소규모 실서비스 적용)

- **적용 대상**: 실제로 운영할 소규모 서비스 (코드 저장소).
- **핵심 태도**: 03 OpenAI도 *"우리처럼 무겁게 투자하지 말라"*고 경고했다. 100만 줄용 인프라(관측성 스택·doc-gardening 에이전트·기능 200개 JSON·병렬 리뷰 에이전트)는 **걷어내고**, 원칙만 가볍게 적용한다.
- **성장 방식**: 처음부터 완벽한 하네스를 깔지 않는다. **"최소 세트로 시작 → 실수가 나올 때마다 규칙·센서를 하나씩 추가"**(래칫 원칙). 04의 *"비계는 양·위치가 변한다"*를, 작게 시작해 점진적으로 조여가는 것으로 실천한다.

## 3. 지금 당장 까는 최소 세트

| 불변 원칙           | 소규모에선 이거면 충분                                | 아직 안 해도 되는 것          |
| --------------- | ------------------------------------------- | --------------------- |
| **가이드 (피드포워드)** | `CLAUDE.md` 한 장 — 프로젝트 맵 + 핵심 규칙 + 완료 기준 양식 | 계층 아키텍처 강제, 커스텀 린터    |
| **센서 — 계산적**    | 린터 + 타입체크 + 테스트 + 가벼운 CI (push마다 자동)        | 관측성 스택, 변이 테스트        |
| **센서 — 추론적**    | PR마다 코드리뷰 1회 (에이전트 또는 본인)                   | 평가 에이전트 패널, E2E 자동화   |
| **작업 분해**       | 작은 PR 단위 + "완료 기준 먼저 적기"                    | 스프린트 계약 문서화           |
| **지식 외부화**      | git + `TODO.md`(진행 상황) 한 장                  | `exec-plans/` 디렉터리 체계 |
| **사람 게이트**      | **처음엔 모든 머지를 직접 확인**                        | 자동 병합                 |

> 계산적 센서(린터·테스트)는 어디서나 싸게 깔 수 있고, 추론적 센서(E2E·평가 에이전트)는 투자가 크다.
> **계산적 센서부터 깔고, 추론적 센서는 나중에** 올리는 게 현실적이다(원칙: "품질을 왼쪽으로").

### 각 항목 — 당장 셋업하는 법

> 예시는 가장 흔한 Node/TypeScript 기준. 다른 스택은 **도구만 바꾸면** 된다(Python: ruff·mypy·pytest / Go: golangci-lint·go test).

**① 가이드 = `CLAUDE.md` 한 장** (저장소 루트)

에이전트가 매번 먼저 읽는 "지도". 작성 원칙은 스터디에서 그대로 나온다.

- **지도지 매뉴얼이 아니다**(OpenAI) → 세부는 본문에 욱여넣지 말고 **링크로** 뺀다. A4 한 장(≈100줄) 넘으면 매뉴얼이 되는 신호.
- **적정 고도**(Anthropic) → "이 경우엔 A, 저 경우엔 B…" 하드코딩❌, "알아서 잘"❌. **방향은 분명히, 세부는 모델 판단에** 맡긴다.
- **처음엔 비어도 된다** → 규칙 칸은 4~5줄로 시작해 **래칫으로 채운다**(같은 실수 2번이면 한 줄 추가).

채워 쓰는 템플릿:
```markdown
# [서비스명] — 한 줄 소개          # (예) 동네 헬스장 회원·출석 관리 API

## 실행·검증 명령                 # 에이전트가 가장 자주 쓰는 부분 → 맨 위에
- 개발 서버: `npm run dev`
- 테스트:    `npm test`
- 린트·타입: `npm run lint` / `npx tsc --noEmit`

## 스택
TypeScript · Next.js · PostgreSQL(Prisma) · Vitest

## 디렉터리 맵                    # "어디에 뭐가 있나" 지도
- `src/app/`    라우트·페이지
- `src/server/` 비즈니스 로직 (외부 호출은 여기서만)
- `src/db/`     스키마·쿼리
- 자세한 설계 → docs/DESIGN.md   # 세부는 링크로 뺀다

## 핵심 규칙                      # load-bearing(진짜 중요한) 것만, 5~10줄
- 에러는 삼키지 말 것. 잡으면 로그 남기고 다시 던지거나 명시적으로 처리.
- DB 접근은 `src/db/` 함수를 통해서만. 라우트에서 직접 쿼리 금지.
- 비밀키·토큰 하드코딩 금지. `.env` 사용.

## 완료 기준 (Definition of Done) # 작업이 "끝났다"고 보는 기준
1. 관련 테스트 + 린트·타입 통과
2. 영향받는 기능 수동 확인 1가지
3. 변경 이유를 커밋 메시지에 1줄

## 하지 말 것
- `main`에 직접 push (브랜치+PR로)
- 테스트를 지우거나 비활성화해서 통과시키기
```

> **적정 고도 감잡기**: "함수는 무조건 20줄 이하"(너무 낮음) ↔ "함수는 한 가지 일만, 길어지면 쪼갠다"(적정) ↔ "코드 깔끔하게"(너무 높음).

**② 센서(계산적) = 린터·타입·테스트·CI** — 네 개를 push마다 자동 실행
- 린터·포매터: `eslint` + `prettier` 설치 → `npm run lint` 스크립트.
- 타입: `tsconfig.json`에 `"strict": true`.
- 테스트: `vitest`/`jest`로 **핵심 경로 1개라도** 먼저 작성(0개→1개가 가장 중요).
- CI: `.github/workflows/ci.yml` 한 장 — push마다 lint→type→test.
```yaml
on: [push, pull_request]
jobs:
  check:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
      - run: npm ci
      - run: npm run lint && npx tsc --noEmit && npm test
```

**③ 센서(추론적) = PR마다 리뷰 1회**
- PR 템플릿(`.github/pull_request_template.md`)에 **"무엇을·왜·어떻게 검증했나"** 3줄 강제.
- 머지 전 `/code-review`(또는 본인 눈)로 1회 점검. 처음엔 이걸로 충분.

**④ 작업 분해 = 작은 PR + 완료 기준 먼저**
- 브랜치 1개 = **작업 1단위**(반나절~하루 분량). 거대 PR 금지.
- 착수 전 PR/이슈 본문에 **"완료 기준"**을 한 줄 적고 시작(가이드 ①의 양식 사용).

**⑤ 지식 외부화 = git + `TODO.md`**
- 루트에 `TODO.md`: `## 진행 중` / `## 다음 할 일` / `## 결정 로그(왜 이렇게 했나)` 세 칸.
- 커밋 메시지에 **"무엇을·왜"**를 남겨, 다음 세션이 git log만으로 맥락을 잡게 한다.

**⑥ 사람 게이트 = 머지 직접 확인**
- GitHub `main` 브랜치 보호 설정: **CI 통과 필수 + 본인 승인 후 머지**.
- 처음엔 모든 머지를 직접 본다. 신뢰가 쌓인 영역부터 7절대로 완화.

> 셋업 순서 추천: **① CLAUDE.md → ② 린트·CI → ⑤ TODO.md → ⑥ 브랜치 보호 → ③④는 첫 PR 때 자연스럽게.** 반나절이면 골격이 선다.

## 4. 핵심 루프 (작업 한 건당 — 소규모 축약형)

```
[0] 컨텍스트 적재
    CLAUDE.md(맵·규칙) · TODO.md(진행 상황) 읽기
        ↓
[1] 계획·분해 (가이드)
    큰 작업을 작은 단위로 쪼개고, "무엇이 완료인가" 기준을 먼저 적는다
        ↓
[2] 실행
    한 단위씩 구현 (깊이 우선 — 한 조각을 끝까지)
        ↓
[3] 검증 (센서)
    계산적: 린터·타입·테스트 통과 (실패 시 자가 교정 → [2]로)
    추론적: 코드리뷰 1회
    ※ 피드백은 "틀렸다"가 아니라 "이렇게 고쳐라"까지 담는다
        ↓
[4] 사람 게이트
    머지 전 직접 확인 (판단 필요한 지점만 — 처음엔 전부)
        ↓
[5] 핸드오프·기록
    진행 상황·결정을 TODO.md·커밋 메시지에 남긴다 (다음 세션이 이어받게)
```

## 5. 래칫(점진 강화) 규칙 — 소규모의 핵심

> **래칫(ratchet)** = 한 방향으로만 돌아가는 톱니바퀴(자전거 페달·케이블 타이처럼 조여지기만 하고 풀리지 않음). 여기선 *"한 번 막은 실수는 규칙으로 박아 영영 되돌아가지 않게 한다 → 하네스가 앞으로만 단단해진다"*는 뜻(Addy Osmani의 래칫 원칙).

작게 시작하므로, **하네스를 키우는 규칙**이 가장 중요하다.

1. **같은 실수가 2번 나오면 규칙으로 승격한다.** → `CLAUDE.md`에 한 줄 추가하거나, 가능하면 린트·테스트로 기계화한다.
2. **센서는 항상 LLM이 읽기 좋게.** 린터·테스트가 실패를 알릴 때 원인과 **수정 방향**까지 메시지에 담는다(세 글 공통 강조).
3. **막히면 환경을 의심한다.** 에이전트가 헤매면 "무능한 탓"이 아니라 *"맵·규칙·도구 중 뭐가 빠졌나"*를 먼저 본다.
4. **비계는 한 번 만들고 끝이 아니다.** 서비스가 커지거나 모델을 새 버전으로 올릴 때:
   - *이제 없어도 되는 비계(양)*: 모델이 쉽게 해내게 된 영역의 보조 장치는 뺀다.
   - *옮겨야 할 비계(위치)*: 더 어려워진 새 지점에 센서·규칙을 새로 세운다.

## 6. 실전: 스킬 매핑

실제로는 각 단계에 **이전에 공부한 스킬들**을 끼워 쓴다. 한 가지 유의점 — `/office-hours`·`/brainstorming`·`/grill-me`는 모두 **"가이드(행동 전 생각 정리)" 쪽** 스킬이다. 이중 통제 원칙상 **뒷단(센서)이 비지 않도록** `/tdd`(계산적)·`/review`(추론적)·`/diagnose` 같은 피드백 스킬을 반드시 함께 둔다.

| 하네스 단계                | 원칙          | 쓸 스킬 / 실천                                     | 비고                    |
| --------------------- | ----------- | --------------------------------------------- | --------------------- |
| **A. 착수 검증**          | 가이드         | **`/office-hours`**                           | "이걸 만들 가치가 있나" 타당성 압박 |
| **B. 설계·접근 탐색**       | 가이드         | **`/brainstorming`**                          | 설계안 펼치고 고르기           |
| **B′. 초기 하네스 셋업**(1회) | 가이드+센서 토대   | `CLAUDE.md` + 린터·CI + `docs/` PRD             | 3절 최소 세트 (단 진행 관리는 PRD) |
| **C. 변경 계획 압박**(수정 시) | 가이드         | **`/grill-me`** (파트별), 필요시 `/grill-with-docs` | "왜 바꾸나·영향 범위" 회귀 방지   |
| **D. 구현 + 검증(계산적)**  | **센서(계산적)** | **`/tdd`** (Red→Green→Refactor) + 린터·타입       | 뒷단의 핵심. 테스트가 곧 센서     |
| **D′. 검증(추론적)**       | **센서(추론적)** | **`/review`** (P0/P1/P2 우선순위)                 | Böckeler "추론적 센서=코드리뷰". 리뷰 없이 커밋 금지 |
| **E. 디버깅 교정 루프**      | 센서 교정       | **`/diagnose`**                               | 검증 실패 시 규율 있는 디버깅     |
| **F. 사람 게이트**         | 사람은 핵심 판단   | 본인 머지 확인                                      | 처음엔 전부, 신뢰 쌓이면 완화     |
| **G. 기록·핸드오프**        | 지식 외부화      | **`/to-prd`** 로 `docs/` PRD 갱신(체크박스) + git 커밋 | 03의 "기록 시스템"에 해당. **TODO.md 대신 PRD** 사용 |
| **상시. 래칫**            | 비계 양·위치     | 실수 2번 → 규칙 승격                                 | 위 5절                  |

### 다듬은 전체 흐름

```
[프로젝트 1회]
 A. /office-hours        ── 만들 가치 검증 (가이드 최상위)
 B. /brainstorming       ── 설계·접근 결정
 B′. 하네스 셋업          ── CLAUDE.md + 린터·CI + docs/ PRD

[기능/작업마다 반복하는 루프]
 0. CLAUDE.md·docs/ PRD 읽기                   (적재)
 1. 작게 쪼개고 "완료 기준" 적기                 (분해·가이드)
      └ 기존 코드 수정이면 ▶ C. /grill-me 로 변경 계획 압박
 2. /tdd 로 구현 (실행)                            (센서·계산적)
 3. /review(P0/P1/P2)로 검증 → P0/P1 즉시 수정      (센서·추론적)
      └ 린터·타입·CI 통과까지 자가 교정 / 버그는 ▶ E. /diagnose
      └ "리뷰 없이 커밋 금지"
 4. 사람이 머지 확인 (리뷰 통과만으론 머지 불가)      (게이트)
 5. /to-prd 로 docs/ PRD 갱신(- [x]) + 커밋          (핸드오프)

[상시]
 래칫: 같은 실수 2번 → CLAUDE.md 규칙 or 린트로 승격
 비계 점검: 모델 업글·서비스 성장 시 양↓·위치 이동
```

### 보완 제안

- **`/tdd`·`/diagnose`가 내는 실패 메시지·에러를 그대로 에이전트에 물려** "이렇게 고쳐라"까지 가게 하면, 센서 원칙("LLM이 읽기 좋게")이 살아 자가 교정이 빨라진다.
- **`/grill-me`는 수정 때뿐 아니라 신규 기능 B(설계) 직후에도 한 번** 돌리면(계획 압박) 첫 구현 품질이 올라간다 — grill 계열의 원래 용도(코딩 전 계획 검증)와 정확히 맞는다.

> ※ 이 매핑은 두 가정에 기댄다 — ① `/office-hours` = 타당성 검증, ② `/brainstorming` = 설계 탐색. 실제 용도가 다르면 조정 필요.

### 보류 (스터디 근거가 약하거나 단서가 필요해 아직 매핑하지 않음)

아래 스킬도 실무에서 쓰지만, 스터디(01~04) 원칙과의 부합도가 확실하지 않아 **보류**한다. 근거가 정리되면 편입한다.

| 스킬 | 두려고 했던 자리 | 보류 사유 |
|------|---------------|----------|
| **`/zoom-out`** | [0] 컨텍스트 적재 | 부합은 하나 **결이 다름**. 스터디의 [0] 적재 본령은 *"미리 써둔 맵(CLAUDE.md) 읽기"*인데, `/zoom-out`은 *"에이전트가 코드를 훑어 맵을 만드는"* 쪽 → Anthropic의 **적시 검색(JIT Retrieval)**에 가깝다. 매핑 위치를 그렇게 재정의해야 정확. |
| **`/improve-codebase-architecture`** | 상시 — 엔트로피 관리 | Böckeler의 **유지보수성 하네스**엔 맞지만, OpenAI의 *자동·상시 가비지 컬렉션*과 **동일시하면 과장**(이건 사람이 부르는 수동 리팩터). 또 "딥 모듈"은 스터디에 직접 없는 개념. "수동 유지보수 하네스"로 한정하면 편입 가능. |
| **`/ship`** | 배포 단계 | **스터디 근거가 가장 약함.** 세 글 모두 *배포(ship)를 하네스 원칙으로 다루지 않는다*(Böckeler "Keep Quality Left"는 검사 분산이지 배포 단계가 아님). 실서비스에 필요한 **실무 단계일 뿐 스터디에서 도출된 것이 아니다.** 넣으려면 "스터디 밖 실무"로 표시하거나 F 게이트에 흡수. |

## 7. 나중에 올릴 것 (서비스가 커지면)

지금은 과투자지만, 규모·신뢰가 쌓이면 단계적으로 도입한다.

- **추론적 센서 강화**: E2E 자동화, 평가 에이전트로 PR 자동 점검.
- **아키텍처 강제**: 계층 규칙을 커스텀 린트·구조적 테스트로 기계화(03의 `Types→…→UI`처럼).
- **지식 베이스 구조화**: `TODO.md` → `docs/`(설계·계획·레퍼런스)로 분화, 짧은 진입점 + 점진적 공개.
- **사람 게이트 완화**: 신뢰가 쌓인 영역부터 에이전트 간 리뷰로 넘기고, 사람은 판단 지점만.

## 한 줄 요약

> 일반형 뼈대는 **가이드 → 실행 → 센서 → 사람 게이트**(+적재·핸드오프) 루프다.
> 소규모에선 **`CLAUDE.md`(가이드) + 린터·테스트·CI(센서) + 작은 PR + git·TODO(핸드오프) + 사람 머지 확인**이면 골격이 선다.
> 실전에선 앞단을 **`/office-hours`·`/brainstorming`·`/grill-me`**(가이드)로, 뒷단을 **`/tdd`·`/diagnose`**(센서)와 **`/to-prd`**(핸드오프)로 채워 이중 통제를 완성하고, 나머지는 **래칫으로 키운다**.
