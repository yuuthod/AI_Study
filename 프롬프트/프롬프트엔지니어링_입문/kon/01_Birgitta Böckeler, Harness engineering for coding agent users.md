# 01_Birgitta Böckeler — Harness engineering for coding agent users

> **대상 문서**: 「Harness engineering for coding agent users」
> **저자/소속**: Birgitta Böckeler (Thoughtworks)
> **원문**: https://martinfowler.com/articles/harness-engineering.html

---

## 1. 정의

- **하네스(Harness)**: AI 에이전트에서 모델을 제외한 모든 것. `Agent = Model + Harness`.
  코딩 에이전트 맥락에서는 "팀이 자기 시스템·용례에 맞게 에이전트 행동을 통제하려고 만든 장치들"을 가리킨다.
- **하네스 엔지니어링**: 에이전트가 만든 코드에 대한 **신뢰(confidence)를 높이고**, 사람의 **감독 부담을 줄이며**, 시스템 품질을 높이기 위해 **피드포워드(feedforward)·피드백(feedback) 통제 장치를 일관된 시스템으로 설계하고 계속 다듬는 실천**.

## 2. 핵심 프레임워크 — 가이드(Guides)와 센서(Sensors)

| 통제 유형 | 시점 | 역할 | 예시 |
|----------|------|------|------|
| **가이드 (Feedforward)** | 행동 **이전** | 좋은 결과가 한 번에 나올 확률을 높임 | 코딩 컨벤션 문서, 부트스트랩 스크립트, 코드모드, 아키텍처 규칙 |
| **센서 (Feedback)** | 행동 **이후** | 결과를 관찰해 스스로 교정하게 함 | 린터, 테스트, 코드리뷰 에이전트, 구조 분석 |

- **핵심 통찰**: 피드백만 있으면 같은 실수를 반복하고, 피드포워드만 있으면 규칙이 검증되지 않는다 → **둘 다 필요**.
- 센서는 **LLM이 읽기 좋게** 만들 때 특히 강력하다(예: 수정 지시까지 담은 커스텀 린터 메시지).

**실행 방식 두 가지**
- **계산적(Computational)**: 결정론적·빠름·저렴 (테스트·린터·타입체커·구조분석) → 모든 변경마다 돌릴 수 있음.
- **추론적(Inferential)**: 의미 판단·느림·비쌈·비결정적 (코드리뷰, LLM-as-judge) → 통합 이후 높은 가치의 게이트에만 아껴서 사용.

## 3. 주요 섹션별 논지

- **The Steering Loop**: 사람은 **하네스 자체를 반복 개선**한다. 문제가 재발하면 가이드·센서를 고쳐 재발을 막는다. 에이전트도 하네스 구축을 도울 수 있다.
- **Keep Quality Left (품질을 왼쪽으로)**: 비용·속도에 따라 검사를 개발 수명주기 전반에 분산. 커밋 전엔 빠른 린터, 통합 후엔 변이 테스트·광범위 리뷰, 상시로는 드리프트 탐지·런타임 모니터링.
- **하네스가 규제하는 3가지 범주**:
  1. **유지보수성(Maintainability)** — 가장 쉬움(성숙한 도구 존재). 중복·복잡도·커버리지·드리프트를 계산적 센서가 잘 잡음.
  2. **아키텍처 적합성(Architecture Fitness)** — Fitness Function으로 성능·관측가능성 같은 특성을 피드포워드/피드백.
  3. **행동/기능 정확성(Behaviour)** — **가장 어려움.** 현재는 명세를 피드포워드, AI 생성 테스트를 피드백으로 쓰지만 "AI가 만든 테스트에 너무 많은 신뢰를 거는 셈이라 아직 충분하지 않다."
- **Harnessability(하네스 적용 가능성)**: 코드베이스마다 다르다. 타입 강한 언어·명확한 모듈 경계는 유리. 역설 — **"하네스가 가장 필요한 곳(레거시)이 가장 만들기 어렵다."**
- **Ashby의 법칙**: "규제자는 규제 대상만큼의 다양성을 가져야 한다." → 토폴로지(서비스 아키타입)를 정해 에이전트가 만들 수 있는 다양성을 줄이면, 포괄적 하네스가 실현 가능해진다.
- **사람의 역할**: 사람은 흡수된 컨벤션·심미적 판단·조직 정렬·사회적 책임·직관 같은 **암묵적 하네스**를 가진다. 하네스는 이를 외부화하려는 시도이나 불완전. **"좋은 하네스는 사람의 입력을 완전히 없애는 게 아니라, 가장 중요한 곳으로 향하게 하는 것."**

<br>

<b>개발 과정을 왼쪽 → 오른쪽 시간 흐름으로 본다.</b>

<pre>
기획 → 코딩 → 커밋 → 통합 → 테스트 → 배포 → 운영
(왼쪽)                                      (오른쪽)
</pre>

<ul>
<li>왼쪽 = 작업 초기(코드를 막 짜는 순간)</li>
<li>오른쪽 = 작업 후기(배포·운영 중)</li>
</ul>

<b>"품질을 왼쪽으로"</b> = 품질 검사(테스트·린트·리뷰)를 오른쪽(나중)이 아니라 왼쪽(가능한 한 빨리)에서 하자는 것. 버그는 늦게 발견될수록 고치는 비용이 폭발적으로 커지기 때문이다.

<ul>
<li>코딩하는 순간 린터가 잡아주면 → 5초 만에 수정</li>
<li>커밋 후 통합 단계에서 발견 → 다른 코드와 얽혀서 30분</li>
<li>운영(배포 후) 중 발견 → 장애 + 롤백 + 고객 영향 → 며칠</li>
</ul>

그래서 하네스도 검사를 한곳에 몰지 말고 비용·속도에 따라 분산한다 — <b>싸고 빠른 검사(계산적 센서)는 최대한 왼쪽으로 당겨 자주 돌리고, 비싸고 느린 검사(추론적 센서)는 오른쪽 게이트에 아껴 둔다.</b> 에이전트 맥락에선 더 중요하다 — AI가 실수를 빨리(왼쪽에서) 피드백받을수록 스스로 교정하고, 사람이 뒤늦게 잘못된 코드를 떠안는 일이 줄어든다.

## 4. 이 글이 명시하는 원칙

- 하네스 설계는 **일회성 설정이 아니라 지속적 엔지니어링 실천**이다.
- **피드포워드 + 피드백** 두 축은 모델이 바뀌어도 유지되는 구조적 원칙.
- **품질을 왼쪽으로(shift-left)**, **계산적/추론적 통제의 균형**, **토폴로지로 다양성 축소** 등 기존 소프트웨어 공학 원리(CI, fitness function)가 그대로 이어진다.
- 모델이 발전해도 **사람의 판단이 가장 필요한 지점은 남는다** — 하네스는 그 지점을 가리키는 도구.

---

## 종합: 이 글의 하네스 불변 원칙

- **가이드(피드포워드)와 센서(피드백)는 함께 가야 한다** — 한쪽만으로는 반복 실수 또는 미검증 규칙에 빠진다.
- **하네스는 계속 다듬는 실천**이다 — Steering Loop로 문제가 재발하면 하네스를 고친다.
- **사람의 판단은 사라지지 않고, 가장 중요한 곳으로 모인다.**

### 한 줄 요약
> 하네스는 **"행동 이전의 가이드 + 행동 이후의 센서"**라는 두 통제 축으로 이뤄지며,
> 모델이 바뀌어도 이 구조와 *"사람을 가장 중요한 판단으로 향하게 한다"*는 원리는 유지된다.
