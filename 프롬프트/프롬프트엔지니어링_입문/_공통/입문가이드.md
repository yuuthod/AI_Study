## 1. 하네스 개발이란 무엇이고, 누가 만들었나?

### 하네스(Harness)의 뜻

"하네스(harness)"는 원래 말에 채우는 마구(馬具)를 뜻합니다. AI 맥락에서는 **모델을 실제로 쓸 수 있게 감싸는 모든 것**을 의미합니다.

```
Agent = Model + Harness
AI 에이전트 = 모델 + 하네스
```

모델은 언어를 이해하고 생성하는 핵심 두뇌입니다. 하네스는 그 두뇌가 실제 작업을 수행할 수 있도록 감싸는 시스템 전체입니다:

| 하네스의 구성 요소 | 설명 |
|-----------------|------|
| 컨텍스트 관리 | 어떤 정보를 모델에게 줄지 결정 |
| 도구(Tools) | 파일 읽기, 웹 검색, 코드 실행 등 |
| 훅(Hooks) | 특정 이벤트에 자동으로 실행되는 코드 |
| 권한 시스템 | 무엇을 허락하고 금지할지 |
| 피드백 루프 | 결과를 보고 다음 행동을 결정 |
| 오류 처리 | 실패했을 때 어떻게 복구할지 |

### 하네스 엔지니어링(Harness Engineering)이라는 용어는 누가 만들었나?

"하네스 엔지니어링"이라는 용어 자체는 단 한 명이 만든 것이 아닙니다. 2026년 초에 여러 사람이 거의 동시에 이 개념을 정립했습니다.

**주요 기여자들 (시간순)**:

**① Mitchell Hashimoto** (HashiCorp[^1] 공동창업자)
- 2026년 2월 초, 개인 블로그 포스트에서 처음으로 "harness engineering"이라는 용어를 사용
- 코딩 에이전트를 실제로 사용하면서 경험한 것을 정리

**② OpenAI**
- 같은 달, 케이스 스터디 포스트 제목으로 "Harness Engineering" 사용
- 기업이 공식적으로 이 용어를 채택하면서 빠르게 확산

**③ Birgitta Böckeler** (Thoughtworks[^2] Distinguished Engineer)
- 2026년 4월 2일, Martin Fowler의 사이트(martinfowler.com)에 **"Harness engineering for coding agent users"** 기고
- 가장 체계적인 정의를 내린 글로 꼽힘
- 하네스를 "가이드(guides)"와 "센서(sensors)"로 분류하는 프레임워크 제시
- Martin Fowler 본인이 "AI 기반 소프트웨어 개발의 핵심을 정리한 글"이라고 추천

**④ Addy Osmani** (Google Chrome DevRel 수석)
- "좋은 모델 + 나쁜 하네스 < 평범한 모델 + 좋은 하네스"라는 핵심 명제를 정립
- 하네스를 설계할 때 **"래칫[^3] 원칙"** 개념 도입: 에이전트의 모든 실수를 영구적인 시그널로 활용하여 하네스를 점진적으로 개선

**⑤ Anthropic**
- 2026년 3월, 하네스 설계에 관한 심층 분석 공개
- Claude Code 공식 문서에 "Claude Code는 Claude를 감싸는 에이전트 하네스입니다"라고 명시

### 왜 이 용어가 중요한가?

2025년까지는 "프롬프트를 잘 쓰면 AI를 잘 쓸 수 있다"는 생각이 지배적이었습니다. 하지만 실제로 AI 에이전트를 프로덕션[^4] 환경에 배포해보니, **프롬프트 한 줄보다 그것을 둘러싼 시스템**이 더 중요하다는 것이 명확해졌습니다. "하네스 엔지니어링"은 이 인식의 전환을 담은 용어입니다.

## 2. 프롬프트 엔지니어링의 역사

### 연대기

```
2018  Richard Socher (Salesforce Research)
      멀티태스크 언어 모델 — 하나의 모델로 여러 작업 수행
      핵심 발견: 작업 설명을 입력에 포함시키면 같은 모델이 번역도, QA도 가능
                ↓
2020  Tom Brown et al. — GPT-3 논문
      "Language Models are Few-Shot Learners"
      핵심 발견: 예시를 몇 개 보여주는 것만으로 성능이 크게 향상됨 (Few-shot)
                ↓
2022  Jason Wei et al. (Google Brain) — CoT[^5] 논문
      "Chain-of-Thought Prompting Elicits Reasoning in Large Language Models"
      핵심 발견: "단계적으로 생각해보자"는 지시가 수학/추론 문제에서 성능 폭발적 향상
                ↓
2022  Suzgun et al. — Zero-shot CoT
      "단계적으로 생각해보자 (Let's think step by step)"라는 단순한 문장 하나가
      복잡한 few-shot 예시만큼 효과적임을 발견
                ↓
2023  자동화된 프롬프트 최적화 연구 급증
      DSPy, APE(Automatic Prompt Engineer) 등 프롬프트를 자동으로 개선하는 프레임워크 등장
                ↓
2024  RAG[^6], Tool Use, Agentic 패턴 주류화
      단순 Q&A를 넘어 여러 단계를 거치는 에이전트 워크플로우 확산
                ↓
2025  Andrej Karpathy, Tobi Lütke
      "Context Engineering" 개념 공식화
      "프롬프트 엔지니어링"이라는 말은 너무 좁다,
      컨텍스트 창을 채우는 기술 전체를 새롭게 정의해야 한다
                ↓
2026  Birgitta Böckeler, Mitchell Hashimoto, Addy Osmani
      "Harness Engineering" 개념 정립
      모델을 감싸는 시스템 전체를 설계하는 것이 AI 개발의 핵심 역량임
```

### 핵심 인물 정리

| 인물 | 소속/역할 | 기여 |
|------|---------|------|
| **Richard Socher** | Salesforce Research | 멀티태스크 프롬프팅의 아버지로 불림 |
| **Tom Brown** | OpenAI | GPT-3 논문 저자, few-shot prompting 정립 |
| **Jason Wei** | Google Brain → OpenAI | Chain-of-Thought prompting 창안 |
| **Elvis Saravia** | DAIR.AI 공동창업자 | promptingguide.ai 창설, 가장 포괄적인 무료 가이드 제작 |
| **Andrej Karpathy** | OpenAI 전 연구원 | "Context Engineering" 용어 대중화 |
| **Birgitta Böckeler** | Thoughtworks | "Harness Engineering" 체계적 정의 |
| **Addy Osmani** | Google Chrome DevRel | 하네스 엔지니어링 실무 원칙 정리 |

## 3. 변하지 않는 기본 개념

> AI 모델이 GPT-4에서 Claude 4으로, 또 다음 세대로 바뀌어도 이 원칙들은 여전히 유효합니다.

### 원칙 1: 명확성 (Clarity)

AI는 당신의 머릿속을 읽을 수 없습니다. 모호한 질문은 모호한 답을 낳습니다.

```
❌ 나쁜 예: "이 코드 고쳐줘"

✅ 좋은 예: "아래 Python 함수는 빈 리스트가 들어왔을 때 IndexError를 냅니다.
            빈 리스트 처리 로직을 추가하고, 변경한 이유를 주석으로 설명해줘.
            [코드 붙여넣기]"
```

**핵심**: 원하는 것, 제약 조건, 출력 형식을 명시할수록 결과가 좋아집니다.

---

### 원칙 2: 맥락 제공 (Context)

AI는 당신의 상황을 모릅니다. 관련된 배경 정보를 먼저 알려줄수록 더 관련성 높은 답변이 나옵니다.

```
❌ 나쁜 예: "이메일 작성해줘"

✅ 좋은 예: "나는 스타트업 CEO이고, 상대방은 잠재 투자자입니다.
            지난주 미팅 후속으로 IR 자료를 첨부해서 보내는 이메일입니다.
            톤: 전문적이지만 친근하게. 길이: 200자 이내"
```

---

### 원칙 3: 예시 (Examples / Few-shot)

설명보다 예시가 더 효과적입니다. 2020년 GPT-3 논문에서 증명된 원칙입니다.

```
입력: "안녕하세요" → 출력: "Hello"
입력: "감사합니다" → 출력: "Thank you"
입력: "사랑해요" → 출력: ???
```

이처럼 패턴을 보여주면 AI가 그 패턴을 그대로 적용합니다.

---

### 원칙 4: 역할 부여 (Role Assignment)

"당신은 \_\_\_입니다"라는 설정이 출력의 질을 크게 바꿉니다. AI는 역할에 맞는 어휘, 관점, 수준으로 응답합니다.

```
"당신은 10년 경력의 시니어 백엔드 개발자입니다. 
주니어 개발자에게 REST API를 설명해주세요."

vs

"당신은 대학교수입니다. 
REST API를 컴퓨터공학 개론 수준으로 설명해주세요."
```

---

### 원칙 5: 단계별 사고 유도 (Step-by-step Reasoning)

복잡한 문제일수록 "단계적으로 생각해보자"는 지시가 효과적입니다. Wei et al. (2022)이 증명한 Chain-of-Thought의 핵심입니다.

```
"이 수학 문제를 단계별로 풀어주세요. 
각 단계의 이유를 설명하면서 진행해주세요."
```

단순히 답만 요구하는 것보다 추론 과정을 명시적으로 요청할 때 정확도가 크게 올라갑니다.

---

### 원칙 6: 구조화 (Structure)

출력의 형식을 지정하면 일관성이 올라갑니다.

```
"다음 형식으로 답변해주세요:
## 요약 (3줄 이내)
## 주요 포인트 (번호 목록)
## 결론"
```

Anthropic은 특히 `<xml 태그>`를 활용한 구조화를 강력하게 추천합니다:
```xml
<instructions>
  이 텍스트를 요약해주세요.
</instructions>
<text>
  [분석할 텍스트]
</text>
```

---

### 원칙 7: 반복 개선 (Iteration)

처음 작성한 프롬프트가 완벽할 수는 없습니다. 결과를 보고 문제를 파악하고 프롬프트를 수정하는 과정이 필수입니다.

```
프롬프트 작성 → 결과 확인 → 문제 파악 → 수정 → 반복
```

## 4. 계속 발전하는 기법들

> 아래 기법들은 개념은 안정적이지만, 최적의 방법은 모델이 발전함에 따라 계속 바뀝니다.

### 4-1. Few-shot → Zero-shot 전환

초기 LLM[^7]에서는 예시 없이(Zero-shot) 작업을 시키면 성능이 낮았습니다. 그래서 예시를 몇 개 보여주는 Few-shot이 필수였습니다.

최신 모델은 Zero-shot 성능이 크게 향상되어, 잘 설계된 지시 하나만으로도 복잡한 작업을 처리합니다. **예시 제공의 필요성이 줄었지만, 없어진 것은 아닙니다.**

---

### 4-2. Chain-of-Thought (CoT) 기법들

```
CoT의 발전 단계:

Manual CoT (Wei 2022)
  "단계적으로 생각하고 각 단계를 설명하며 답하라"
  → 수동으로 추론 예시를 제공
          ↓
Zero-shot CoT (Kojima 2022)
  "Let's think step by step"
  → 예시 없이 단순 지시 문장만으로도 효과
          ↓
Auto-CoT (Zhang 2022)
  → 예시 자동 생성 + CoT 자동화
          ↓
Tree of Thoughts (Yao 2023)
  → 단선적 추론이 아닌 트리 구조로 여러 가능성 탐색
          ↓
Extended Thinking (Anthropic, 2024+)
  → 모델이 내부적으로 추론 과정을 갖도록 훈련
    프롬프트 기법이 아닌 모델 자체의 기능으로 통합
```

**현재 방향**: 추론을 "프롬프트로 유도"하는 것에서 → "모델이 기본적으로 수행"하는 방향으로 이동 중.

---

### 4-3. 프롬프트 체이닝 (Prompt Chaining)

복잡한 작업을 작은 프롬프트 연쇄로 분해합니다. 단일 거대 프롬프트보다 오류율이 35~50% 감소한다는 연구 결과가 있습니다.

```
[프롬프트 1] 자료 수집
    → 출력물 →
[프롬프트 2] 분석
    → 출력물 →
[프롬프트 3] 정리 및 작성
```

이것이 현재 대부분의 에이전트 워크플로우의 기반입니다.

---

### 4-4. RAG (Retrieval-Augmented Generation)[^8]

AI 모델은 학습 데이터 이후의 정보를 모릅니다. RAG는 필요한 정보를 외부에서 검색하여 컨텍스트에 포함시키는 패턴입니다.

```
사용자 질문
    ↓
[검색 엔진] 관련 문서 검색
    ↓
"다음 문서를 참고하여 질문에 답하라: [문서 내용]"
    ↓
모델 응답
```

**중요**: RAG는 프롬프트 기법이 아니라 **시스템 아키텍처[^9]**입니다. 하네스의 일부로 자리잡았습니다.

---

### 4-5. XML/구조적 태그 활용

Anthropic의 Claude는 XML 태그로 입력을 구조화할 때 성능이 크게 향상됩니다. 다른 모델들도 구조적 입력에 더 잘 반응하는 방향으로 발전하고 있습니다.

```xml
<task>코드 리뷰</task>
<context>이 코드는 Python으로 작성된 REST API입니다</context>
<code>
def get_user(id):
    return db.query(id)
</code>
<focus>보안 취약점, SQL 인젝션 위험성을 중점으로 검토해주세요</focus>
```

## 5. 지금 일어나는 변화: 컨텍스트 엔지니어링

### "프롬프트 엔지니어링"이라는 말의 한계

2025년 중반, Andrej Karpathy(전 OpenAI 연구원, Tesla AI 수석)와 Tobi Lütke(Shopify CEO)가 동시에 같은 말을 했습니다:

> "프롬프트 엔지니어링(Prompt Engineering)이라는 말은 너무 좁다."

Karpathy의 원문 트윗:
> "+1 for 'context engineering' over 'prompt engineering'.  
> People associate prompts with short task descriptions you'd give an LLM in your day-to-day use.  
> When in every industrial-strength LLM app, **context engineering** is the delicate art and science of filling the context window."

**번역**: 프롬프트 엔지니어링이라고 하면 사람들은 짧은 지시문을 떠올리지만, 실제 프로덕션 LLM 앱에서는 컨텍스트 창을 올바른 정보로 채우는 기술 전체가 중요하다.

---

### 컨텍스트 엔지니어링이란?

```
프롬프트 엔지니어링 ⊂ 컨텍스트 엔지니어링
(프롬프트 엔지니어링은 컨텍스트 엔지니어링의 부분집합)
```

컨텍스트 창은 AI가 한 번에 볼 수 있는 "작업 메모리"입니다. 이 창에 무엇을 어떻게 넣을지가 핵심입니다.

| 컨텍스트의 출처 | 예시 |
|--------------|------|
| 사용자의 직접 입력 | 질문, 코드, 문서 |
| 시스템 프롬프트 | 역할 설정, 규칙, 제약 |
| 검색된 문서 (RAG) | 관련 코드베이스, 문서 |
| 도구 실행 결과 | 터미널 출력, API 응답 |
| 이전 대화 기록 | 대화 맥락 유지 |
| 에이전트 상태 | 진행 중인 작업 정보 |

**컨텍스트 엔지니어는** 이 모든 것을 조율하여, 모델이 현재 작업을 수행하기에 딱 필요한 정보만 컨텍스트 창에 있도록 관리합니다.

---

### 하네스 엔지니어링과의 관계

```
컨텍스트 엔지니어링 = 하네스의 핵심 구성 요소
(Context Engineering ⊂ Harness Engineering)
```

Böckeler의 표현으로: 하네스는 "가이드(무엇을 할지 알려주는 것)"와 "센서(결과를 관찰하는 것)"로 구성되며, 컨텍스트 엔지니어링은 그 가이드를 어떻게 구성할지의 기술입니다.

---

## 6. 앞으로의 방향

### 방향 1: 에이전틱 AI (Agentic AI)의 주류화

```
현재: "AI에게 질문 → AI가 답변"  (단발성 상호작용)
미래: "AI에게 목표 → AI가 계획·실행·수정을 반복"  (자율적 작업 수행)
```

Gartner[^10] 예측:
- 2026년 말까지 기업 앱의 40%에 AI 에이전트 탑재 (2025년에는 5% 미만)
- 2026년까지 기업 GenAI 배포의 30%가 에이전트 아키텍처 사용

**프롬프트 엔지니어링에서 에이전트 프롬프트로의 전환:**
단순히 "잘 물어보는 기술"에서 → "AI가 자율적으로 일하도록 환경을 설계하는 기술"로 확장.

---

### 방향 2: 프롬프트가 모델 안으로 흡수된다

현재는 "CoT를 유도하는 프롬프트를 써야 한다"가 중요합니다. 하지만 Claude 3.5+, GPT-o1+ 같은 최신 모델들은 추론을 내부적으로 수행합니다. 점점 더 많은 "프롬프트 테크닉"이 모델 자체의 기능으로 흡수됩니다.

```
프롬프트 테크닉 (외부) → 모델 내부 기능 (내재화)
예: "단계별로 생각해라" → 모델이 기본적으로 단계적 추론 수행
예: "역할을 부여해라" → 모델이 문맥에 맞는 역할을 자동 인식
```

**결론**: 프롬프트의 세세한 기법보다 **원하는 것을 명확히 표현하는 능력**이 더 중요해집니다.

---

### 방향 3: 하네스 설계가 핵심 경쟁력이 된다

좋은 모델이 범용화될수록, 어떤 회사가 더 좋은 모델을 갖고 있느냐보다 **어떻게 감쌌느냐**가 차별점이 됩니다.

Addy Osmani의 명제:
> "평범한 모델 + 훌륭한 하네스 > 훌륭한 모델 + 평범한 하네스"

---

### 방향 4: 멀티 에이전트 오케스트레이션[^11]

단일 AI가 모든 것을 하는 것이 아니라, 특화된 여러 AI 에이전트가 협력하는 구조가 확산됩니다.

```
오케스트레이터 에이전트 (전체 조율)
    ├── 연구 에이전트 (정보 수집)
    ├── 코딩 에이전트 (구현)
    ├── 검토 에이전트 (검증)
    └── 문서 에이전트 (정리)
```

이때 에이전트 간의 프롬프트와 컨텍스트 전달 방식이 새로운 설계 과제로 등장합니다.

---

## 7. 학습 로드맵과 핵심 자료

### 단계별 학습 순서

```
1단계: 기초 (1~2주)
  → 프롬프트 엔지니어링의 기본 개념 이해
  → 직접 해보며 원칙 체감

2단계: 핵심 기법 (2~4주)
  → Zero-shot, Few-shot, CoT 실습
  → XML 구조화, 역할 부여, 프롬프트 체이닝

3단계: 시스템 관점 (1~2개월)
  → 컨텍스트 엔지니어링 개념
  → RAG, Tool Use 이해
  → 에이전트 아키텍처 기초

4단계: 하네스 설계 (지속적)
  → 실제 프로젝트에서 에이전트 구축
  → 하네스 패턴 학습 및 적용
```

### 직접 실습할 때 기억할 것

1. **기법을 외우지 말고 원칙을 이해하라** — 모델이 바뀌면 기법의 최적값도 바뀌지만 원칙은 유지됩니다
2. **특정 플랫폼에 종속되지 마라** — Claude에서 통하는 것이 GPT에서도 통하는 원칙에 집중
3. **실패에서 배워라** — 잘못된 출력이 나왔을 때 왜 그랬는지 분석하는 것이 가장 빠른 학습
4. **맥락이 전부다** — 좋은 프롬프트의 90%는 "충분한 맥락을 제공했는가"에서 결정됨

## 한눈에 보는 개념 지도

```
프롬프트 엔지니어링 (2018~2024)
├── 변하지 않는 것
│   ├── 명확성, 맥락, 예시, 역할, 구조화, 단계적 사고
│   └── 이 원칙들은 어떤 모델에도 적용됨
│
├── 계속 발전하는 것
│   ├── Few-shot → Zero-shot (모델이 좋아질수록 예시 필요성 감소)
│   ├── 수동 CoT → 내재화 (모델이 추론을 자체적으로 수행)
│   ├── 단순 프롬프트 → 프롬프트 체이닝 → 에이전트 워크플로우
│   └── RAG, Tool Use 통합
│
컨텍스트 엔지니어링 (2025~)
│   컨텍스트 창에 무엇을 넣을지 전체적으로 설계
│   (프롬프트 엔지니어링은 이것의 부분집합)
│
하네스 엔지니어링 (2026~)
    Agent = Model + Harness
    모델을 감싸는 시스템 전체 설계
    (컨텍스트 엔지니어링 + 도구 + 권한 + 피드백 루프 + 오류 처리)
```

[^1]: **HashiCorp**: Terraform, Vault 등 인프라 관리 도구로 유명한 소프트웨어 회사. Mitchell Hashimoto가 공동 창업.
[^2]: **Thoughtworks**: 글로벌 소프트웨어 컨설팅 회사. Martin Fowler가 수석 과학자로 있으며, 소프트웨어 아키텍처 관련 글로 유명.
[^3]: **래칫(Ratchet) 원칙**: 래칫은 한 방향으로만 돌아가는 톱니바퀴. "하네스를 절대 후퇴시키지 않고 계속 개선만 한다"는 개념. 에이전트가 한 번 실수하면 그 실수를 방지하는 규칙이 하네스에 영구적으로 추가됨.
[^4]: **프로덕션(Production)**: 실제 사용자들이 사용하는 운영 환경. 개발/테스트 환경의 반대 개념.
[^5]: **CoT (Chain of Thought)**: 생각의 사슬. AI에게 단계별로 추론 과정을 명시적으로 서술하도록 유도하는 기법. "단계적으로 생각해보자"라는 지시 하나로 수학, 논리 문제 정확도가 크게 향상됨.
[^6]: **RAG (Retrieval-Augmented Generation)**: 검색 증강 생성. AI가 답하기 전에 외부 데이터베이스에서 관련 문서를 검색하여 컨텍스트에 포함시키는 패턴. 최신 정보 활용 및 환각(hallucination) 감소에 효과적.
[^7]: **LLM (Large Language Model)**: 대규모 언어 모델. 방대한 텍스트 데이터로 훈련된 언어 AI. GPT, Claude, Gemini 등이 이에 해당.
[^8]: **RAG**: 각주 6번 참조.
[^9]: **아키텍처(Architecture)**: 시스템을 구성하는 컴포넌트들의 구조와 상호작용 방식. 개별 기능보다 전체적인 설계 방식을 의미.
[^10]: **Gartner**: 전세계 IT 시장 분석 및 연구로 유명한 리서치 회사. 기술 트렌드 예측 보고서로 유명.
[^11]: **오케스트레이션(Orchestration)**: 여러 구성 요소를 조율하여 하나의 통합된 목표를 달성하는 것. 음악의 오케스트라에서 유래.
