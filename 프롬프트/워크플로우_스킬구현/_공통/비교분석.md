# 워크플로우_스킬구현 비교분석

날짜: 2026-06-17
큰 주제: 프롬프트
참여자: river, kon

---

## 스터디 목적
river의 `start/` 번들을 **실무 투입 가능한 수준**으로 끌어올린다 — kon이 정리한 하네스 원칙(특히 **"무엇을 고정하고 무엇을 자라게 둘 것인가"**)을 체크리스트 삼아, river 번들에서 **수정·보완할 지점**을 찾아낸다. ("누가 더 잘했나"가 아니라, kon의 원리 문서를 렌즈로 써서 river의 실제 산출물의 구멍을 메우는 작업.)

## 오늘의 진행 순서
1. 고정 vs 성장 (핵심 축)
2. 진행상황·결정의 외부화 (핸드오프)
3. 가이드 문서의 고도·분량
4. 센서 피드백 + 비계 주기 점검 (운영기)

## river 핵심 정리
**"완성형 설치 키트".** 원본 프롬프트(`직접 작성.md`)에서 출발해, AI가 **질문 0회로 한 번에 돌리면 당장 실무 개발이 가능한 풀스택 프로젝트**가 나오는 실제 산출물.
- `start.md`(오케스트레이터, Phase 0~8) + `AGENTS.md`(라우터 + 불변 규칙) + 워크플로우 7종 + 공유 프래그먼트 6종 + 보안 스니펫.
- 스택·보안·제약을 전부 못박음(RR7, pnpm, Prisma, argon2id, Zod+Conform, Sass+CSS Modules, Storybook…). "확정 결정 = 변경 금지."
- 라우터가 작업을 분류해 `docs/workflows/<작업>.md` **한 장**으로 보냄(점진적 공개).
- 멀티에이전트 호환: `AGENTS.md`=진실원천, `CLAUDE.md`·`GEMINI.md`는 얇은 포인터.
- `start-후속질의/` 8건에 설계 근거(스킬 연동·시뮬레이션·멀티에이전트·브랜치/커밋·prettier·기획문서패턴·성숙도분기·디자인파운데이션)가 풍부.

## kon 핵심 정리
**"원리에서 도출한 설계도".** 지난 스터디(04_종합비교)의 **다섯 불변 원칙**을 워크플로우로 옮기는 *사고 과정* 자체를 문서화.
- **일반형 뼈대 → 소규모 경량화 → 실제 스킬 매핑** 3단으로 내려옴.
- 핵심 루프: 가이드(행동 전) → 실행 → 센서(행동 후) → 사람 게이트, 그 바깥을 적재·핸드오프가 감쌈.
- **래칫 원칙**(최소로 시작 → 실수 2번이면 규칙 승격) + **비계 양·위치 재조정**(모델 업글 시)에 강점.
- 소규모 최소 세트를 Node/TS 예시로 구체화(CLAUDE.md·eslint·vitest·husky·CI·브랜치 보호).
- 스킬 매핑표(office-hours·brainstorming·grill-me = 가이드 / tdd·review·diagnose = 센서).
- 근거 약한 스킬(zoom-out·improve-codebase-architecture·ship)은 정직하게 **"보류"**로 분리.

## 핵심 분석

두 자료 모두 "하네스 워크플로우"를 만들었지만 **출발점이 정반대**다.
- **river = 위에서 아래로**: "완성된 제품"을 그리고 결정을 박아 내려옴. 강점은 **세팅기**(프로젝트를 세우는 것).
- **kon = 아래에서 위로**: "원칙"에서 쌓아 올림. 강점은 **운영기**(세운 뒤 굴리며 하네스를 유지·진화).

이 비대칭이 오늘 비교의 핵심이었다. river의 구멍은 대부분 **운영기**에 있었고, kon의 원리 문서가 정확히 그 자리를 비춰주었다.

### 안건 1 — 고정 vs 성장: 충돌이 아니라 다른 층위
river가 "박은 것"과 kon이 "비우라는 것"은 다른 종류의 규칙이다.
- **인프라/보안 기본기**(프레임워크·경계·토큰) → river가 박은 게 **맞다.** 매 프로젝트 재발명하면 낭비. kon이 "비우라"고 한 대상이 아님.
- **도메인 규칙 / 축적되는 교훈** → 실수에서 자라는 것. kon의 래칫이 겨냥하는 쪽.
- river는 래칫을 이미 가지고 있다(`workflow-change.md`: "한 번 더해진 규칙은 되돌리지 않는다", "거대 트리식 금지, 필요해질 때 하나씩"). 빠진 건 **무엇이 그 PR을 열게 하는 트리거**였다 → 안건 4에서 해결.

### 안건 2 — 진행상황·결정 외부화 (오늘의 핵심 구멍)
kon의 지식 외부화(④)는 두 종류다.
- **계획 외부화**(무엇을 만드나) → river **완비**(specs/overview/screens). ✅
- **세션 상태 외부화**(지금 뭐 하는 중 + 왜 그렇게 구현했나) → river **빈칸.** ❌
- 역설: river의 `start-후속질의/`가 바로 훌륭한 결정 로그인데, **그 습관이 생성될 프로젝트엔 이식되지 않는다.** 번들이 깔리면 결정 근거를 남길 자리가 사라져, 다음 세션이 `git log`로 재발굴하거나 이미 내린 결정을 뒤집는다.

### 안건 3 — 고도·분량: river 이미 통과
- "세부는 링크로" ✅ / "100줄 이하"(AGENTS.md 62줄, 각 워크플로우 24~33줄) ✅ / "얇은 포인터"(CLAUDE·GEMINI) ✅.
- 분량을 **"한 작업엔 문서 하나만"(라우팅=점진적 공개)**으로 해결 — kon이 인용한 Anthropic의 적시 검색(JIT)과 동일 전략.
- "처음엔 비어도 된다"는 river에 비적용: 불변 규칙 12개가 전부 인프라성이고, 키트는 항상 같은 모양의 프로젝트를 찍으므로 미리 박는 게 맞다.
- 결론: **변경 없음.**

### 안건 4 — 운영기 보완 (마찰 로그 3단 구조)
river 번들은 **세팅기**에 최적화돼, 세운 뒤 하네스를 유지·진화시키는 부분이 얇다. 여기서 두 자료가 가장 상호보완적이다.
- 안건 1에서 미룬 **래칫 트리거**("같은 실수 2번")는 *누군가 1번째를 기억해야* 작동하는데, 에이전트는 세션이 바뀌면 기억이 없다 → **기록을 외부 파일에 쌓아** 사람의 기억이 아니라 로그로 판정하게 한다.
- river가 제안한 `/workflow-bug` 스킬 아이디어는 검증된 패턴(kon의 결정로그, OpenAI "규칙 승격", Böckeler "Steering Loop", 이 환경의 `/learn`·`/retro`). 단 river 자신의 **이식성 원칙**(스킬=선택적 가속)과 **기록↔승격 빈도 차이** 때문에 "파일 우선·스킬은 가속·브랜치는 승격 때만"으로 조정.

## 공통점
- 둘 다 하네스의 핵심 루프를 **가이드 → 실행 → 센서 → 사람 게이트**로 본다.
- 둘 다 **기계 게이트(타입·lint·테스트)를 먼저 통과**시키고, 사람은 끝(설계·시각 검수)에만 둔다.
- 둘 다 래칫(점진 강화, 되돌리지 않음)을 채택한다.
- 둘 다 가이드 문서는 "지도지 매뉴얼이 아니다 — 세부는 링크로/점진 공개"를 따른다.
- 둘 다 스킬을 단계에 매핑하되, 이식성/이중통제를 의식한다.

## 토론 내용 (안건별 결정)

**안건 1 — 도메인 규칙 성장 경로**
- 질문: 프로젝트가 굴러가며 배우는 도메인 규칙을 어디에 쌓나? (가벼운 칸 신설 vs 전부 workflow-change vs 트리거만 명시)
- **river 결정: 전부 workflow-change 유지**(엄격·일관, 모든 하네스 변경이 git에 추적). 단 트리거가 비어 있는 점은 안건 4에서 보완.

**안건 2 — 진행/결정 외부화 형태**
- 질문: 진행 상태 + 결정 로그 빈칸을 어떤 형태로 메우나? (ADR+라이브 분리 vs TODO.md 한 장 vs 커밋/PR로 갈음)
- **river 결정: ADR 경량(`docs/decisions/`, 한 결정=한 파일, 불변) + 라이브 진행 파일 분리.** "왜 그렇게 했나"는 영구 보존, "지금 뭐 하는 중"은 휘발성으로 분리.

**안건 3 — 적정 고도 한 줄 추가 여부**
- 질문: 미래에 추가될 규칙의 고도를 잡아줄 한 줄을 workflow-change에 넣나?
- **river 결정: 추가하지 않음.** river가 이미 통과한 항목이고 문서 수를 안 늘리는 게 더 이득.

**안건 4 — 운영기 보완 / 마찰 로그**
- river가 `/workflow-bug` 스킬 아이디어 제시 → 이식성·빈도 차이 지적 → **3단 구조로 조정 합의.**
- "누가 2번째를 판단하나?" = **사람(리뷰어)**, 단 1번째가 로그에 기록돼 있어야 판정 가능(안건 2와 맞물림). 에이전트에 "PR 전 재발 셀프체크"를 시키면 사람 의존 감소.
- 라이프사이클 확정:
  - **append**(사건마다·잦음): 게이트에서 마찰이 걸린 작업 종료 시 `docs/friction-log.md`에 한 줄.
  - **닫힘**(드묾): 같은 부류 2회차 → `workflow-change`로 승격(규칙 강화 or lint·테스트 기계화), 별도 브랜치+PR은 **이때만**.
  - **prune**(주기적): 주간 retro 때 사람이 솎음(1회성 오래된 것=삭제, 반복=승격후보, 승격됨=아카이브).
- **river 결정: 3단 구조(파일+절차 우선, 스킬은 나중).** 이식성 위해 스킬 없어도 수동 append.

## 공동 결론 — start 번들 수정·보완 목록

오늘 목적("실무 투입 가능 수준으로")에 비추어, river 번들에 반영할 변경은 다음과 같다. river의 강점(세팅기)은 그대로 두고, 약점(운영기·핸드오프)만 메운다. 인프라 결정·고정 정책·고도는 **건드리지 않는다.**

1. **`docs/decisions/_template.md` 신설** (ADR 경량, 한 결정=한 파일, 불변)
   - `docs/README.md` 문서 지도에 등록 + `AGENTS.md ②`에서 참조.
   - 용도: "왜 A 대신 B로 갔나"를 영구 보존(후속질의의 결정 로그 습관을 프로젝트로 이식).

2. **라이브 진행 파일 신설** (루트 `TODO.md` 또는 `docs/PROGRESS.md`)
   - `진행 중` / `다음 할 일`. init(`start.md`) 또는 `project-kickoff`에서 생성.
   - 용도: 세션 간 핸드오프 — 다음 세션이 읽고 바로 이어받게.

3. **`docs/friction-log.md` 신설 + 절차** (마찰 로그 3단)
   - append(사건마다) → 승격(2회차, workflow-change) → prune(주기 retro).
   - 각 워크플로우 **공통 종료**에 "마찰 있었으면 friction-log append, 결정이면 ADR" 한 줄.

4. **`workflow-change.md` "언제 여기로 오나"에 트리거 한 줄**
   - "같은 부류의 실수·리뷰 지적이 2번 반복되면(friction-log 2회차) 여기로 와서 규칙·센서로 승격. 1번은 그냥 고치고, 2번째에 박는다. 가능하면 lint·테스트로 기계화."
   - 별도 브랜치+PR은 **승격 때만**임을 명시.

5. **(선택, 추후) `/workflow-bug` 스킬** = friction-log append 가속기
   - 이식성 원칙 준수: "있으면 가속, 없으면 같은 파일에 수동 append."

> **변경하지 않는 것:** 안건 1(인프라 고정·전부 workflow-change), 안건 3(고도·분량) — river가 이미 잘 지키고 있어 손대지 않는다.

> 다음: 위 1~4는 river의 `workflow-change` 절차(별도 브랜치+PR)를 따라 실제 번들에 반영한다.
