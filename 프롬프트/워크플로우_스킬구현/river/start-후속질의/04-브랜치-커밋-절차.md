# Q4. 브랜치 포맷 · 커밋 포맷 · 커밋 전 절차

> 질문: 브랜치 생성 방식, 커밋 형태 예시, 커밋 전 강제 절차(husky로 강제된 내용 — 테스트 전부 통과 등).

## 브랜치 포맷
`<type>/<scope>-<요약>` (소문자 kebab, 1브랜치=1작업=1PR)
```
feat/auth-login   fix/profile-avatar-null-crash   refactor/button-variants
docs/readme-setup   workflow/add-refactor-doc
```

## 커밋 포맷 (Conventional Commits — commitlint 강제)
```
<type>(<scope>): <제목>     # 명령형, 마침표 금지
<빈줄> 본문(왜) <빈줄> 푸터(BREAKING CHANGE / refs)
```
예: `feat(auth): 이메일·비밀번호 로그인 추가` / `fix(profile): avatar null 크래시 방지`
허용 타입: feat fix refactor docs test chore style perf ci build revert

## 커밋 전 절차 (husky 강제 — 계층)
- pre-commit: lint-staged(변경 ts/tsx→eslint --fix+prettier, scss/css/json/md→prettier). 못 고치는 lint→차단.
- commit-msg: commitlint 형식 검증→위반 차단.
- pre-push: `pnpm typecheck && pnpm test`→실패 차단.
- CI(우회 불가): typecheck+lint+test+build+e2e+migrate→실패 시 머지 차단.

### 핵심
1. 테스트 전체 통과 강제는 **pre-push·CI**(매 커밋 전체 테스트는 느려서 --no-verify 우회 유발 → Q10).
2. `--no-verify`로 로컬은 뚫려도 **CI는 못 뚫음** → 진짜 보증은 CI + 브랜치 보호(필수 체크).
