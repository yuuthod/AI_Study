## 0. 프로젝트 기본 정의 (foundation)

### 제품 한 줄 정의
인디 밴드 공연을 **밴드가 직접 개설·운영**하고, 관객은 **무통장입금으로 예매한 뒤 QR로 현장 입장**하는 소규모 라이브 공연 예매 서비스.

### 대상 사용자 / 핵심 가치
- **일반회원(관객)**: SNS 간편 로그인으로 가입, 예매 내역을 "지류 티켓 모음집"처럼 보관·관람 히스토리 수집.
- **비회원(관객)**: 가입 없이 비밀번호 기반으로 예매·조회.
- **밴드회원(주최)**: 공연 개설, 무통장입금 입금확인, 현장 QR 입장 관리까지 직접 운영.
- **핵심 가치**: 소규모 공연에 특화된 *가벼운 예매 + 수기 정산(무통장) + 현장 입장 관리*의 일원화.

### 범위 (Scope)
- **In:** SNS/밴드 인증, 공연 탐색·검색, (회원·비회원) 무통장입금 예매·조회·취소, QR 입장, 마이페이지/티켓 보관, 문의, 밴드의 공연 개설·예매관리·현장입장 관리.
- **Out:** 카드/PG 자동결제, 좌석 지정 예매, 환불 자동화, 정산 자동 송금, 푸시/문자 발송 인프라(초기 범위 밖, 추후 검토).

### 도메인 용어집 (Ubiquitous Language)
| 용어 | 정의 |
|---|---|
| 공연(Performance) | 밴드회원이 개설하는 단위 이벤트. 포스터·일시·장소·티켓가·입금계좌·매수 보유 |
| 밴드회원 | 공연을 개설·운영하는 주최자. 아이디/비번 + 밴드명·인스타ID(인스타 인증) 기반 |
| 일반회원 | SNS(카카오/구글) 로그인 기반 관객 |
| 비회원 | 계정 없이 이름·전화번호·비밀번호로 예매·조회하는 관객 |
| 예매(Reservation) | 특정 공연에 대한 1건의 티켓 구매 신청. 매수·예매자정보·입금정보 포함 |
| 무통장입금 | 본 서비스의 유일 결제 수단. 예매자가 계좌로 송금 → 밴드가 수기 입금확인 |
| 입금확인 | 밴드회원이 예매 건의 입금을 확인 처리하는 행위. 예매 상태를 확정시킴 |
| 지류 티켓 | 종이 티켓 메타포. 예매 내역/입장 QR 화면의 비주얼 콘셉트 |
| QR 입장 | 예매 건마다 발급되는 QR. 현장에서 밴드/스태프가 스캔해 입장 처리 |
| 매진 / 티켓 오픈 전 / 지난 공연 | 공연·예매의 상태값. 예매 가능 여부와 화면 분기를 결정 |
| 공연 히스토리 | 일반회원이 관람 완료한 공연의 아카이브(티켓 컬렉션) |

### 예매 상태 모델 (전 기능 공통 기준)
한 예매 건은 다음 상태를 가진다 — 화면 분기·권한의 기준이 된다.
1. **입금확인중** — 예매 접수, 밴드의 입금확인 대기
2. **입장확인(입금완료)** — 밴드가 입금확인 처리, QR 유효
3. **입장완료** — 현장에서 QR 스캔으로 입장 처리됨
4. **취소** — 예매자/밴드에 의해 취소됨

공연(예매 가능 여부) 상태: **티켓 오픈 전 · 예매 가능 · 매진 · 공연중 · 지난 공연(마감)**.

### 비기능 요구 (기준선)
- 보안: 모든 신뢰 경계 입력 Zod 검증, 세션 httpOnly 쿠키, 시크릿 격리(start 번들 베이스라인 준수).
- 비회원 예매 조회·취소는 **이름+전화번호+비밀번호** 3요소 검증으로만 접근.
- 소유권 인가: 밴드회원은 **자신이 개설한 공연**의 예매/입장만 관리 가능.

## F-01 · 인증 & 회원 관리

**관련 화면:** A1(SNS 로그인), A2(SNS 회원가입·추가정보), A3(밴드 회원가입/로그인) · [화면정의서 A](./화면정의서.md#a-인증)

### 목적/배경
관객은 마찰 없는 SNS 간편 로그인으로, 밴드는 운영 책임이 따르므로 별도 아이디/비번 + 인스타 인증으로 가입한다. 무통장·현장운영 특성상 신원 단위(밴드)가 분명해야 한다.

### 사용자·시나리오
- 관객: 카카오/구글로 최초 로그인 → 닉네임 등 추가정보 1회 입력 → 일반회원 생성.
- 밴드: 아이디·비번·밴드명·인스타ID 입력 후 가입 → 인스타 인증 안내를 거쳐 활성화.

### 범위 (Scope)
- **In:** 카카오/구글 OAuth 로그인, 최초 로그인 시 추가정보(닉네임 등) 입력, 밴드 회원가입/로그인, 인스타 인증 안내, 로그인 실패 처리.
- **Out:** 이메일/비번 기반 일반회원 가입, 비밀번호 찾기(SNS는 위탁), 인스타 인증의 자동화(초기엔 수기/안내 기반).

### 수용 기준
- [ ] 카카오·구글 각각으로 로그인할 수 있고, 실패 시 사유 메시지를 보여준다.
- [ ] SNS 최초 로그인 시 추가정보 입력을 완료해야 일반회원으로 활성화된다.
- [ ] 밴드 가입 시 아이디 중복·필수값(밴드명·인스타ID)을 검증한다.
- [ ] 밴드 계정은 인스타 인증 상태를 가지며, 미인증 상태가 화면에 드러난다.

### 필요 데이터
- 모델/필드(기획): `User`(provider, providerId, nickname, role=일반), `BandAccount`(loginId, passwordHash, bandName, instaId, instaVerifiedStatus, logoUrl).
- 신뢰 경계 입력: OAuth 콜백 토큰, 닉네임, 밴드 loginId/password/bandName/instaId.

### 비고 / 미결
- 인스타 인증 방식(수기 확인 vs 자동) 미확정 → 결정 시 ADR.

## F-02 · 공연 탐색 & 검색

**관련 화면:** B1(진행 중 리스트), B2(지난 공연 리스트), B3(공연 상세·진행중), B4(공연 상세·지난), B5(검색) · [화면정의서 B](./화면정의서.md#b-공연-탐색)

### 목적/배경
관객(로그인 불문)이 볼 공연을 찾는 진입점. 임박순 정렬과 지역·장르 필터로 "곧 있는 공연"을 빠르게 노출하는 것이 최상위 가치.

### 사용자·시나리오
- 비로그인/일반/비회원이 홈에서 진행 중 공연을 임박순으로 훑고, 지역·장르로 좁히거나 검색해 상세로 진입.
- 지난 공연은 아카이브 톤으로 별도 노출(관람 후 회고/밴드 탐색).

### 범위 (Scope)
- **In:** 진행 중 공연 리스트(임박순 정렬, 지역·장르 필터), 지난 공연 리스트, 공연 상세(상태별 5분기), 검색(입력/결과/결과없음).
- **Out:** 추천·개인화 정렬, 찜/알림, 무한스크롤 고도화(초기엔 기본 페이지네이션).

### 수용 기준
- [ ] 진행 중 리스트가 임박순으로 정렬되고 지역·장르 필터가 동작한다.
- [ ] 공연 상세가 ①예매가능 ②예매내역보유 ③매진 ④티켓오픈전 ⑤지난공연 5케이스로 분기된다.
- [ ] 지난 공연 상세는 비활성 버튼 "예매가 끝난 공연입니다"를 노출한다.
- [ ] 검색 결과 없음 케이스에 빈 상태 안내를 보여준다.

### 필요 데이터
- 모델/필드: `Performance`(title, posterUrl, bandId, startAt, region, genre, ticketPrice, totalQty, soldQty, ticketOpenAt, status).
- 파생: 예매가능 여부 = `status·soldQty·ticketOpenAt·startAt` 조합으로 산출.

### 비고 / 미결
- "예매내역 보유" 분기는 로그인/비회원 식별 후에만 정확 → 비회원은 조회 흐름과 연계.

## F-03 · 예매 & 결제 (무통장입금)

**관련 화면:** C1(예매하기), C2(예매 확인 모달), D1(비회원 예매하기), D2(비회원 확인 모달), D3(비회원 예매 조회), K1·K2(확인 모달) · [화면정의서 C/D](./화면정의서.md#c-예매--결제--일반회원)

### 목적/배경
서비스의 핵심 전환 지점. 결제는 무통장입금 단일 수단이므로, 예매 폼에서 **계좌 안내·입금자명·입금일시**를 명확히 받아 밴드의 수기 입금확인이 가능하게 한다.

### 사용자·시나리오
- 일반회원: 공연 상세 → 예매하기(C1) → 확인 모달(C2/K1)로 최종 확인 → 입금확인중 상태로 접수.
- 비회원: 동일 폼 + **비밀번호 필드**(D1) → 확인 모달(D2/K2) → 이후 D3에서 이름·전화번호·비밀번호로 조회.

### 범위 (Scope)
- **In:** 매수·예매자명·전화번호·입금자명·입금일시 입력, 계좌번호 복사, 예매 확인 모달(금액 합계·계좌 최종 확인), 비회원 비밀번호 설정, 비회원 예매 조회.
- **Out:** 자동 결제/입금 매칭, 부분 환불, 예매 변경(수량 수정은 취소 후 재예매로 대체).

### 수용 기준
- [ ] 매수 입력 시 총 금액이 자동 계산되어 확인 모달에 표시된다.
- [ ] 계좌번호 복사 버튼이 동작한다.
- [ ] 잔여 수량(매진/초과)을 검증해 예매를 막는다.
- [ ] 비회원 예매는 비밀번호가 필수이고, D3에서 이름·전화번호·비밀번호 3요소로만 조회된다.
- [ ] 예매 접수 시 상태가 **입금확인중**으로 생성된다.

### 필요 데이터
- 모델/필드: `Reservation`(performanceId, userId|null, buyerName, phone, depositorName, depositAt, quantity, amount, guestPasswordHash|null, status, qrToken).
- 신뢰 경계 입력: 매수·예매자명·전화번호·입금자명·입금일시·(비회원)비밀번호.
- 규칙: `amount = quantity × ticketPrice`(서버 재계산), 잔여수량 = `totalQty − soldQty`.

### 비고 / 미결
- 입금일시는 "예정 입금일시" 입력인지 "실제 입금" 보고인지 정의 필요 → 밴드 입금확인 UX와 함께 확정.

## F-04 · 티켓 보관 & QR 입장

**관련 화면:** E2(예매 내역), E3(예매 상세), E4(입장 QR), G1(비회원 예매 상세=E3 재활용), K3(예매 취소 확인) · [화면정의서 E](./화면정의서.md#e-마이페이지--일반회원)

### 목적/배경
예매 후 ~ 현장 입장까지의 관객 동선. "지류 티켓 모음집" 메타포로 예매를 소장 가치 있게 보여주고, QR로 현장 입장을 잇는다.

### 사용자·시나리오
- 일반회원: 마이페이지 → 예매 내역(E2, 3상태) → 예매 상세(E3) → 입장 QR(E4)을 스태프에게 제시.
- 비회원: D3 조회 → 예매 상세(G1=E3) → 동일 QR(E4 재활용).
- 취소: E3/G1에서 예매 취소(K3 모달) → 상태 취소.

### 범위 (Scope)
- **In:** 예매 내역 리스트(입금확인중/입장확인/입장완료 3상태), 예매 상세(공연정보+계좌+예매자정보), 예매 취소, 입장용 QR 표시(지류 티켓 스타일), 스태프 확인 버튼.
- **Out:** QR 오프라인 캐싱, 양도/재발급(초기 범위 밖).

### 수용 기준
- [ ] 예매 내역이 3가지 상태로 시각 구분되어 표시된다.
- [ ] 예매 상세에서 공연정보·입금계좌·예매자정보를 확인하고, 가능 상태에서 취소(K3)할 수 있다.
- [ ] 입장확인(입금완료) 상태에서만 유효 QR이 노출된다.
- [ ] 비회원도 G1/E4를 동일하게 사용할 수 있다.

### 필요 데이터
- `Reservation.qrToken`(입장 검증용), 상태값, 연결된 `Performance` 정보.
- 규칙: QR 유효 = 상태 입장확인 && 미입장. 취소 가능 = 입금확인중/입장확인 && 공연 시작 전(정책 확정 필요).

### 비고 / 미결
- 취소 가능 시점(공연 N시간 전 마감 등) 정책 미확정.

## F-05 · 공연 히스토리 & 아카이브

**관련 화면:** E5(공연 히스토리) · [화면정의서 E5](./화면정의서.md#e5-공연-히스토리)

### 목적/배경
관람 완료한 공연을 티켓 컬렉션으로 모아 재방문·소장 동기를 만든다(리텐션). **현재 논의 중** 기능.

### 사용자·시나리오
- 일반회원이 입장완료된 공연을 아카이브에서 다시 보고, 모은 티켓을 감상.

### 범위 (Scope)
- **In:** 관람 완료 공연 아카이브, 티켓 컬렉션 뷰.
- **Out:** 공유/뱃지/SNS 연동(추후).

### 수용 기준
- [ ] 입장완료된 예매가 히스토리에 누적 표시된다.

### 필요 데이터
- `Reservation`(status=입장완료) + `Performance` 조인.

### 비고 / 미결
- **우선순위 중·논의 중**: 범위/디자인 미확정. MVP 후 검토 가능.

## F-06 · 문의 (Q&A)

**관련 화면:** C3(문의하기), E6(내 문의 내역), J1(밴드 문의 관리) · [화면정의서](./화면정의서.md#c3-문의하기)

### 목적/배경
예매·공연 관련 문의를 관객↔밴드 사이에서 처리. 비회원도 문의 가능해야 한다.

### 사용자·시나리오
- 관객/비회원: 문의 작성(종류·내용·공개여부, 비회원은 비밀번호) → E6에서 내 문의·답변 확인.
- 밴드: J1에서 미답변 알림 확인 → 답변 등록.

### 범위 (Scope)
- **In:** 문의 작성(종류/내용/공개여부, 비회원 비밀번호), 내 문의 리스트+상세, 밴드 답변 등록·미답변 알림.
- **Out:** 실시간 채팅, 첨부 다중 파일(초기엔 텍스트 위주).

### 수용 기준
- [ ] 일반/비회원 모두 문의를 작성할 수 있고, 비회원은 비밀번호로 비공개 문의를 보호한다.
- [ ] 작성자는 자신의 문의와 답변 상태를 E6에서 본다.
- [ ] 밴드는 미답변 문의 알림을 보고 답변을 등록한다.

### 필요 데이터
- `Inquiry`(authorType, userId|null, performanceId|null, category, content, isPublic, guestPasswordHash|null, answer, answeredAt).

### 비고 / 미결
- 문의 귀속 대상(서비스 전체 vs 특정 공연/밴드) 정의 필요.

## F-07 · 회원 정보 & 계정 관리

**관련 화면:** E1(마이페이지 메인), F1(회원 정보), F2(회원 정보 수정·탈퇴), J2(밴드 정보), J3(밴드 정보 수정) · [화면정의서 F/J](./화면정의서.md#f-마이페이지--계정)

### 목적/배경
계정 정보 확인/최소 수정/탈퇴. SNS 기반이라 일반회원은 수정 여지가 적고, 밴드는 일부 식별 정보(밴드명·인스타ID)를 임의 변경 불가로 잠근다.

### 사용자·시나리오
- 일반회원: 마이페이지 메인(E1) 허브 → 회원정보(F1) → 거의 없는 수정/로그아웃/탈퇴(F2).
- 밴드: 밴드 정보(J2, 인증상태·로고) → 비번 변경(J3), 밴드명/인스타ID는 문의로만 변경.

### 범위 (Scope)
- **In:** 마이페이지 허브 내비, SNS 기반 정보 표시, 로그아웃, 탈퇴, 밴드 로고 업로드/비번 변경.
- **Out:** 일반회원의 광범위한 프로필 편집(SNS 위탁).

### 수용 기준
- [ ] 일반회원은 정보 확인·로그아웃·탈퇴를 할 수 있다.
- [ ] 밴드는 비번 변경·로고 업로드가 가능하되, 밴드명·인스타ID는 변경 불가(문의 안내)다.

### 필요 데이터
- `User`(nickname, provider), `BandAccount`(bandName, instaId, instaVerifiedStatus, logoUrl, passwordHash).

### 비고 / 미결
- 탈퇴 시 예매/공연 데이터 처리(보존·익명화) 정책 미확정.

## F-08 · 밴드 공연 운영

**관련 화면:** H1(밴드 홈/대시보드), I1(공연 만들기), I2(공연 설정/수정), I3(예매 관리), I4(현장 입장 관리), K4(입금 확인 모달) · [화면정의서 H/I](./화면정의서.md#h-밴드회원--홈대시보드)

### 목적/배경
밴드가 공연을 직접 개설하고, 무통장입금을 수기로 정산하며, 현장 입장을 관리하는 운영의 핵심. 예매 관리·현장 입장이 최상위 우선순위.

### 사용자·시나리오
- 개설: 대시보드(H1)에서 새 공연 개설 → 공연 만들기(I1, 20+ 필드) → 운영.
- 정산: 예매 관리(I3)에서 입금대기/완료를 보고 입금확인(K4) 처리.
- 현장: 입장 관리(I4)에서 QR 스캔으로 입장 처리, 미입장 인원 파악·검색.
- 수정/삭제: I2에서 정보 수정, 단 1매 이상 판매 시 삭제 불가.

### 범위 (Scope)
- **In:** 공연 CRUD(개설/수정/조건부 삭제), 대시보드 공연·상태 목록, 예매자 명단·입금확인 처리, QR 스캔 입장 처리·미입장 표시·검색.
- **Out:** 정산 자동 송금, 다중 스태프 권한 관리(초기엔 밴드 단일 계정), 좌석 관리.

### 수용 기준
- [ ] 밴드는 자신의 공연만 개설·관리할 수 있다(소유권 인가).
- [ ] 공연 만들기에서 포스터·정보·티켓·계좌 등 필수 필드를 검증한다.
- [ ] 1매 이상 판매된 공연은 삭제할 수 없다(수정만 가능).
- [ ] 예매 관리에서 입금대기/완료가 구분되고, 입금확인(K4) 시 예매 상태가 입장확인으로 바뀐다.
- [ ] 현장 입장 관리에서 QR 스캔으로 입장완료 처리되고 미입장 인원이 표시·검색된다.

### 필요 데이터
- `Performance`(밴드 소유, 20+ 필드: 포스터/일시/장소/장르/티켓가/매수/입금계좌/안내 등), `Reservation`(상태·입금정보·qrToken).
- 규칙: 삭제 가능 = `soldQty == 0`. 입금확인 = 밴드가 `Reservation.status: 입금확인중 → 입장확인`. 입장처리 = `입장확인 → 입장완료`(중복 입장 차단).

### 비고 / 미결
- I1의 20+ 필드 전체 목록 확정 필요(별도 필드 정의 표). 스태프 위임(여러 명 입장 처리) 추후.
