# 워크플로우: 기능/페이지 추가 (feature-build)

> 작업 단위 = 페이지/기능 = **브랜치/PR**. 컴포넌트 여러 개 + 라우트를 묶는 **상위 오케스트레이터**.
> 이 문서 하나로 진행한다. 하위 단계에서 필요할 때만 `component-create` · `route-create` 를 연다.
> @참조: `_shared/gates.md` · `_shared/naming-and-structure.md` · `docs/README.md`(문서 지도)
> 추천 스킬(에이전트가 지원하면): 0단계에서 `grill-me`·`to-prd`. 없으면 아래 절차만으로 진행.

## 0. 기능 정의 & 검증 게이트 (빌드 진입 전 — "완벽한 기획" 가정 금지)
> 라우터가 "기능 추가"로 보냈다고 기능이 완성된 게 아니다. **개발 가능 수준이 될 때까지 빌드 진입 금지.**
- **기준점 읽기:** `docs/product/overview.md`(기본 정의)에 비춰 이 기능이 필요/적합한가?
- **정의서 확보:** `docs/specs/<기능>.md` 가 있나? 없거나 부족하면 `docs/specs/_template.md` 양식으로 작성/보완(스킬 있으면 `grill-me`/`to-prd`로 사용자와 합의). 수용기준이 체크 가능해야 한다.
- **모호하면 되묻는다.** 범위·수용기준이 안 잡히면 추측 말고 사용자에게.
- (성숙도가 낮아 기획 자체가 없으면 → `project-kickoff.md` 로 보낸다.)

## 1. 계획 & 쪼개기 (사람 게이트: 설계)
- 기능을 **작업 단위로 분해**한다(예: 회원가입 → env/스키마 → action → 입력 컴포넌트들 → 연동).
- 각 단위가 "컴포넌트(보임)"인지 "라우트/서버(안 보임)"인지 표시 → 어디에 사람 게이트가 필요한지 미리 안다(`_shared/gates.md`).
- **계획 문서(스펙·순서)를 먼저 쓰고**(0단계의 `docs/specs/<기능>.md` 갱신), 사람에게 "이 설계로 진행할까요?" 게이트를 받는다. 통과 전 코드 금지.

## 2. 브랜치
- `feat/<도메인>-<요약>` 브랜치 생성(작업 단위 = 브랜치). worktree 권장.

## 3. 실행 루프 (경계 안은 자율, 경계선에서 게이트)
계획의 각 단위를 순서대로:
- 서버/데이터 단위 → **`route-create.md`** 절차로.
- UI 컴포넌트 단위 → **`component-create.md`** 절차로.
- 각 단위는 **기계 게이트(타입·lint·테스트·렌더) 통과 후** 다음으로. 실패는 사람 안 부르고 고친다.
- 보이는 산출물(컴포넌트/화면)만 **사람 시각 게이트**.

## 4. 통합 & 연동
- 단위들을 라우트에서 조립. 핵심 흐름은 Playwright E2E 1개로 안전망(인증·결제 등).

## 5. 종료 게이트
- `pnpm typecheck && pnpm lint && pnpm test && pnpm build` 통과.
- `feat:` 커밋 → PR. **CI(우회 불가 벽)** 통과 후 머지.

## 하지 말 것
- 계획·설계 게이트 없이 코드부터 시작.
- 한 PR에 여러 기능 섞기(쪼개라).
