# 유사스킬 프롬프트비교 — 비교분석

날짜: 2026-06-09
큰 주제: 프롬프트
참여자: river, kon

---

## river 핵심 정리

세 스킬을 구조적으로 해부하고 **FocusTrack 시뮬레이션**을 직접 실행해 설계도 출력을 비교했습니다.

- **기본 스펙**: grill-me(11줄) · brainstorming(165줄) · office-hours(2,090줄)
- **철학 스펙트럼**: 최소주의(grill-me) → 완전성(brainstorming) → 풍부함(office-hours)
- **설계도 독자상**: office-hours = 창업자 본인 / grill-me = 그 대화에 참여한 개발자 본인 / brainstorming = 이 대화를 보지 못한 다른 개발자
- **구현 준비도**: brainstorming(높음) > grill-me(중간) > office-hours(낮음)
- **결론**: 세 스킬은 "동일한 목적의 다른 구현"이 아니라 "서로 다른 철학을 가진 독립적인 도구"

### river의 설계 교훈 5가지

1. 길이와 품질은 비례하지 않는다
2. 명시적 원칙이 암묵적 원칙보다 일관성이 높다
3. 산출물(문서, git 커밋)이 있는 스킬은 대화가 끝난 후에도 가치를 제공한다
4. 종료 조건의 명확성이 중요하다
5. 사용자의 에너지를 어디에 집중시킬지가 스킬의 가치를 결정한다

## kon 핵심 정리

각 스킬의 실사용 경험을 기반으로 평가하고 **실용적 사용 흐름**을 제안했습니다.

- **한 줄 요약**: brainstorming = "무엇을 만들지" 설계, office-hours = "만들 가치가 있는지" 검증, grill-me = "이 계획이 맞는지" 압박 테스트
- **핵심 통찰**: 하네스(harness)가 적을수록 AI 재량에 더 의존한다
- **office-hours 평가**: "다소 한물간 느낌" — 초기 AI 성능에 맞춰 프롬프트를 길게 작성했지만, 현재는 AI 성능이 향상되어 더 짧게도 같은 효과 가능
- **추천 사용 흐름**: `/office-hours` → `/brainstorming` → `/grill-me` (프로젝트 시작 → 설계 → 파트별 수정 검증)

## 공통점

| 원칙 | office-hours | grill-me | brainstorming |
|------|-------------|----------|---------------|
| 질문은 하나씩 | "ONE AT A TIME" | "one at a time" | "Only one question per message" |
| 구현 전 설계 | HARD GATE | 공유된 이해 전까지 계속 질문 | HARD GATE |
| 대안 탐색 | Phase 4에서 2~3개 필수 | 결정 트리 각 분기 탐색 | "Propose 2-3 approaches" |
| 컨텍스트 파악 먼저 | git log, CLAUDE.md 탐색 | 코드베이스 직접 탐색 | 파일, 문서, 커밋 탐색 |
| 추천 제시 의무 | Recommendation 필드 필수 | "provide your recommended answer" | "Lead with your recommended option" |

## 차이점

| 항목 | office-hours | grill-me | brainstorming |
|------|-------------|----------|---------------|
| 대상 사용자 | 창업자/빌더 (비즈니스 맥락) | 설계가 있는 개발자 | 아이디어가 있는 개발자 |
| 질문 성격 | 심문 — 증거를 요구하고 전제 도전 | 탐정 — 설계 트리를 따라 결정 명시화 | 협력 — 이해를 쌓고 합의 형성 |
| 산출물 | 디자인 문서 + 관계형 클로징 | 없음 (공유된 이해가 결과) | 스펙 문서 + git 커밋 |
| 프롬프트 구조 | 큰 틀 + 단계별 체크 목록 | 틀 없이 하나의 목적으로 깊게 탐구 | 큰 틀 + 단계별 체크 목록 |
| AI 재량 | 낮음 (명시적 규칙이 많음) | 높음 (규칙 3개뿐) | 중간 |
| 외부 의존성 | 높음 (gstack 전용 바이너리) | 없음 | 낮음 (선택적 브라우저 서버) |
| 코드 작성 | 명시적 금지 (HARD GATE) | 명시적 금지 없음 (설계 특성상 코드 불필요) | 명시적 금지 (HARD GATE) |

## 토론 내용

### Q1. grill-me 코드 작성 금지 해석

- **쟁점**: river는 세 스킬 모두 코드 작성이 금지라고 정리했고, kon은 grill-me는 "제한 없음 (탐색만 언급)"이라고 기록했다.
- **river**: 코드 작성 금지 조항은 없지만, 반복적 질문이 원칙이고 "계획" 위주의 스킬이라는 맥락에서 다른 스킬들과 같은 선상으로 분류했다.
- **결론**: 원문 기준으로는 kon의 해석이 더 정확하다. grill-me에는 명시적 코드 작성 금지가 없다. 단, 스킬의 성격상 코드 작성이 거의 발생하지 않는다.

### Q2. office-hours "한물갔다" 평가

- **kon의 근거**: 초기 AI 성능을 보완하기 위해 2,000줄이 필요했지만, 현재 AI 성능 향상으로 더 짧게도 가능하다.
- **분석**: 기술적 구현(gstack 바이너리, 외부 의존성)은 타당히 "구식" 느낌이다. 그러나 YC 6개 핵심 질문 프레임워크와 반시오판티즘 철학은 지금도 유효하다.
- **결론**: "한물간 구현, 유효한 철학" — 구현은 업데이트가 필요하지만 방법론 자체는 시대를 타지 않는다.

### Q3. 하네스 복잡도와 AI 재량

- **kon의 통찰**: 하네스가 적을수록 AI 재량에 더 의존한다.
- **river의 확인**: 시뮬레이션에서 quality 차이보다는 **구조적 차이**를 느꼈다. office-hours/brainstorming은 큰 틀 안에서 아이디어를 조각조각 탐구하는 반면, grill-me는 틀 없이 하나의 목적으로 깊게 탐구하는 느낌이었다.
- **결론**: 하네스가 많다 = 넓게 체크한다. 하네스가 적다 = 하나를 깊게 판다.

### Q4. 설계도의 독자상

- **river의 발견**: 동일 프로젝트(FocusTrack)임에도 세 스킬이 만든 설계도는 서로 다른 독자를 대상으로 한다.
- **kon**: 실사용 당시에는 이 관점을 의식하지 않았다.
- **공동 인식**: "이 문서를 누가 읽을 것인가"를 먼저 결정하면 스킬 선택이 명확해진다.

## 공동 결론

### 선택 기준

| 상황 | 추천 스킬 | 이유 |
|------|---------|------|
| 아이디어의 가치와 방향을 확인하고 싶다 | `/office-hours` | YC 방식의 비즈니스 검증, 가장 냉혹한 평가 |
| 팀원에게 넘길 수 있는 완성된 스펙이 필요하다 | `/brainstorming` | 다른 개발자도 이해하는 구현 준비 문서 생성 |
| 이미 설계가 있고, 기술 결정을 빠르게 점검하고 싶다 | `/grill-me` | 부담 없이 꺼내 쓸 수 있는 압박 테스트 |

### 이상적인 사용 흐름

```
/office-hours    →   "이것을 만들어야 하는가?" 검증
      ↓
/brainstorming   →   "무엇을 어떻게 만들 것인가?" 설계
      ↓
/grill-me        →   수정 발생 시 파트별 빠른 설계 점검
```

### 핵심 인사이트

> **"하네스가 많을수록 넓게 체크한다. 하네스가 적을수록 하나를 깊게 판다."**

세 스킬은 경쟁 관계가 아니라 상호 보완적이며, 프로젝트의 단계와 목적에 따라 선택하는 것이 중요하다.
