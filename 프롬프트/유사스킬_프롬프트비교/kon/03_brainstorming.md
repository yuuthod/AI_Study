# superpowers: /brainstorming

- 출처: https://github.com/obra/superpowers
- 위치: `skills/brainstorming`

## 목적

창의적 작업(기능 추가, 컴포넌트 빌드, 동작 수정 등)을 시작하기 전에 아이디어를 완성된 설계와 스펙으로 변환하는 협업 대화 스킬.

## 핵심 규칙

> **HARD-GATE**: 설계를 제시하고 사용자의 승인을 받기 전까지 코드를 작성하거나 어떤 구현 행동도 취해서는 안 된다. 아무리 간단한 프로젝트라도 예외 없음.

## 9단계 체크리스트

```
┌──────┬─────────────────────────────────────────────────────────┐
│ 단계 │                          내용                           │
├──────┼─────────────────────────────────────────────────────────┤
│ 1    │ 프로젝트 컨텍스트 탐색 (파일, 문서, 최근 커밋)          │
├──────┼─────────────────────────────────────────────────────────┤
│ 2    │ 비주얼 컴패니언 제공 (시각적 질문이 필요한 경우)        │
├──────┼─────────────────────────────────────────────────────────┤
│ 3    │ 명확화 질문 — 한 번에 하나씩                            │
├──────┼─────────────────────────────────────────────────────────┤
│ 4    │ 2-3가지 접근 방법 + 트레이드오프 + 추천 제시            │
├──────┼─────────────────────────────────────────────────────────┤
│ 5    │ 설계 제시 → 사용자 승인                                 │
├──────┼─────────────────────────────────────────────────────────┤
│ 6    │ 설계 문서 작성                                          │
│      │ (docs/superpowers/specs/YYYY-MM-DD-<topic>-design.md)   │
├──────┼─────────────────────────────────────────────────────────┤
│ 7    │ 스펙 자체 검토 (placeholder, 모순, 모호성 확인)         │
├──────┼─────────────────────────────────────────────────────────┤
│ 8    │ 사용자의 스펙 검토 요청                                 │
├──────┼─────────────────────────────────────────────────────────┤
│ 9    │ writing-plans 스킬로 전환                               │
└──────┴─────────────────────────────────────────────────────────┘
```

## 주요 원칙

- 질문은 한 번에 하나 — 여러 질문을 동시에 하지 않음
- YAGNI 철저히 적용 — 불필요한 기능 제거
- 항상 2-3가지 대안 탐색 후 결정
- 터미널 종착지는 writing-plans 스킬 — 다른 구현 스킬 직접 호출 금지

## 비주얼 컴패니언

로컬 브라우저 기반 시각화 도구로, UI 목업·다이어그램·레이아웃 비교 등을 보여줄 수 있음. 사용자 동의 후에만 활성화되며, 모든 질문에 사용하는 게 아니라 "보는 게 읽는 것보다 나은 경우"에만 사용.
