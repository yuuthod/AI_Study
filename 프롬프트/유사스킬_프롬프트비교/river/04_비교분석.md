## 2. 철학적 접근 비교

### 문제를 다루는 방식

```
/office-hours
  "문제가 올바른지 검증하라"
  → 솔루션 전에 수요, 현재상태, 타겟을 증명

/grill-me  
  "계획의 모든 결정을 명시화하라"
  → 이미 있는 계획의 빈틈을 드러냄

/brainstorming
  "아이디어를 설계로 완성하라"
  → 막연한 아이디어에서 구현 가능한 스펙까지
```

### 사용자와의 관계

| 스킬 | AI의 역할 | 사용자의 역할 |
|------|-----------|--------------|
| `/office-hours` | 엄격한 파트너 (판사형) | 답변하고 검증받는 창업자 |
| `/grill-me` | 탐정형 인터뷰어 + 추천자 | 검증이 필요한 설계자 |
| `/brainstorming` | 협업적 설계 파트너 | 아이디어를 가진 개발자 |

## 3. 질문 방식 비교

### 공통점
세 스킬 모두 **"질문은 하나씩"** 원칙을 따름.

### 차이점

**`/office-hours`의 질문 방식**
- 6개의 정해진 강제 질문 (Startup 모드)
- 각 질문에 명시적인 **"푸시 패턴"** 존재
- 첫 답변을 믿지 않고 반드시 한 번 더 파고듦
- 모드별 스마트 라우팅으로 질문 세트 최적화
- 질문에 Anti-sycophancy[^1] 규칙 명시

**`/grill-me`의 질문 방식**
- 정해진 질문 없음 — AI가 설계 트리를 탐색하며 자유롭게 생성
- 각 질문에 **AI의 추천 답** 함께 제시
- 코드베이스로 답할 수 있으면 질문 대신 **직접 탐색**

**`/brainstorming`의 질문 방식**
- 정해진 질문 없음 — 목적/제약/성공 기준에 집중
- **객관식** 질문 선호 (열린 질문보다 답하기 쉬움)
- 스코프가 너무 크면 즉시 분해[^2] 제안

## 4. 구조적 깊이 비교

### `/office-hours` — 피라미드 구조

```
Phase 1:  맥락 파악 (코드베이스 탐색)
    ↓
Phase 2A/2B: 핵심 질문 (모드별)
    ↓
Phase 2.5: 관련 디자인 발견
    ↓
Phase 2.75: 시장 환경 조사 (WebSearch)
    ↓
Phase 3: 전제 도전
    ↓
Phase 3.5: 크로스 모델 2차 의견
    ↓
Phase 4: 대안 생성 (필수)
    ↓
Phase 4.5: 창업자 시그널 종합
    ↓
Phase 5: 디자인 문서 작성
    ↓
Phase 6: 관계형 클로징 (티어별)
```

복잡성의 이유: YC 오피스 아워 경험을 **완전히 재현**하려는 야심찬 목표

### `/grill-me` — 선형 구조

```
계획/설계 입력 → 집요한 질문 → 공유된 이해
(설계 트리를 따라 분기하되, 전체는 단순한 루프)
```

복잡성이 낮은 이유: "무엇을 할지"만 정의하고 "어떻게 할지"는 AI에게 위임

### `/brainstorming` — 체크리스트 구조

```
1 → 2 → 3 → 4 → 5 → 6 → 7 → 8 → 9
(선형이지만 각 단계에서 승인 게이트 존재)
```

## 5. 산출물 비교

### `/office-hours`의 산출물 (디자인 문서)

```markdown
# 섹션 예시 (Startup 모드)
- 문제 진술
- 수요 증거
- 현재 상태
- 타겟 사용자 & 가장 좁은 쐐기
- 제약 조건
- 전제들
- 검토된 접근법들
- 권장 접근법
- 성공 기준
- 배포 계획
- The Assignment (다음에 할 행동 1개)
- "What I noticed about how you think" (AI의 관찰)
```

저장 위치: `~/.gstack/projects/{slug}/`

### `/grill-me`의 산출물

없음. 대화 자체가 결과물. 공유된 이해가 유일한 목표.

### `/brainstorming`의 산출물 (스펙 문서)

```markdown
# 섹션 예시
- 아키텍처
- 컴포넌트
- 데이터 플로우
- 에러 처리
- 테스팅
```

저장 위치: `docs/superpowers/specs/YYYY-MM-DD-{topic}-design.md` (git 커밋 포함)

## 8. 진입 장벽 비교

### 사용자 관점

```
/grill-me
  가장 낮음 — "grill me"라고 말하면 AI가 알아서 진행
  
/brainstorming
  낮음 — 체크리스트를 따라가면 됨, 설명이 명확
  
/office-hours
  높음 — 어떤 모드로 진행할지 선택해야 하고, 
         6개의 날카로운 질문에 구체적인 답을 해야 함
```

### AI 작성자 관점

```
/grill-me
  가장 낮음 — 규칙 3개면 충분

/brainstorming
  중간 — 체계적 구조 + 명확한 게이트 필요

/office-hours  
  매우 높음 — 10개 이상의 Phase, 텔레메트리, 
               프로파일 시스템 등 복잡한 인프라 필요
```

## 9. 적합한 사용 시나리오 비교

### 시나리오 1: 막연한 아이디어가 있을 때

```
최적: /brainstorming
  → 아이디어를 구체적 스펙으로 만들어줌
  
차선: /office-hours (Builder 모드)
  → 아이디어를 가장 멋진 버전으로 발전

부적합: /grill-me
  → 이미 계획이 있어야 질문할 수 있음
```

### 시나리오 2: 스타트업 아이디어를 검증하고 싶을 때

```
최적: /office-hours (Startup 모드)
  → YC 파트너 수준의 날카로운 검증

차선: /grill-me
  → 계획의 논리적 빈틈을 찾을 수 있음

부적합: /brainstorming
  → 비즈니스 검증보다 기술 설계에 집중
```

### 시나리오 3: 이미 만들 것을 알고 있고, 기술 설계만 점검하고 싶을 때

```
최적: /grill-me
  → 설계 결정을 빠르게 점검
  
차선: /brainstorming
  → 더 체계적이지만 더 오래 걸림
  
부적합: /office-hours
  → 비즈니스 검증에 집중되어 있어 오버킬[^4]
```

## 10. 설계 철학 스펙트럼

```
                 간결함                          완결성
                  ←─────────────────────────────────→
                  
     /grill-me ──────── /brainstorming ──────── /office-hours

     11줄            165줄               2,090줄
     규칙 3개       9단계 체크리스트      10+ Phase
     대화가 결과     스펙 문서가 결과      디자인 문서 + 관계가 결과
```

세 스킬은 **동일한 목적의 다른 구현**이 아니라, **서로 다른 철학을 가진 독립적인 도구**입니다.

---

[^1]: **Anti-sycophancy (반시오판티즘)**: AI가 사용자가 듣고 싶어하는 말만 하는 경향을 방지하는 원칙. 동의 대신 비판적이고 솔직한 평가를 제공.
[^2]: **분해(Decomposition)**: 복잡한 시스템을 독립적으로 관리 가능한 작은 단위로 나누는 것.
[^3]: **지속성(Persistence)**: 세션이 끝난 후에도 데이터가 유지되는 성질. 여기서는 스킬 실행 기록, 학습, 프로파일 등이 다음 세션에 활용되는 것.
[^4]: **오버킬(Overkill)**: 필요 이상의 과도한 수단을 사용하는 것. 간단한 문제에 너무 복잡한 도구를 쓰는 경우.
