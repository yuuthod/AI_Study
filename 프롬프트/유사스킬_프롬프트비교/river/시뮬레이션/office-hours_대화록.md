### 빌더 Q1 — 가장 멋진 버전

**D2 — 이것의 가장 멋진 버전은 무엇인가요?**

> ELI10: 지금 생각하는 앱의 기본 기능(시간 추적 + 분류)을 넘어서, 이 앱이 진짜 "와우!"를 만들어내려면 무엇이 있어야 할까요?  
> 지금 떠오르는 것 이상을 탐색해 봅시다 — 단순한 타이머가 아니라, 어떤 앱이 되면 사람들이 친구에게 "이거 써봐"라고 말할까요?

A) 단순 추적기 — 시간 기록하고 목록 보여주는 것  
B) 시각적 생산성 대시보드 — 예쁜 차트, 하루 흐름이 한눈에 보임  
C) 행동 코치 — 비생산적 시간이 길어지면 알림 + 동기 부여 메시지

**👤 사용자 답변:**
B인데, 거기다가 알림도 있었으면 좋겠어. 하루가 끝날 때 "오늘 생산적인 시간 6시간, 비생산적 2시간" 이런 거 보고 싶고. 차트는 진짜 예뻤으면 좋겠어. 그리고 트레이에 아이콘 있어서 간단히 확인할 수 있으면 좋겠어.

> 오, 좋아요. 차트가 예뻐야 한다는 게 핵심이네요 — 단순히 "동작하는" 앱이 아니라 **보고 싶어지는** 앱을 원하시는군요. 시스템 트레이에서 일일 스냅샷을 보고, 클릭하면 예쁜 대시보드가 열리는 것 — 거기서 주간 흐름을 볼 수 있다면 그게 "와우"입니다.

### 빌더 Q2 — 누구에게 보여줄 건가요?

**D3 — 완성되면 누구에게 먼저 보여주고 싶은가요?**

> ELI10: "누구에게 보여주는가"가 UI/UX의 방향을 결정합니다. 개발자 친구에게 보여주는 거라면 GitHub 링크 + CLI 옵션도 좋고, 일반인에게 보여주는 거라면 설치 쉽고 직관적이어야 합니다.

A) 나 자신 — 진짜 내가 쓸 도구  
B) 개발자 친구들 — GitHub 오픈소스로 공유  
C) 생산성에 관심 있는 일반인 — Product Hunt 배포

**👤 사용자 답변:**
일단 나 자신. 그다음에 개발자 친구들한테 보여주고 싶고, 반응 좋으면 Product Hunt도 올려볼까 해.

> 완벽한 순서예요. 본인이 매일 쓰면서 "이게 빠졌네", "이건 거슬리네"를 자연스럽게 발견하게 됩니다. 그게 개발자 친구들한테 보여줄 때 훨씬 설득력 있는 시연이 됩니다.

### 빌더 Q3 — 기존 도구와의 차별점

**D4 — RescueTime, ActivityWatch 같은 도구를 알고 있나요? 이것들과 어떻게 다른가요?**

> ELI10: 비슷한 도구가 이미 존재한다는 것을 알면서도 새로 만드는 이유가 있을 것입니다. 그 이유가 설계 방향을 결정합니다.  
> 만약 차별점이 없다면 기존 도구를 쓰는 게 낫지만, 분명히 "이게 없어서 불편했다"는 포인트가 있을 겁니다.

**👤 사용자 답변:**
RescueTime은 유료고 복잡해. ActivityWatch는 오픈소스인데 UI가 좀 투박해. 나는 코딩 관련 사이트(Codex, ChatGPT, GitHub)를 생산적으로 분류하는 게 기본으로 들어간, 개발자 특화 미니멀 앱을 원해. 설치하면 바로 쓸 수 있는 것.

> 정확히요. "개발자 기본값이 맞게 설정된 미니멀한 앱" — 그게 이 앱의 포지셔닝입니다. ActivityWatch는 너무 범용이라 개발자가 쓰려면 설정에 30분 써야 해요. 이 앱은 설치하면 GitHub, VS Code, ChatGPT가 이미 생산적으로 분류돼 있는 것.

## Phase 4: 대안 생성

**D8 — 구현 접근법을 선택해 주세요**

> Project: FocusTrack (Windows → Mac 데스크탑 생산성 추적기)  
> ELI10: 어떤 기술로 만들지를 결정합니다. 세 가지 방향이 있으며, 각각 개발 속도, 성능, Mac 이식성에서 트레이드오프가 있습니다.  
> Recommendation: A — Electron + TypeScript because Mac 출시 목표와 개인 사용 시작에 가장 균형이 좋습니다.  
> Note: options differ in kind, not coverage — no completeness score.

---

**APPROACH A: Electron + TypeScript + React (추천)**
- **요약**: Chromium 기반 크로스플랫폼 앱. React로 UI, TypeScript로 로직, N-API 모듈로 Windows 네이티브 기능 연동
- **노력**: M (human: 2~3주 / solo: 3~4일 집중)
- **위험**: 낮음
- ✅ Mac 이식이 네이티브 모듈 교체만으로 가능
- ✅ React 생태계로 예쁜 차트 구현 쉬움 (Recharts, Victory)
- ✅ `electron-builder`로 인스톨러 자동 생성
- ❌ 메모리 사용량이 네이티브보다 높음 (약 150-200MB, Chromium 포함)
- ❌ 앱 크기가 큼 (약 80-150MB 인스톨러)

---

**APPROACH B: WPF / WinUI 3 (Windows 네이티브)**
- **요약**: C# + XAML로 Windows 전용 네이티브 앱. 성능 최적, UI Automation 연동 직접적
- **노력**: M (human: 3~4주 / solo: 1주)
- **위험**: 중간
- ✅ 네이티브 성능, 메모리 사용량 최소
- ✅ Windows UI Automation 연동이 가장 자연스러움
- ❌ Mac 지원 불가 — 나중에 Mac 버전 처음부터 다시 작성 필요
- ❌ C# 경험 없으면 학습 곡선 높음

---

**APPROACH C: Python 백엔드 + Electron 프론트엔드**
- **요약**: 추적 로직은 Python, UI는 Electron. IPC로 통신
- **노력**: L (human: 4~5주 / solo: 1~2주)
- **위험**: 높음
- ✅ Python으로 추적 로직 구현이 빠름 (`pygetwindow`, `uiautomation`)
- ✅ 기존 Python 실력 활용 가능
- ❌ 두 프로세스 간 IPC 복잡성 추가
- ❌ 배포 시 Python 런타임 번들링 문제
- ❌ Mac 이식 시 Python 코드도 수정 필요

**Net**: Electron은 Mac을 염두에 둔 설계에서 가장 자연스러운 선택입니다. WPF는 성능이 좋지만 Mac 계획을 포기해야 합니다. Python 조합은 초기 빠르지만 유지보수 부채가 큽니다.

**👤 사용자 답변:**
A로 가자. Mac도 해야 하니까.
