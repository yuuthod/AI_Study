## Step 3: 명확화 질문

---

### 질문 1 — 앱의 주 목적

앱의 주 목적이 무엇인가요?

A) **실시간 모니터링** — 지금 비생산적인 걸 하고 있다고 즉시 알려줌  
B) **사후 분석** — 하루/주 단위로 돌아보며 패턴 파악  
C) **둘 다** — 실시간 경고 + 사후 리포트

**👤 사용자 답변:**
C. 둘 다. 실시간으로도 알려주고, 하루 마감에 요약도 보고 싶어.

---

### 질문 2 — 추적 범위

어떤 것을 추적할 건가요?

A) **브라우저 탭만** — URL 기반으로 사이트만 분류  
B) **브라우저 + 데스크탑 앱** — VS Code, Figma, Steam 같은 앱 이름도 포함  
C) **특정 앱 목록만** — 사용자가 지정한 앱들만

**👤 사용자 답변:**
B. 브라우저 URL이랑 앱 이름 다 추적하고 싶어. VS Code는 생산적, Steam은 비생산적.

---

### 질문 3 — 분류 기준 설정 방식

생산적/비생산적 분류 기준을 어떻게 관리할까요?

A) **완전 수동** — 사용자가 처음부터 다 등록  
B) **기본 목록 제공 + 수정 가능** — 미리 정해진 목록이 있고 추가/제거 가능  
C) **AI 자동 분류** — URL이나 앱 이름을 보고 AI가 자동으로 판단

**👤 사용자 답변:**
B. 기본 목록 있고 수정 가능하게. 기본으로 GitHub, VS Code, ChatGPT는 생산적으로, YouTube나 Instagram은 비생산적으로 넣어줘.

---

### 질문 4 — 앱 실행 방식

앱이 어떻게 실행되어야 할까요?

A) **항상 백그라운드 실행** — 시스템 시작 시 자동 실행, 트레이 상주  
B) **수동으로 켜고 끄기** — 추적하고 싶을 때만 실행  
C) **스케줄 실행** — 업무 시간(예: 9-18시)에만 자동 실행

**👤 사용자 답변:**
A. 항상 백그라운드에서. 신경 안 쓰고 싶어.

---

### 질문 5 — 배포 목적

이 앱을 혼자만 쓸 건가요, 다른 사람들과 공유할 예정인가요?

A) **개인 사용만** — 배포 계획 없음  
B) **오픈소스 공유** — GitHub에 올리고 개발자들이 직접 빌드  
C) **배포 앱으로 출시** — 인스톨러 제공, 일반 사용자도 쓸 수 있게

**👤 사용자 답변:**

## Step 4: 2~3가지 접근법 제안

지금까지 파악한 요구사항을 바탕으로 세 가지 구현 방향을 제안합니다. 제 추천은 **A번**입니다.

---

### Approach A: Electron + TypeScript + React ✅ 추천

**왜 추천하는가**: Mac 출시 목표가 있고, 예쁜 대시보드 UI가 중요하다면 Electron이 가장 균형 잡힌 선택입니다. React 생태계의 차트 라이브러리(Recharts, Victory)로 시각적으로 완성도 높은 UI를 만들 수 있고, `electron-builder`로 Windows/Mac 인스톨러를 동시에 만들 수 있습니다.

| | |
|-|-|
| **노력** | 중간 (solo 기준 약 1~2주 집중) |
| **위험** | 낮음 |
| ✅ | Mac 이식이 네이티브 모듈 교체만으로 가능 |
| ✅ | React로 예쁜 차트 구현 용이 |
| ✅ | electron-builder로 인스톨러 자동 생성 |
| ❌ | 메모리 사용량 높음 (~150-200MB) |
| ❌ | 앱 용량이 큼 (~100MB 인스톨러) |

---

### Approach B: WPF / WinUI 3 (Windows 전용 네이티브)

**언제 선택하는가**: 성능이 최우선이고 Mac 계획이 없을 때.

| | |
|-|-|
| **노력** | 중간 (C# 숙련도에 따라 다름) |
| **위험** | 중간 |
| ✅ | 네이티브 성능, 메모리 최소 |
| ✅ | Windows UI Automation 연동 직접적 |
| ❌ | Mac 지원 불가 — 나중에 처음부터 다시 작성 필요 |
| ❌ | C# 학습 곡선 |

---

### Approach C: Python + Electron (하이브리드)

**언제 선택하는가**: 추적 로직을 Python으로 빠르게 검증하고 싶을 때.

| | |
|-|-|
| **노력** | 큼 (두 언어 + IPC 복잡성) |
| **위험** | 높음 |
| ✅ | Python 추적 라이브러리 풍부 (`uiautomation`, `pygetwindow`) |
| ❌ | 두 프로세스 간 IPC 복잡성 |
| ❌ | Python 런타임 번들링 문제 |

**👤 사용자 답변:**
A로 가자. Mac도 해야 하고 TypeScript 써봤어.

## Step 5: 설계 제시 (섹션별 확인)

### 5-1. 전체 아키텍처

```
Electron Main Process (Node.js)
├── PlatformTrackerService 인터페이스
│   └── WindowsTrackerService
│       ├── SetWinEventHook — 활성 창 변경 감지
│       └── UI Automation API — 브라우저 현재 URL 읽기
├── TrackingEngine
│   ├── 1초마다 활성 앱/URL 확인
│   └── 5초 이상 동일 항목 → 세션 DB에 기록
├── CategoryService
│   └── categories.json 기반 생산적/비생산적 판별
├── SQLiteStore
│   └── better-sqlite3 → %APPDATA%/focustrack/data.db
├── NotificationService
│   ├── 임계값 초과 토스트 알림
│   └── 일일 요약 (node-cron)
└── TrayManager — 오늘 요약 툴팁, 대시보드 열기

Renderer Process (React + TypeScript)
├── DashboardWindow
│   ├── 오늘 통계 카드 (생산적/비생산적/중립 시간)
│   ├── 시간별 활동 흐름 차트 (Recharts)
│   ├── 상위 앱/사이트 목록
│   └── 카테고리 관리 탭
└── SettingsPage
    ├── 알림 임계값
    ├── 일일 요약 시간
    └── 데이터 보존 기간
```

이 아키텍처 방향이 맞아 보이나요?

**👤 사용자 답변:**
좋아. `PlatformTrackerService` 추상화가 Mac 대응에 중요하겠네.

---

### 5-2. 데이터 플로우

```
활성 창 변경 이벤트
    ↓
WindowsTrackerService.getActiveWindow()
    ↓
앱 이름 + URL (브라우저인 경우) 수집
    ↓
CategoryService.classify(appName, url)
    ↓ productive | unproductive | neutral
TrackingEngine — 5초 유지 시 세션 시작
    ↓
SQLiteStore.saveSession(...)
    ↓
NotificationService — 임계값 확인
    ↓ 초과 시
Windows 토스트 알림
```

**👤 사용자 답변:**
5초 기준이 왜 5초야?

> 마우스를 잠깐 다른 창으로 옮기거나, Alt+Tab으로 짧게 왔다 갔다 할 때 의미 없는 1~2초짜리 세션이 많이 생깁니다. 5초 이상 집중한 것만 기록하면 노이즈가 줄어듭니다. 설정에서 조절 가능하게 만들게요.

**👤 사용자 답변:**
그렇군. 맞아, 5초로 하자.

---

### 5-3. 에러 처리

- **UI Automation 실패**: Firefox 등 일부 브라우저에서 URL 읽기 실패 시 앱 이름으로만 기록 (무결성 유지)
- **DB 잠금**: 동시 접근 오류 시 재시도 로직 (better-sqlite3의 WAL 모드 사용)
- **트레이 아이콘 클릭 → 앱 없음**: 메인 프로세스 충돌 시 자동 재시작 (`electron-squirrel-startup`)
- **카테고리 파일 손상**: 기본값으로 폴백, 경고 알림

**👤 사용자 답변:**
좋아. Firefox 부분적 지원은 일단 그렇게 처리하자.

---

### 5-4. 테스팅 전략

- **Unit**: CategoryService 분류 로직 (Vitest)
- **Integration**: TrackingEngine + SQLiteStore (실제 DB 사용, 인메모리 없이)
- **E2E**: Playwright for Electron (대시보드 렌더링, 데이터 표시 확인)
- **수동 테스트**: 실제 Chrome에서 YouTube → GitHub 전환 시 분류 확인

**👤 사용자 답변:**
테스팅은 일단 Unit이랑 Integration만 해도 될 것 같아.

> 네, MVP 단계에서는 충분합니다. E2E는 나중에 추가 가능합니다.
