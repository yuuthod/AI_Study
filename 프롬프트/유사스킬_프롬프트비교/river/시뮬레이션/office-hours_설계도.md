## Problem Statement

개발자들이 하루 중 실제로 생산적인 작업에 얼마나 시간을 쓰는지 파악하기 어렵다. 기존 도구(RescueTime, ActivityWatch)는 너무 복잡하거나, 개발자 워크플로우에 맞는 기본값이 없다. 설치 후 즉시 사용할 수 있고, 개발자 기본 카테고리(GitHub, VS Code, ChatGPT = 생산적)가 미리 설정된 미니멀한 도구가 없다.

---

## What Makes This Cool

- **설치하면 바로 쓸 수 있는 개발자 기본값**: GitHub, VS Code, ChatGPT, Codex가 기본으로 생산적으로 분류됨
- **시스템 트레이에서 오늘 요약 한눈에**: 클릭 한 번으로 하루 생산성 스냅샷
- **예쁜 차트**: 보고 싶어지는 대시보드 — 하루의 흐름이 시각적으로 보임
- **거슬리지 않는 추적**: 별도 설정 없이 백그라운드에서 조용히 실행

---

## Constraints

- Windows 우선 출시, Mac 추후 지원
- 개인 사용 → 오픈소스 공유 → Product Hunt 순서
- 로컬 데이터만 (클라우드는 팀 버전 시 고려)
- Chrome과 Edge 지원 우선, Firefox는 부분적

---

## Premises

1. Windows UI Automation API로 Chrome, Edge의 현재 탭 URL을 읽을 수 있다
2. Electron으로 만들면 Mac 이식 시 네이티브 모듈만 교체하면 된다
3. 개발자 기본 카테고리 목록이 이 앱의 핵심 차별점이다
4. 초기에는 로컬 SQLite만으로 충분하다

---

## Approaches Considered

### Approach A: Electron + TypeScript + React ✅ 선택됨

- 크로스플랫폼 우선, React로 예쁜 차트 구현
- Mac 이식 시 네이티브 모듈만 교체
- 메모리 사용량이 높지만 (150-200MB) 허용 가능

### Approach B: WPF / WinUI 3

- 네이티브 성능 최적
- Mac 지원 불가 — 사용자 요구사항과 충돌

### Approach C: Python 백엔드 + Electron UI

- IPC 복잡성, 배포 번들링 문제로 유지보수 부채 큼

---

## Recommended Approach

**Electron + TypeScript + React**

Mac 출시 목표와 예쁜 UI 요건을 모두 충족하는 유일한 옵션. Recharts 또는 Victory로 차트 구현, `electron-builder`로 Windows 인스톨러 자동 생성.

## 아키텍처 개요

```
Electron Main Process
├── PlatformTrackerService (인터페이스)
│   └── WindowsTrackerService
│       ├── SetWinEventHook (활성 창 감지)
│       └── UI Automation (브라우저 URL)
├── TrackingEngine (1초 폴링, 5초 이상 → DB 기록)
├── CategoryService (categories.json)
├── SQLiteStore (%APPDATA%/focustrack/data.db)
├── NotificationService (토스트 + 일일 요약)
└── TrayManager

Electron Renderer (React)
├── DashboardWindow
│   ├── 오늘 통계 (생산적/비생산적 시간)
│   ├── 주간 차트 (Recharts)
│   └── 카테고리 관리
└── SettingsWindow
```

## 핵심 데이터 모델

```sql
CREATE TABLE sessions (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  app_name TEXT NOT NULL,
  url TEXT,
  category TEXT NOT NULL,  -- "productive" | "unproductive" | "neutral"
  started_at INTEGER NOT NULL,
  ended_at INTEGER NOT NULL,
  duration_ms INTEGER NOT NULL
);
```

## What I noticed about how you think

- "차트가 예뻐야 한다"고 기능보다 경험을 먼저 언급했습니다 — 사용자 경험에 민감한 개발자입니다.

- "일단 나 자신"이라고 했지만 Product Hunt까지 이미 생각하고 있었습니다 — 자신이 진짜 사용자인 것이 이 앱의 가장 큰 강점입니다. 본인이 매일 불편함을 느끼면서 고치면 그게 가장 좋은 QA입니다.
