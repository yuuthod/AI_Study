## 3. 섹션별 깊이 비교

### 아키텍처 섹션

세 설계도 모두 아키텍처를 포함하지만, **표현 방식과 깊이**가 다릅니다.

**office-hours — 개요 수준**
```
개발자가 읽고 "무엇을 만드는지" 이해하는 데 집중.
PlatformTrackerService 추상화의 존재만 언급.
파일 구조 없음.
```

**grill-me — 결정 중심**
```
각 컴포넌트가 왜 그렇게 결정됐는지 대화에서 추적 가능.
단일 프로세스로 간 이유, Electron 선택 이유가 설계도에 반영됨.
파일 구조 없음.
```

**brainstorming — 구현 준비 수준**
```
실제 파일 트리(src/main/platform/, src/renderer/ 등) 포함.
TypeScript 인터페이스 정의 완전 작성.
→ 이 섹션만 보고 코드 작성 시작 가능.
```

---

### 데이터 모델 섹션

**office-hours**
```sql
-- 언급 수준: "sessions 테이블 있음" 정도
CREATE TABLE sessions (
  id, app_name, url, category, started_at, ended_at, duration_ms
);
```
인덱스 없음. 설정 테이블 없음.

**grill-me**
```sql
-- 동일 수준이지만 저장 경로 명시
-- %APPDATA%/focustrack/data.db
CREATE TABLE sessions (...);
CREATE TABLE category_rules (...);
```
인덱스 없음.

**brainstorming**
```sql
-- 가장 완전
CREATE TABLE sessions (...);
CREATE INDEX idx_sessions_started_at ON sessions(started_at);
CREATE INDEX idx_sessions_category ON sessions(category);
CREATE TABLE category_rules (...);
CREATE TABLE settings (key TEXT PRIMARY KEY, value TEXT NOT NULL);
```
인덱스, settings 테이블까지 포함. 구현 시 그대로 사용 가능.

### 고유 섹션 비교 (다른 두 스킬에 없는 것)

**office-hours만 있는 섹션**:

> **"What Makes This Cool"**
> - 차트가 예뻐야 한다
> - 설치하면 바로 쓸 수 있는 개발자 기본값
> - 거슬리지 않는 추적

→ 기능 목록이 아닌 **제품의 감성**을 기록. 이후 UI/UX 결정 시 기준이 됨.

> **"The Assignment"**
> → Electron + TypeScript 세팅 후 Chrome URL을 콘솔에 출력하는 프로토타입

→ 설계도를 읽은 사람이 **지금 당장 무엇을 해야 하는지** 명시. 다른 두 스킬에 없는 행동 촉구.

> **"What I noticed about how you think"**
> - "차트가 예뻐야 한다"고 먼저 말했습니다 — 경험을 먼저 생각하는 사람
> - RescueTime, ActivityWatch를 이미 알고 시작했습니다

→ 설계 결정이 아닌 **빌더 심리 기록**. 이후 세션에서 이 사람의 성향을 파악하는 데 활용됨.

---

**grill-me만 있는 섹션**:

> **기술 스택 테이블**
> | 레이어 | 선택 | 이유 |
> |--------|------|------|
> | 프레임워크 | Electron | 크로스플랫폼 |
> | DB | SQLite | 로컬, 빠른 집계 |

→ "무엇을 선택했는가"와 "왜 선택했는가"를 명시적으로 연결. 설계도에 **결정 근거**가 남음.

---

**brainstorming만 있는 섹션**:

> **파일 트리 (File Structure)**
> ```
> src/main/platform/PlatformTrackerService.ts
> src/main/platform/WindowsTrackerService.ts
> src/renderer/components/Dashboard/
> ```

> **TypeScript 인터페이스 전문**
> ```typescript
> interface PlatformTrackerService { ... }
> interface ActiveWindowInfo { ... }
> interface TrackingSession { ... }
> ```

> **UI 명세 섹션**
> - 트레이 아이콘 툴팁 형식
> - 대시보드 각 섹션 명세
> - 설정 페이지 항목 목록

> **테스팅 전략**
> - Unit, Integration, E2E 각각의 범위

## 4. 독자(Audience) 분석

설계도를 누가 읽을 것인지를 가정하면 각 스킬의 성격이 명확해집니다.

### office-hours 설계도의 독자

**→ 제품을 만들기로 결심한 창업자/빌더 본인**

설계도를 읽으면 "무엇을 만들고 왜 만드는가"는 명확하지만, 개발자를 고용해서 "이걸 만들어주세요"라고 하면 기술 사양이 부족합니다. 그러나 "이런 감성의 앱을 만들고 싶다"는 방향은 가장 잘 담겨 있습니다.

### grill-me 설계도의 독자

**→ 그 대화에 참여했던 개발자 본인**

각 결정의 근거가 **대화 기록 안에** 있습니다. 설계도만 보면 "왜 단일 프로세스인가?"를 알 수 없지만, 대화록을 함께 읽으면 이해됩니다. 문서보다 **대화가 더 중요한** 구조.

### brainstorming 설계도의 독자

**→ 이 대화에 참여하지 않은 다른 개발자**

TypeScript 인터페이스, SQL 스키마, 파일 트리까지 있으므로, 대화록 없이 설계도만으로도 구현을 시작할 수 있습니다. **가장 이식성이 높은** 문서.

## 5. "구현 준비도" 평가

각 설계도를 받은 개발자가 코딩을 시작하기까지 추가로 결정해야 할 것들:

### office-hours 설계도를 받은 경우

추가로 결정해야 할 것:
- TypeScript 인터페이스 직접 설계
- SQL 스키마 상세화 (인덱스, settings 테이블)
- 에러 처리 방식 결정
- UI 컴포넌트 구조 설계
- 테스팅 전략 결정
- 파일/폴더 구조 결정

→ **구현 준비도: 낮음** — 좋은 시작점이지만 기술 설계 대부분이 남아 있음

### grill-me 설계도를 받은 경우

추가로 결정해야 할 것:
- UI 컴포넌트 구조 설계
- 에러 처리 방식 결정
- 테스팅 전략 결정
- 파일/폴더 구조 결정
- 인터페이스 상세화

→ **구현 준비도: 중간** — 기술 결정은 완료, UI와 에러 처리가 남아 있음

### brainstorming 설계도를 받은 경우

추가로 결정해야 할 것:
- Firefox URL 추적 실제 검증

→ **구현 준비도: 높음** — 거의 바로 코딩 시작 가능

## 7. 설계도에 담긴 철학 차이

세 설계도에서 가장 흥미로운 점은 **동일한 결론**(Electron + TypeScript + React, SQLite, 트레이 앱)에 도달했음에도 **전혀 다른 이유와 방식으로 기록**한다는 것입니다.

### office-hours 설계도가 말하는 것

> "이 앱은 개발자들이 설치하면 바로 쓸 수 있는, 차트가 예쁜 미니멀 도구다."

제품의 **정체성(identity)**을 가장 잘 담습니다. 6개월 후 이 설계도를 읽으면 "내가 왜 이걸 만들려 했는가"가 생각납니다.

### grill-me 설계도가 말하는 것

> "이 기술 결정들은 이러이러한 이유로 이렇게 선택되었다."

**결정의 근거**를 가장 잘 담습니다. 나중에 "왜 WPF가 아니라 Electron으로 했지?"라는 질문에 답할 수 있습니다.

### brainstorming 설계도가 말하는 것

> "다음 주 월요일에 코딩 시작할 수 있다."

**구현 준비**를 가장 잘 담습니다. 신입 개발자에게 건네줘도 이해하고 시작할 수 있는 수준.

## 8. 세 설계도를 합치면?

세 스킬의 설계도를 상호 보완적으로 사용한다면:

```
office-hours 설계도   →  "왜, 무엇을" 방향성 확립
        +
grill-me 설계도       →  "각 결정을 왜 그렇게 했는가" 근거 추가
        +
brainstorming 설계도  →  "어떻게 구현할 것인가" 상세화
        =
완전한 제품 설계 문서
```

현실에서는 하나의 스킬만 쓰는 것이 일반적이므로, **목적에 따라 선택**하는 것이 중요합니다.

| 상황 | 추천 스킬 |
|------|---------|
| 아이디어의 가치와 방향을 먼저 확인하고 싶다 | `/office-hours` |
| 이미 만들 것을 알고, 기술 결정을 기록하고 싶다 | `/grill-me` |
| 팀원에게 넘길 수 있는 완성된 스펙이 필요하다 | `/brainstorming` |
| 세 가지 모두 중요하다 | `/office-hours` → `/grill-me` → `/brainstorming` 순서로 |
