# 각 스킬의 장점과 단점

---

## `/office-hours` (gstack)

### 장점

#### 1. 비즈니스 검증의 깊이
YC 오피스 아워를 AI로 재현한 가장 완성도 높은 구현입니다. 6개의 강제 질문은 실제 YC 파트너들이 스타트업에게 묻는 핵심 질문을 압축한 것으로, 아이디어의 실현 가능성을 체계적으로 검증합니다.

```
Q1 수요 현실    → "정말 필요로 하는 사람이 있는가?"
Q2 현재 상태    → "지금 어떻게 해결하고 있는가?"
Q3 구체적 타겟  → "누가 가장 필요로 하는가?"
Q4 최소 쐐기    → "가장 작게 시작할 수 있는 것은?"
Q5 실제 관찰    → "실제 사용을 직접 봤는가?"
Q6 미래 적합성  → "세상이 변해도 살아남는가?"
```

#### 2. 누적 지식 시스템
반복 사용할수록 더 가치있어지는 구조입니다.
- 세션 기록으로 이전 과제 추적
- 학습 로그로 프로젝트별 인사이트 축적
- 사용자 프로파일로 창업자 여정 추적
- 티어별 맞춤 클로징으로 관계 심화

#### 3. 크로스 모델 검증
Codex 또는 Claude 서브에이전트를 통한 **독립적 2차 의견**을 제공하여 확증 편향[^1]을 방지합니다. 동일 AI 시스템의 관점에 갇히지 않고 다양한 시각을 확보합니다.

#### 4. 반시오판티즘 규칙의 명시성
"그것은 흥미로운 접근이네요"와 같은 무의미한 긍정 표현을 명시적으로 금지하고, 대신 구체적인 입장 표명을 요구합니다. 이는 AI의 고질적 문제인 **동조 편향**을 설계 수준에서 차단합니다.

#### 5. 맥락 인식 자료 추천
34개의 YC 관련 자료 풀에서 사용자의 세션 맥락에 맞는 2~3개를 선별하여 추천합니다. 일방적 목록이 아닌 **큐레이션된** 학습 경로를 제공합니다.

#### 6. 모드 적응성
- 스타트업 모드: 날카로운 비즈니스 검증
- 빌더 모드: 열정적인 창의적 협업

동일한 스킬로 완전히 다른 경험을 제공합니다.

---

### 단점

#### 1. 과도한 복잡성
2,090줄의 프롬프트는 유지 보수[^2] 부담이 극도로 높습니다. 수정 시 의도치 않은 부작용이 발생할 가능성이 높고, 전체를 이해하는 데만 수 시간이 걸립니다.

#### 2. 셋업 의존성
많은 기능이 외부 바이너리[^3]에 의존합니다:
- `gstack-config`, `gstack-slug` 등의 커스텀 CLI 도구
- `browse/dist/browse` (브라우저 자동화 바이너리)
- `design/dist/design` (디자인 생성 바이너리)
- `codex` CLI

이 도구들이 설치되지 않으면 기능이 단계적으로 비활성화됩니다.

#### 3. gstack 생태계 종속성
`~/.gstack/` 경로, gbrain, gstack-specific 설정 등 **gstack 전용 인프라**에 깊게 종속되어 있습니다. 다른 환경으로 이식하거나 독립적으로 사용하기 어렵습니다.

#### 4. 과도한 질문 게이팅[^4]
텔레메트리 동의, 라우팅 추가 여부, gbrain 설정, 아티팩트 동기화[^5] 등 스킬 실행 전 처리해야 할 질문이 많습니다. 빠르게 핵심에 도달하고 싶은 사용자에게 마찰이 됩니다.

#### 5. 비즈니스 중심 편향
기술적 설계 결정보다 비즈니스 검증에 집중합니다. 이미 유효성이 검증된 아이디어에 대해 기술 아키텍처를 설계하는 용도로는 적합하지 않습니다.

## `/grill-me` (mattpock)

### 장점

#### 1. 극단적 단순성
11줄로 핵심 기능을 완전히 구현했습니다. 오버엔지니어링[^6] 없이 목적에 집중한 최소주의 설계입니다. 어떤 환경에서도 즉시 작동합니다.

#### 2. 낮은 마찰
사용자가 준비해야 할 것이 없습니다. 설계나 계획이 있으면 그냥 시작할 수 있습니다. 복잡한 온보딩[^7]이나 모드 선택 없이 즉시 진입합니다.

#### 3. AI 추천 답의 협업 가치
각 질문에 AI의 추천 답을 함께 제시하는 것은 중요한 설계 선택입니다. 사용자가 "모르겠어요"에서 멈추지 않고 추천 답을 기반으로 동의/반대/수정할 수 있어 **의사결정 속도**가 높아집니다.

#### 4. 코드베이스 자동 탐색
질문이 코드베이스로 답할 수 있는 것이면 AI가 직접 탐색합니다. 이는 중요한 기능입니다 — 실제 코드 상태를 근거로 결정을 내릴 수 있기 때문입니다.

#### 5. 유연한 적용 범위
어떤 종류의 계획이나 설계에도 적용 가능합니다. 아키텍처 결정, 기능 스펙, API 설계, 배포 전략 등 모든 영역에서 동일하게 작동합니다.

---

### 단점

#### 1. 출력물 없음
대화로 공유된 이해에 도달하지만 문서가 없습니다. 나중에 참고할 기록이 남지 않으며, 같은 내용을 다시 논의해야 할 수 있습니다.

#### 2. 종료 기준 불명확
"공유된 이해"가 언제 달성되었는지 기준이 없습니다. AI가 판단해야 하는데, 너무 일찍 끝낼 수도, 너무 오래 끌 수도 있습니다.

#### 3. 프로세스 일관성 부족
정해진 질문 세트나 단계가 없어 매번 다른 품질의 결과가 나올 수 있습니다. 어떤 때는 중요한 결정을 놓칠 수 있습니다.

#### 4. 비즈니스 검증 부재
기술적 설계 트리를 탐색하는 데 특화되어 있어 "이게 올바른 문제인가?"를 검증하는 기능이 없습니다.

#### 5. 이미 계획이 있어야 함
아직 아이디어만 있는 단계에는 적합하지 않습니다. 적어도 기본적인 계획이나 설계가 있어야 의미 있는 질문이 가능합니다.

## `/brainstorming` (superpowers)

### 장점

#### 1. 완성된 워크플로우
아이디어에서 구현 계획까지의 전체 흐름을 하나의 스킬로 처리합니다. 9단계 체크리스트는 중요한 것을 빠뜨리지 않게 하는 **인지 오프로딩[^8]** 역할을 합니다.

#### 2. YAGNI 원칙의 강조
모든 설계에서 불필요한 기능을 제거하라는 원칙을 명시적으로 강조합니다. AI가 기능을 추가하는 방향으로 흐르기 쉬운데, 이 스킬은 반대 방향으로 힘을 줍니다.

#### 3. 스펙 자체 검토
사용자에게 보여주기 전에 AI가 스스로 4가지 항목을 검토합니다:
1. 플레이스홀더[^9] 스캔 (TBD, TODO 등)
2. 내부 일관성 확인
3. 스코프[^10] 적절성 확인
4. 모호성 확인

이는 품질 보증 단계를 프롬프트 수준에서 강제화합니다.

#### 4. git 통합
스펙 문서를 git에 커밋하여 **변경 이력**을 남깁니다. 설계가 어떻게 발전했는지 추적 가능하며, 팀 협업 시 리뷰하기 쉽습니다.

#### 5. 비주얼 컴패니언
브라우저 기반 시각적 도우미를 선택적으로 제공합니다. 모든 질문에 강제하지 않고 시각적 처리가 도움이 되는 질문에만 사용하는 **선택적 적용**이 현명합니다.

#### 6. 독립성과 이식성
gstack이나 특정 생태계에 종속되지 않습니다. 어느 프로젝트에서도 표준 파일 시스템과 git만 있으면 작동합니다.

#### 7. 스코프 과부하 방지
요청이 여러 독립 시스템을 포함하면 즉시 분해를 제안합니다. "모든 것을 한 번에"하려는 경향을 구조적으로 방지합니다.

---

### 단점

#### 1. 비즈니스 검증 부재
기술적 설계에 집중하며 "이것을 만들어야 하는가?"를 검증하지 않습니다. `/office-hours`의 수요 검증이나 현재 상태 분석에 해당하는 것이 없습니다.

#### 2. 강제 직전 스킬 호출
항상 `writing-plans` 스킬 호출로 끝나야 합니다. `writing-plans`가 없는 환경에서는 마지막 단계가 실패합니다.

#### 3. 중간 복잡도의 모호함
`/grill-me`보다는 복잡하지만 `/office-hours`보다는 단순합니다. 이 중간 지점이 어느 쪽의 강점도 완전히 갖지 못할 수 있습니다.

#### 4. 날카로움의 부재
`/office-hours`의 반시오판티즘 규칙이나 `/grill-me`의 집요한 질문에 비해, `/brainstorming`은 상대적으로 협력적이고 부드럽습니다. 날카로운 검증보다 완성도에 집중합니다.

[^1]: **확증 편향(Confirmation bias)**: 자신의 기존 믿음이나 가설을 확인하는 정보만 찾고 반대 정보는 무시하는 경향. 동일한 AI가 계속 같은 관점만 가질 수 있어 독립적 검증이 필요.
[^2]: **유지 보수(Maintenance)**: 소프트웨어나 문서를 현재 상태로 유지하거나 개선하는 지속적인 작업.
[^3]: **바이너리(Binary)**: 컴파일된 실행 파일. 소스 코드 없이 바로 실행 가능한 프로그램.
[^4]: **질문 게이팅(Question gating)**: 다음 단계로 진행하기 전에 사용자에게 질문하는 것. 너무 많으면 진행 속도가 느려짐.
[^5]: **아티팩트 동기화(Artifacts sync)**: 로컬에서 생성된 디자인 문서, 계획 등을 원격 저장소(GitHub 등)와 동기화하는 것.
[^6]: **오버엔지니어링(Over-engineering)**: 현재 필요보다 지나치게 복잡하거나 정교한 시스템을 구축하는 것. 단순한 문제에 복잡한 해결책을 적용.
[^7]: **온보딩(Onboarding)**: 새로운 도구나 서비스를 처음 사용할 때 거치는 초기 설정 및 안내 과정.
[^8]: **인지 오프로딩(Cognitive offloading)**: 기억하거나 생각해야 할 것을 외부 도구(체크리스트, 문서 등)에 위임하여 인지 부하를 줄이는 것.
[^9]: **플레이스홀더(Placeholder)**: "추후 작성 예정"을 의미하는 임시 텍스트. TBD(To Be Determined), TODO 등이 이에 해당.
[^10]: **스코프(Scope)**: 작업의 범위. 스코프가 너무 넓으면 한 번에 구현하기 어렵고, 설계가 모호해짐.
