# 공통점과 핵심 차이점

---

## 공통점

### 1. "질문은 하나씩" 원칙

세 스킬이 공유하는 가장 명확한 공통 원칙입니다.

| 스킬 | 원문 |
|------|------|
| `/office-hours` | "Ask these questions **ONE AT A TIME** via AskUserQuestion." |
| `/grill-me` | "Ask the questions one at a time." |
| `/brainstorming` | "Only one question per message" |

**왜 이 원칙이 중요한가?**  
여러 질문을 동시에 하면 사용자는 어디에 집중해야 할지 모르고, 중요한 질문이 다른 질문에 묻힐 수 있습니다. 한 번에 하나씩 묻는 것은 **대화의 깊이**를 유지하는 핵심 기법입니다.

---

### 2. 구현 전 설계 우선주의

세 스킬 모두 코드 작성 전에 충분한 이해와 설계를 요구합니다.

```
/office-hours  → "HARD GATE: Do NOT invoke any implementation skill"
/grill-me      → 공유된 이해 도달 전까지 계속 질문
/brainstorming → "HARD GATE: Do NOT invoke any implementation skill... 
                  write any code, scaffold any project"
```

이는 세 스킬이 **"빠른 코딩의 함정"**에 대한 공통된 인식에서 출발했음을 보여줍니다. 설계 없이 바로 구현에 들어가는 것이 결국 더 많은 낭비를 초래한다는 철학이 공유됩니다.

---

### 3. 대안 탐색의 강조

세 스킬 모두 하나의 접근법에 집착하지 않고 여러 대안을 탐색합니다.

| 스킬 | 대안 탐색 방식 |
|------|--------------|
| `/office-hours` | Phase 4에서 2~3개의 접근법 (최소 실행 가능 + 이상적 아키텍처 + 창의적) 필수 |
| `/grill-me` | 설계 트리의 각 분기를 탐색하며 결정 |
| `/brainstorming` | "Propose 2-3 different approaches with trade-offs" |

---

### 4. 컨텍스트 파악 우선

대화를 시작하기 전에 현재 상태를 이해하는 것을 공통적으로 강조합니다.

| 스킬 | 컨텍스트 파악 방법 |
|------|-----------------|
| `/office-hours` | `git log`, `CLAUDE.md`, 기존 디자인 문서 읽기 |
| `/grill-me` | "코드베이스를 탐색하면 직접 탐색" |
| `/brainstorming` | "Check out the current project state first (files, docs, recent commits)" |

이는 AI가 사용자의 상황을 모른 채 추상적인 조언만 하는 것을 방지합니다.

---

### 5. 추천 제시의 의무화

세 스킬 모두 AI가 단순히 질문만 하는 것이 아니라 자신의 입장을 표명하도록 설계되었습니다.

| 스킬 | 추천 방식 |
|------|---------|
| `/office-hours` | AskUserQuestion에 "Recommendation" 필드 필수 |
| `/grill-me` | "For each question, provide your recommended answer" |
| `/brainstorming` | "Lead with your recommended option and explain why" |

AI가 "이것도 있고 저것도 있다"가 아닌 **명확한 입장**을 취하게 하는 설계입니다.

---

### 6. 탈출구(Escape Hatch) 제공

사용자가 과정을 건너뛰고 싶을 때의 처리를 모두 고려합니다.

- `/office-hours`: "escape hatch" 명시 — 두 번 재촉하면 존중하고 다음 단계로 진행
- `/grill-me`: 암묵적으로 사용자가 방향을 결정
- `/brainstorming`: 스코프가 너무 크면 분해를 제안하고 계속 진행

---

## 핵심 차이점

### 1. 대상 독자

```
/office-hours  → 스타트업 창업자 또는 빌더 (비즈니스 맥락)
/grill-me      → 설계가 있는 개발자 (기술 맥락)
/brainstorming → 아이디어가 있는 개발자 (기술 맥락, 모든 경험 수준)
```

`/office-hours`는 **창업자**를 위한 도구이고, 나머지 둘은 **개발자**를 위한 도구입니다.

---

### 2. 질문의 성격

```
/office-hours  → 심문(Interrogation): 증거를 요구하고 전제를 도전
                 "이 증거가 충분하지 않습니다. 더 구체적으로 말해주세요."

/grill-me      → 탐정(Detective): 설계 트리를 따라 결정을 명시화
                 "이 결정에 대해 어떻게 생각하세요? 제 추천은 X입니다."

/brainstorming → 협력(Collaboration): 이해를 쌓고 합의를 만들어감
                 "이 접근법이 맞아 보이나요?"
```

---

### 3. 사용자에 대한 기본 가정

| 스킬 | 사용자에 대한 가정 |
|------|-----------------|
| `/office-hours` | "당신의 첫 번째 답은 충분하지 않을 것이다" (의심에서 시작) |
| `/grill-me` | "당신에게 계획이 있고, 빈틈을 찾고 싶다" (신뢰에서 시작) |
| `/brainstorming` | "당신은 아이디어가 있고, 구체화가 필요하다" (중립에서 시작) |

---

### 4. 스킬의 복잡성 철학

이것이 세 스킬의 가장 근본적인 차이입니다.

**`/office-hours` — 풍부함(Richness) 철학**
> "AI가 만드는 것을 저렴하게 만든다. 완전성을 추천하라."  
> (Boil the Lake 원칙 — "호수를 끓여라")

YC 오피스 아워의 **전체 경험**을 재현하는 것이 목표입니다. 그러므로 규모가 클수록 정당화됩니다.

**`/grill-me` — 최소주의(Minimalism) 철학**
> 핵심 행동만 정의하고 나머지는 AI의 판단에 위임

3줄 지시사항이 수백 줄의 상세 규칙만큼 효과적일 수 있다는 신념.

**`/brainstorming` — 완전성(Completeness) 철학**
> "모든 프로젝트는 이 과정을 거친다. 단순한 것도 예외 없다."

체크리스트를 통한 **빠짐없는** 진행이 목표.

---

### 5. 종료 방식

| 스킬 | 종료 방식 | 결과물 |
|------|---------|-------|
| `/office-hours` | 디자인 문서 승인 후 관계형 클로징 | 디자인 문서 + 다음 액션 1개 |
| `/grill-me` | 공유된 이해 도달 | 없음 |
| `/brainstorming` | `writing-plans` 스킬 호출 | 스펙 문서 (git 커밋) + 구현 계획 |

`/office-hours`는 다음 스킬을 **선택적으로 추천**하고,  
`/brainstorming`은 다음 스킬을 **필수적으로 호출**하며,  
`/grill-me`는 **다음 단계를 정의하지 않습니다**.

## 설계 원칙의 스펙트럼 분석

### 명시적 vs 암묵적 규칙

```
명시적 (모든 것이 규정됨)        암묵적 (AI의 판단에 위임)
     ←──────────────────────────────────→
     
  /office-hours          /brainstorming    /grill-me
  
  Anti-sycophancy        체크리스트 제공    "집요하게 하라"는
  규칙 명시               하지만 각 단계의  지침만 있고
  푸시 패턴 명시          방법은 AI 자율    나머지는 AI 판단
  AskUserQuestion        
  포맷까지 규정           
```

### 인간 노력 vs AI 노력

```
인간이 더 많이 함              AI가 더 많이 함
     ←──────────────────────────────────→
     
  /office-hours          /brainstorming    /grill-me
  
  6개의 날카로운           명확화 질문에    AI가 코드베이스를
  질문에 구체적            답하고 설계를     직접 탐색하고
  답해야 함               승인해야 함       추천도 제시
```

## 상호 보완성

세 스킬은 경쟁하는 것이 아니라 **상호 보완적**으로 사용할 수 있습니다.

### 이상적인 사용 순서

```
단계 1: /office-hours 
        → "이것을 만들어야 하는가?"를 검증
        
단계 2: /brainstorming
        → "무엇을 어떻게 만들 것인가?"를 설계
        
단계 3: /grill-me
        → "설계의 빈틈이 없는가?"를 최종 점검
        
단계 4: 구현 시작
```

혹은 더 빠른 경로:

```
단계 1: /grill-me (이미 계획이 있을 때)
        → 빠른 설계 검증
        
단계 2: 구현 시작
```

## 스킬 설계에서 배울 수 있는 교훈

### 교훈 1: 길이와 품질은 비례하지 않는다
`/grill-me`는 11줄이지만 목적에 완벽히 부합합니다. 스킬의 길이는 그것이 해결하려는 문제의 복잡성에 비례해야 하지, 많을수록 좋은 것이 아닙니다.

### 교훈 2: 명시적 원칙이 암묵적 원칙보다 일관성이 높다
`/office-hours`가 Anti-sycophancy 규칙을 명시적으로 나열하는 것은 AI가 매번 다르게 해석할 여지를 줄입니다. 반면 `/grill-me`의 "집요하게"는 AI에 따라 해석이 달라질 수 있습니다.

### 교훈 3: 산출물은 스킬의 가치를 연장한다
산출물(문서, git 커밋)이 있는 스킬은 대화가 끝난 후에도 가치를 제공합니다. `/grill-me`는 대화 중에만 가치가 있고 종료 후에는 흔적이 없습니다.

### 교훈 4: 종료 조건의 명확성이 중요하다
"공유된 이해에 도달할 때"(grill-me)는 모호한 종료 조건입니다. "writing-plans를 호출할 때"(brainstorming)나 "디자인 문서가 승인될 때"(office-hours)는 명확합니다.

### 교훈 5: 사용자의 에너지를 어디에 집중시킬지가 스킬의 가치를 결정한다
- `/office-hours`: 비즈니스 검증에 집중
- `/grill-me`: 기술 결정에 집중  
- `/brainstorming`: 스펙 완성에 집중

스킬은 사용자가 무엇에 집중해야 하는지를 안내하는 **집중 도구**입니다.
