# 종합비교 — 5개 스킬을 관통하는 4가지 원칙

5개 스킬([01_grill-me](01_grill-me.md), [02_grill-with-docs](02_grill-with-docs.md), [03_tdd](03_tdd.md), [04_diagnose](04_diagnose.md), [05_to-prd](05_to-prd.md))은 서로 다른 일을 하지만, 밑바탕에 같은 생각이 깔려 있다.

## 4가지 공통 원칙

| 원칙 | 쉽게 말하면 | 어디서 나타나나 |
|------|------------|----------------|
| **겉으로 드러나는 동작을 검증한다** | "안에서 어떻게 짰는지"가 아니라 "밖에서 보이는 결과"를 본다 | tdd(공개 함수만 테스트), to-prd(외부 동작만 기록), diagnose(제대로 된 테스트 지점) |
| **한 번에 하나씩 처리한다** | 한꺼번에 몰아치지 않고 하나 끝내고 다음으로 | grill(질문 하나씩), tdd(테스트 하나→코드 하나), diagnose(변수 하나씩 바꿔보기) |
| **AI가 먼저 답을 내고 검증받는다** | AI가 입장을 제시 → 사람이 승인/반박 | grill(추천 답변), diagnose(가설 순위), tdd·to-prd(사람 승인 단계) |
| **정한 용어·결정을 문서로 남긴다** | 합의한 내용을 휘발시키지 않고 파일에 기록 | grill-with-docs가 `CONTEXT.md`·ADR을 만들고 → 나머지가 그걸 가져다 씀 |

## 두 갈래 구조

5개는 크게 "**계획 단계**"와 "**실행 단계**"로 나뉜다.

```
┌─────────────────────────┬──────────────────────────────────────┐
│       계획 단계            │            실행 단계                  │
├─────────────────────────┼──────────────────────────────────────┤
│ grill-me                │ tdd       (행동 기반 구현)              │
│ grill-with-docs         │ diagnose  (규율 있는 버그 추적)         │
│ (생각을 강제로 명확화)       │ to-prd    (대화→PRD 발행)             │
└─────────────────────────┴──────────────────────────────────────┘
```

## 스킬들이 이어지는 흐름

실제로는 이런 순서로 맞물려 쓸 수 있다.

```
grill-with-docs ──→ to-prd ──→ tdd ──→ diagnose
 (언어·결정 확정)   (PRD 발행)  (구현)   (버그 추적)
```

- `grill-with-docs`로 **쓸 용어와 결정을 확정**하고
- `to-prd`로 그 내용을 **PRD 문서로 발행**한 뒤 (`ready-for-agent` 표시)
- `tdd`로 **실제 구현**하고
- 버그가 나면 `diagnose`로 **차분히 원인을 추적**한다.

다섯 스킬의 공통 바탕은 `CONTEXT.md`(프로젝트 용어집)와 `docs/adr/`(왜 그렇게 정했는지 기록)이다. grill-with-docs가 이 둘을 **만들어내고**, tdd·diagnose·to-prd가 코드를 탐색할 때 그걸 **가져다 쓴다**.

## grill-me vs grill-with-docs

이름이 비슷한 두 스킬의 차이.

| 항목 | grill-me | grill-with-docs |
|------|----------|-----------------|
| 분량 | 11줄 | 본문 + 부속 파일 2개 |
| 목적 | 생각 정리만 | 정리한 내용을 문서로 정착 |
| 결과물 | 머릿속 합의 (문서 없음) | `CONTEXT.md` / ADR 갱신 |
| 사전 준비 | 없음 | 프로젝트 문서 구조를 인식해야 함 |
| 질문 방식 | 질문을 죽 던짐 | 질문마다 답을 기다림 |

## 심화 분석 — 스킬별 핵심

프롬프트를 "무엇을 시키나"가 아니라 **"왜 이렇게 썼나 / 무엇을 막으려 하나"** 관점에서 본 정리다.

아래 7가지 관점("분석 렌즈")으로 본다:

| 렌즈 | 묻는 것 |
|------|--------|
| ① 쓸 때 / 쓰면 안 될 때 | 언제 효과적이고, 언제 오히려 역효과인가 |
| ② 막으려는 AI의 흔한 실수 | 그냥 두면 AI가 저지를 실수를 어떤 문구로 막나 |
| ③ 부속 파일의 역할 | 본문을 쪼개 옆 파일에 둔 이유와 그 도움 방식 |
| ④ 딴 길로 못 새게 막는 장치 | 순서·완료 기준을 강제하는 구조 |
| ⑤ 결과물 형식 약속 | 최종 산출물을 어떤 틀로 못박았나 |
| ⑥ 말투가 하는 일 | 강조·명령조 같은 표현이 행동에 주는 효과 |
| ⑦ 다른 스킬과 맞물리는 방식 | 혼자 쓰나, 공유 기반에 기대나 |

> 약한 칸은 "거의 없음"으로 두되 *왜 없는지*를 적었다. 그 빈칸이 곧 그 스킬의 성격을 말해주기 때문이다.

### grill-me
- **① 쓸 때 / 쓰면 안 될 때:** *이미 있는 계획*을 따져볼 때 좋다. 아이디어가 백지일 때는 따질 게 없어 헛돈다(그건 brainstorming/office-hours가 할 일).
- **② 막으려는 실수:** "한 번에 하나씩" → 질문 한꺼번에 쏟기 방지 / "코드로 답되면 직접 찾아봐라" → 게으른 되묻기 방지.
- **③ 부속 파일의 역할:** **없음.** 본문 11줄로 자족 — 부속이 없다는 것 자체가 "가볍게 어디서든 쓰는 도구"라는 신호.
- **④ 막는 장치:** **거의 없음.** 단계 잠금·체크리스트가 없고 "한 번에 하나씩"이 유일한 순서 통제. 그만큼 자유롭고 가볍다.
- **⑤ 결과물 형식 약속:** **없음.** 산출물은 파일이 아니라 "서로 맞춰진 이해"(머릿속). 문서를 안 남기는 게 의도.
- **⑥ 말투:** 짧아도 "끈질기게 물어라" + "질문마다 추천 답을 달아라" 두 마디로 행동이 정해진다.
- **⑦ 맞물리는 방식:** 혼자서도 돌아간다. 공유 문서(CONTEXT/ADR)를 안 쓰는, grill-with-docs의 **경량판**.

### grill-with-docs
- **① 쓸 때 / 쓰면 안 될 때:** 계획을 *프로젝트의 용어·기존 결정*에 비추어 검증할 때 좋다. 문서가 아예 없는 극초기나 가벼운 잡담엔 과하다.
- **② 막으려는 실수:** 용어 혼용(즉시 지적), 모호한 말 방치(표준어 제안), 결정 휘발(바로 문서화), 말과 코드 불일치(교차 확인).
- **③ 부속 파일의 역할:** `CONTEXT-FORMAT.md`·`ADR-FORMAT.md`가 *결과물의 형식*만 따로 보관 → 형식을 바꿔도 본문은 안 건드린다.
- **④ 막는 장치:** ADR은 "3가지 조건이 모두 맞을 때만" 만들게 해 **남발을 차단**. "CONTEXT.md는 용어집일 뿐"이라는 제약도 같은 역할.
- **⑤ 결과물 형식 약속:** `CONTEXT.md`(용어집) + ADR(결정 기록). 둘 다 정해진 템플릿을 따른다.
- **⑥ 말투:** 본문은 grill-me처럼 명령형. 부속의 "단호하게 정하라(Be opinionated)" 같은 표현이 어정쩡한 용어집을 막는다.
- **⑦ 맞물리는 방식:** 5개가 공유하는 용어집·ADR을 **만들어내는 쪽**. grill-me에 "문서 인식"을 더한 강화판.

### tdd
- **① 쓸 때 / 쓰면 안 될 때:** 만들 기능의 *동작을 말로 정의할 수 있을 때* 좋다. 뭘 만들지조차 모르는 탐색적 실험엔 안 맞는다.
- **② 막으려는 실수(핵심):** "테스트 다 쓰고 코드 다 쓰기 금지" → AI가 흔히 빠지는 *몰아쓰기*를 정면 차단. 내부를 mock하는 가짜 테스트도 금지.
- **③ 부속 파일의 역할:** 좋은 예/나쁜 예 코드(`tests.md`), mock 기준(`mocking.md`) 등 5개가 *지식과 예시*를 본문 밖으로 빼서, 본문은 흐름만 짧게 유지.
- **④ 막는 장치:** "테스트 실패(RED) 상태에선 리팩토링 금지", "사이클마다 체크리스트", "계획에 사용자 승인"으로 순서·완료를 강제.
- **⑤ 결과물 형식 약속:** 코드 + 테스트. 별도 문서 템플릿은 없지만 "사이클 체크리스트 통과"가 사실상 완료 조건.
- **⑥ 말투:** "절대 ~하지 마라(DO NOT)", "쓰레기 테스트", "헤드라이트보다 앞서 달리지 마라" 같은 강한 경고어로 안티패턴을 각인.
- **⑦ 맞물리는 방식:** 용어집·ADR을 가져다 쓰고, to-prd가 정한 "테스트 결정"을 이어받아 실제 구현으로 옮긴다.

### diagnose
- **① 쓸 때 / 쓰면 안 될 때:** *어려운 버그·성능 저하*에 좋다. 한눈에 보이는 사소한 버그엔 6단계 절차가 오히려 거추장스럽다.
- **② 막으려는 실수:** "가설 3~5개 먼저 순위" → 첫 생각에 갇히기 방지 / `[DEBUG-]` 꼬리표 → 로그 방치 방지 / "로그 다 찍고 grep 금지" / 재현 확인으로 "엉뚱한 버그 고치기" 방지.
- **③ 부속 파일의 역할:** `scripts/hitl-loop.template.sh` — 사람이 직접 눌러봐야 하는 최후의 경우에도 절차가 흐트러지지 않게 돕는 보조 스크립트.
- **④ 막는 장치(핵심):** "재현 수단을 만들기 전엔 다음 단계 금지" 같은 **단계 잠금**과 Phase 6 완료 체크리스트. 디버깅을 *감*이 아니라 *절차*로 바꾼다.
- **⑤ 결과물 형식 약속:** 수정 + 재발 방지 테스트, 그리고 "맞았던 가설을 커밋 메시지에 기록". 테스트 끼울 자리가 없으면 그 사실 자체를 발견으로 남긴다.
- **⑥ 말투:** "이게 곧 이 스킬의 핵심이다", "포기하지 마라" 같은 강한 표현이 AI의 **섣부른 포기**를 누르고 어디에 힘쓸지 짚어준다.
- **⑦ 맞물리는 방식:** 용어집·ADR을 가져다 쓰고, 끝에서 구조 문제면 `/improve-codebase-architecture`로 넘긴다.

### to-prd
- **① 쓸 때 / 쓰면 안 될 때:** "**되묻지 말고 정리만 해라**"가 핵심. 대화가 충분히 쌓인 *뒤*에만 쓸모 있다. 빈약한 초반엔 빈 내용으로 부실한 문서만 나온다.
- **② 막으려는 실수:** 불필요한 재질문(종합만 하게) / 금방 낡는 산출물(파일 경로·코드 조각 금지).
- **③ 부속 파일의 역할:** **없음.** 대신 PRD 양식을 본문 안에 직접 품고 있다 — 따로 뺄 만큼 형식이 길지 않아서다.
- **④ 막는 장치:** 테스트 지점을 "사용자와 먼저 확인"하는 점검점, "`ready-for-agent` 외 추가 분류 불필요"로 군더더기 차단.
- **⑤ 결과물 형식 약속(핵심):** PRD(문제 / 해결 / 사용자 스토리 / 구현 결정 / 테스트 결정 / 범위 밖 / 메모) + `ready-for-agent` 라벨.
- **⑥ 말투:** "되묻지 마라(Do NOT interview)"를 대문자로 강조해, 이 스킬이 "정리 전용 모드"임을 못박는다.
- **⑦ 맞물리는 방식(허브):** grill → to-prd → tdd 흐름의 *중간 연결점*. 앞 단계가 정한 용어·테스트 지점을 물려받아 PRD로 굳힌다.
